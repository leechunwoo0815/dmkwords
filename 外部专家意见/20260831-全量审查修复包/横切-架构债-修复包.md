## 一、决策卡（需用户拍板）

### HC-A1【中·需拍板】EventBus 宪法与实现两头不靠：跨域写全直调，事件退化为通知总线

- **证据**【事实】（10 类写边全部核实，逐条有代码位置）：

| # | 写边 | 位置 |
|---|---|---|
| 1 | identity→billing（Deposit 置 refunded + 插 Ledger） | wm10_service.py:369-386 |
| 2 | identity→billing（Deposit 置 refunding ×3 处） | wm10_service.py:494-504、wm10_withdrawal_service.py:286-299、transfer_service.py:395-406 |
| 3 | identity→activity（直改报名状态） | wm10_service.py:549-565 |
| 4 | billing→identity（直接 new Order） | billing/service.py:111-122 |
| 5 | activity→identity（调私有方法建 Order + 改订单状态） | activity/service.py:440-442、:362-364 |
| 6 | circulation→catalog（直改副本状态） | circulation/service.py:272、:323-328 |
| 7 | reading→catalog（直改副本状态 ×4） | reading/service.py:359、:378-380、:400-402、:594 |
| 8 | reading→circulation（service 直调） | reading/service.py:597-601 |

对照：唯一走事件完成的跨域写只有审计（audit.requested）。
docstring 漂移实证：`events.py:169-177` 声称 OrderPaidEvent 订阅者含"child: 更新
会员状态 / deposit: 更新押金状态"——实际会员开通（identity/service.py:486-516）、
押金联动（:509-511）全是直调，事件仅被通知订阅器消费。
- **风险**【推断】：不是当下 bug（同事务直调一致性反而强），而是：① 宪法与代码
  系统性背离，新人按宪法写事件、老人按现状直调，两种风格并存；② 新增订阅方
  （WM12 支付回调）会漏掉只存在于直调里的副作用。
- **方案对比**（请用户拍板）：

| | 方案 A：按宪法迁移到事件 | 方案 B：修宪承认现状（推荐） |
|---|---|---|
| 内容 | 10 类写边逐条迁 EventBus，补跨域事务测试 | 宪法 §四改写："同进程同事务的域间联动允许 service 直调；EventBus 用于通知与审计" |
| 工作量 | 大（每条写边一个迁移+测试批，约 2-3 天） | 小（一份 ADR + 宪法一行修订） |
| 收益 | 解耦、订阅方可扩展、符合原宪法愿景 | 消除两头不靠、文档与现实一致、零回归风险 |
| 风险 | 迁移期引入回归（同事务直调→事件的事务边界变化） | 放弃事件化解耦愿景（单机部署下代价可控） |
| 推荐理由 | — | 项目为单机单进程部署（ADR-001/005），直调的事务一致性是**优点**而非债务；事件价值在通知场景已被验证（WM11） |

- **修复方案**：裁决后写 `docs/ADR/ADR-xxx-跨域联动方式.md`；方案 B 还需同步
  修订宪法 §四措辞（走宪法修订流程：提案+用户确认，AI 不自改宪法）
- **验证等级**：方案 B 纯文档；方案 A 为 C 级
- **标注**：【事实】（写边清单）；风险【推断】

### HC-A2【中·需拍板】Order/RefundRequest/WithdrawalRequest 宿主在 identity 域

- **证据**【事实】：`backend/domain/identity/models.py:102-103` 自述注释：

```text
class Order(BaseModel):
    """订单（billing 语义，宿主放 identity 域避免域循环；WM5 后如膨胀再拆 billing 域目录）。"""
```

宪法 §四定义 billing 域持有"订单(5类7态)、支付、退款、押金"。实测 billing 域只
有 Deposit/DepositLedger；订单逻辑分裂：创建/确认在 identity（OrderService 占
identity/service.py 的 330 行，全文件 701 行）、押金联动在 billing、活动订单入口
在 activity（调私有方法）。触发条件"WM5 后如膨胀再拆"已到而未拆——也是
HC-A3 循环依赖的直接根源。
- **方案对比**：

| | 方案 A：迁 billing 域（推荐，WM12 前） | 方案 B：ADR 保留 identity + 修宪法 |
|---|---|---|
| 工作量 | 纯代码移动（模型+OrderService+RefundRequest/WithdrawalRequest 迁 billing；7 个消费域 import 路径更新；alembic 无表变更）约 1 天 | 半小时文档 |
| 收益 | 域职责归位、断 HC-A3 循环、WM12 支付域归属清晰 | 零改动 |
| 风险 | 中（import 面广，靠 gate 架构关+全量测试护航） | 持续漂移，identity 继续膨胀 |

- **修复方案**：方案 A 施工步骤——① 建 billing 域新文件（models 搬运 + service
  拆 OrderService/RefundService 目录）② 全库 `rg "from backend.domain.identity.models import.*Order"`
  逐点改 import（审查实测 7 个消费域）③ identity 保留 re-export 兼容一个批次
  后删除 ④ gate 全量
- **验证等级**：C 级（跨 7 域）
- **标注**：【事实】

### HC-A6【中】LIKE 搜索通配符未转义（5 处）——用户传 % 即全表模糊

- **证据**【事实】：`identity/service.py:570-572`（orders keyword）、
  `reading/miniapp_router.py:132-134`（books）、`billing/service.py:231-233`
  （deposits）、identity parents/children 搜索——均为
  `f"%{keyword}%"` 裸拼接。非 SQL 注入（全参数化已核实），但 `%` 使前缀通配
  → 索引失效慢查询/轻量 DoS。
- **修复方案**：统一接线现成工具 `backend/common/sql_utils.py:16-30` 的
  `escape_like`（全库零调用——本卡是它的第一个用户）：

```text
from backend.common.sql_utils import escape_like
...
    like = f"%{escape_like(keyword)}%"
    q = q.filter(Book.title.like(like, escape="\\"), ...)
```

- **测试要求**：keyword=`%` 传给 /api/admin/orders，断言 total != 全表数
  （**修复前等于全表数，RED**）
- **验证等级**：B 级（跨三域小改）
- **标注**：【事实】
