## 二、任务卡

### WM13-F1【中】WM13 收件箱与计数全表加载 + Python 内存分页

- **验收可见性**：验收测不出（千级通知前无感）；badge 每 60s 轮询放大 QPS
- **证据**【事实】：`backend/domain/admin/todo_service.py:235` 与 `:341-344`：

```text
rows = q.order_by(AdminNotification.created_at.desc(), AdminNotification.id.desc()).all()   # 235，无 limit
...
all_rows = (
    self.db.query(AdminNotification).filter(AdminNotification.is_deleted == 0).all()        # 342，超管全表
)
```

`list_inbox` 随后在 Python 内过滤 status_filter、排序、切片分页（243-256）。
- **现象与根因**：通知表随运营积累线性膨胀（活动批量退款一晚可插数百条），每次
  badge 轮询 `todo_counts` 都全表拉取 + resolve_many 批量 IN 查询四张业务表。
  根因：显示态"实时算"设计落地时把过滤/分页也搬进了内存（显示态依赖业务表
  JOIN，SQL 端难以表达三态）。
- **修复方案**（分两步走，交接卡已有"千级再改 SQL"的裁定——本卡是排期卡）：
  - **短期（通知量 < 千时）**：`list_inbox` 加 `limit(1000)` 兜底 + keyword/scene
    过滤下推 SQL（保留 status 三态内存判定）；`todo_counts` 的 pending 计数改
    SQL 分组（pending 判定可翻译为对 refund/withdrawal/transfer/activity 四表的
    状态子查询——`todo_service.py:324-378` 的 resolve 逻辑逐 scene 下推）
  - **长期**：待办态落快照列或定时物化（挂 docs/09 排期，不在本卡）
- **测试要求**：既有 WM13 计数一致性测试回归（todo_counts == list_inbox pending
  的同源断言不弱化）；构造 200 条通知分页正确
- **验证等级**：B 级（admin 域）→ 涉及公共查询模式建议 C 级
- **施工顺序**：验收后随反馈批次（交接卡已有此挂账裁定）
- **标注**：【事实】（全表加载实证）；性能退化幅度【推断】

### WM13-F3【低】admin_notifications 唯一索引含可空列 is_deleted（NULL 不去重）

- **证据**【事实】：迁移 `alembic/versions/b8d4f2a6c9e1_wm13_admin_notification_table.py:60-62`
  中 `is_deleted SmallInteger nullable=True` 参与唯一索引。MySQL 唯一索引对 NULL
  不去重——若出现 NULL 行幂等失效。ORM 默认 0 兜底（当前无实害），但原生 SQL/
  批量导入可产生 NULL。orders/notifications 同款设计（既有模式）。
- **修复方案**：迁移改 `nullable=False, server_default="0"`（新迁移；orders/
  notifications 的同款列**不动**——历史模式，另立卡评估）。
- **测试要求**：alembic check 零差异；幂等写入回归（双触发只一条）
- **验证等级**：C 级（迁移）
- **标注**：【事实】
