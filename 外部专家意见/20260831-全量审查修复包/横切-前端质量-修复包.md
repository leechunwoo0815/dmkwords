### HC-F1【高】资金/状态机弹窗系统性缺失防双击（全站仅 2/15+ 处有 confirmLoading）

- **证据**【事实】：grep `confirmLoading` 全 src 仅 2 处（`SystemConfig.tsx:177`、
  `Notifications.tsx:569`）。无提交中禁用的资金/状态机 onOk ≥15 处：
  - `RefundCenter.tsx:302-304`（审核弹窗）、`:313-317`（执行退款）
  - `MemberManage.tsx:201`（退款 Modal.confirm）、`:596-607`（确认收款）
  - `DepositManage.tsx:165-176`（赔偿登记）
  - `ActivityManage.tsx:121`（退款审核）、`:59-76`（发布活动 onCreate）
  - `GrowthManage.tsx:297`（积分调整）
- **现象与根因**：antd `<Modal onOk>` 不会因 async 自动 loading——网络慢双击
  → 同一资金操作并发两次请求。与 P1-F1/F2/F3 的后端无锁缺陷叠加 = 完整触发链
  （后端修锁后前端仍应防：不制造脏请求）。根因：SystemConfig/Notifications 已建立
  正确模式（saving state + confirmLoading）未推广。
- **修复方案**（统一模板，参照项目内正确写法 `Notifications.tsx:151/269-283`）：

```tsx
// 每页每弹窗加 saving state + confirmLoading：
const [executeSaving, setExecuteSaving] = useState(false);
<Modal
  title="执行退款"
  confirmLoading={executeSaving}
  okButtonProps={{ disabled: executeSaving }}
  onOk={async () => {
    try {
      setExecuteSaving(true);
      await apiExecuteRefund(...);
      message.success("已执行");
      setOpen(false);
      await refresh();
    } catch (e) {
      message.error(e instanceof Error ? e.message : "执行失败");
    } finally {
      setExecuteSaving(false);
    }
  }}
```

  `Modal.confirm` 类（非受控）：onOk 返回 promise 时 antd 自带 loading
  （保持 `return apiX()` 即可），但双击需另加节流或改受控 Modal——
  建议资金类全部改受控 Modal 统一模式。
- **测试要求**：DevTools Network 限速 Slow 3G，双击各资金弹窗确认按钮，
  断言只发一次请求（逐弹窗手动清单核对）
- **验证等级**：A 级（tsc）——涉及 6 文件，一次批改完
- **施工顺序**：**与 P1-F2 同批交付**（前端防触发 + 后端防穿透）
- **标注**：【事实】

## 二、格式化与显示统一（两张工具卡）

### HC-F4【中】时间显示不统一：7 处 ISO 原始串含 "T" 直出

- **证据**【事实】：
  - 直出带 "T"：`MemberManage.tsx:438`（订单 created_at 无 render）、
    `GrowthManage.tsx:229,244`、`AuditLog.tsx:117`、`Reservations.tsx:92-93`、

  - slice 含 "T"：`CirculationDesk.tsx:226-227,254`（`v?.slice(0, 16)` 切出
    `2026-08-31T14:23`）
  - 正确范式对照组：`RefundCenter.tsx:196` `v.replace("T", " ").slice(0, 19)`
- **修复方案**：抽公共工具 `src/utils/format.ts`：

```tsx
export function formatDateTime(v?: string | null): string {
  if (!v) return "-";
  return v.replace("T", " ").slice(0, 19);
}
```

  9 处统一替换；金额/日期列建议加 `font-variant-numeric: tabular-nums`。
- **验证等级**：A 级（tsc）
- **标注**：【事实】

### HC-F5【低】金额格式化无两位小数保证（49.90 显示 49.9）

- **证据**【事实】：主流写法 `Number(v).toLocaleString()`（15+ 处）无
  minimumFractionDigits——`49.90` 显示 `49.9`；`ActivityManage.tsx:202`
  `` `￥${v}` `` 完全未格式化。grep `toFixed` 全站 0 处（无浮点精度问题——
  金额以字符串从后端来，仅显示层缺规范）。
- **修复方案**：并入 HC-F4 的 format.ts：

```tsx
export function formatMoney(v?: string | number | null): string {
  if (v === null || v === undefined) return "-";
  return `￥${Number(v).toLocaleString("zh-CN", {
    minimumFractionDigits: 2, maximumFractionDigits: 2,
  })}`;
}
```

- **验证等级**：A 级
- **标注**：【事实】

### HC-F7【中】URL 状态只读一次：同路由二次跳转参数不生效

- **证据**【事实】：`useState(searchParams.get("tab")...)` 只在挂载时取值——
  `RefundCenter.tsx:51-56`、`Notifications.tsx:131-137`、`MemberManage.tsx:92-102`。
  用户已停在 /refund-center 时，从通知中心再点另一条待办
  （`?tab=withdrawals&highlight=456`）→ 组件不重挂载 → **tab 不切换、不高亮**
  （WM13 的通知跳转定位高亮功能实际半失效）。
- **修复方案**：加 `useEffect` 监听 searchParams 同步 state，或全部改派生值
  （`const tab = searchParams.get("tab") ?? "refunds"`——推荐派生，URL 为唯一
  事实源 + mirrorUrl 写入已有）。
- **测试要求**：通知中心连点两条不同类型待办 → tab 切换 + 对应行高亮
- **验证等级**：A 级
- **标注**：【事实】（行为推断自 React Router 语义：同路径仅 search 变化不重挂载）

### HC-F8【中】数据获取全站无取消机制（竞态：旧响应覆盖新响应）

- **证据**【事实】：全站 26 处 useEffect 数据获取，0 处 AbortController/ignore 标志。
  典型：`MemberManage.tsx:186`（快速切 tab/翻页时 loadChildren 与 loadOrders 并发）、
  `Notifications.tsx:210-213`（box/tab/keyword 连续变化触发重建）。
- **修复方案**（最小模式，逐页推广）：

```tsx
useEffect(() => {
  let active = true;
  apiListOrders(...).then((v) => { if (active) setOrders(v); })
                    .catch(...);
  return () => { active = false; };
}, [deps]);
```

- **验证等级**：A 级
- **标注**：【事实】（竞态触发【推断】——慢网络/快速切换时）
