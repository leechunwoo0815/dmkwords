## B-1 【高|事实】TransferService.review() 缺少行锁——并发审核可触发12步事务双执行

**可见性**：阻断级（资金+状态双损）

**证据**：
- `backend/domain/identity/transfer_service.py:356-359`
```python
req = (
    self.db.query(TransferRequest)
    .filter(TransferRequest.id == transfer_id, TransferRequest.is_deleted == 0)
    .first()  # ← 缺少 with_for_update()
)
```
- 对比同文件 `apply()` 对 Child 行有锁（line 111 of wm10_withdrawal_service.py 同模式），`review()` 对 TransferRequest 无锁
- `review()` 的 approve 路径执行 12 步事务（lines 382-466）：source→withdrawn、押金退款自动创建、target→formal 继承到期日、双方解锁
- 两个超管同时点"通过"→ 两个事务都读到 `status=pending` → 都进入 12 步 → 第二个 commit 时 source 已经是 withdrawn（member_status 被覆盖两次）、target 到期日被覆盖、押金退款单创建两笔

**根因**：review 是管理端低频操作，开发者假设"不会有两个超管同时审同一单"，但未做防呆

**修复提案**：
```python
req = (
    self.db.query(TransferRequest)
    .filter(TransferRequest.id == transfer_id, TransferRequest.is_deleted == 0)
    .with_for_update()  # P1-F1 同模式
    .first()
)
```

**红测**：两个浏览器 tab 同时打开同一转让的审核页，同时点"通过"→ 观察是否创建两笔押金退款单

**门禁级别**：Service 单测（mock 两个并发 review 调用）

**依赖**：无

**事实/推断**：事实（代码无锁可验证）

## B-2 【中高|事实】_complete_refund_withdrawal() 过早解锁——押金退款失败时孩子已解冻但退会卡死

**可见性**：高（影响资金安全与操作冻结语义）

**证据**：
- `backend/domain/identity/wm10_service.py:393-394`（execute 成功路径调用 _complete_refund_withdrawal）
- `backend/domain/identity/wm10_service.py:482-499`：
```python
def _complete_refund_withdrawal(self, admin, req, order):
    child = self.db.query(Child).filter(Child.id == req.child_id).first()
    if not child or child.member_status == Child.MEMBER_WITHDRAWN:
        return
    child.member_status = Child.MEMBER_WITHDRAWN
    child.withdraw_reason = reason_code
    child.operation_locked = 0  # ← 过早解锁
    # 然后自动发起押金退款申请（lines 500-534）
```
- 场景：主动退会（normal source）有两笔退款单——会员费订单 + 押金。会员费先 execute 成功 → _complete_refund_withdrawal 把 child 设为 withdrawn + operation_locked=0 → 押金退款 execute 失败 → 退会流程卡在 refunding（_advance_withdrawal 不会推进因为 open_cnt > 0）→ 但 child 已经 unlocked，家长可以重新借书/报名，而退会状态是"半完成"
- 对比：`_advance_withdrawal()` (line 536-577) 正确地在所有退款单终态后才解锁

**根因**：_complete_refund_withdrawal 把"退会状态设置"和"解锁"绑定在第一笔退款成功上，而非所有退款完成后

**修复提案**：
- 方案 A：_complete_refund_withdrawal 中不设置 operation_locked=0，让 _advance_withdrawal 统一解锁
- 方案 B：在 _complete_refund_withdrawal 中检查是否还有关联的 pending 退款单，有则不解锁

**红测**：创建一个有押金的孩子，发起退会，审核通过，先 execute 会员费退款成功，再 execute 押金退款失败 → 观察 child.operation_locked 是否为 0 且 withdrawal.status 是否为 refunding

**门禁级别**：集成测试（需要两笔退款单的场景）

**依赖**：与 B-3 相关

**事实/推断**：事实（代码路径可追踪）

**红测**：两个超管同时审核同一退款单（被 RefundRequest 锁阻挡，第二个阻塞到第一个 commit 后读到 approved → 被 status guard 拒绝）→ 实际已安全

```python
        raise ValidationError(f"状态 {e.status} 不可取消")
```

**红测**：创建一个付费活动，报名并确认收款，然后家长端调用 `/cancel` → 观察订单是否仍为 PAID 且无退款记录

```python
if req.withdrawal_id:
    w = self.db.query(WithdrawalRequest).filter(...).first()
    if w and w.status == WithdrawalRequest.STATUS_APPLYING:  # ← 只处理 APPLYING
        w.status = WithdrawalRequest.STATUS_REJECTED
        child.operation_locked = 0
```
- 退会审核通过后 withdrawal 已是 `REFUNDING`（非 `APPLYING`），拒绝分支的 `w.status == APPLYING` 守卫**永远不命中** → 退款单被拒但退会状态不变
- `wm10_service.py:214-229`（cancel 路径）：撤销退款单同样不碰 withdrawal
- `_advance_withdrawal()`（`:536-577`）仅在退款 **execute 成功** 时触发，reject/cancel 不触发
- 全部结算退款单被拒 → `open_cnt=0` 但 `_advance_withdrawal` 从未被调用 → withdrawal 永久停留 `REFUNDING`，child 永久 `operation_locked=1`

**影响**：家长发起退会 → 超管批准 → 结算退款单被拒（如金额争议）→ 退会流程死锁。孩子无法借书、预约、转让，只能数据库手改。

**修复提案**：退款 reject/cancel 路径增加 withdrawal 状态推进逻辑：
```python
# wm10_service.py review reject 分支
if req.withdrawal_id:
    w = self.db.query(WithdrawalRequest).filter(...).with_for_update().first()
    if w and w.status in (WithdrawalRequest.STATUS_REFUNDING, WithdrawalRequest.STATUS_PENDING_SETTLE):
        # 检查是否所有关联退款单都已终态
        self._advance_withdrawal_or_reject(w)
```

**红测**：创建退会 → 审核通过（生成结算退款单）→ 拒绝所有退款单 → 查询 withdrawal 状态（预期：卡 refunding）

**门禁级别**：集成测试

**依赖**：与 B-2 关联（解锁时序）

**事实/推断**：事实（代码路径完整可追踪）

## B-16 【高|事实】identity map 陷阱——with_for_update() 缺 populate_existing() 致守卫读旧值

**可见性**：高（P1-F1~F9 行锁修复被静默架空）

**证据**：
- 全仓 grep `populate_existing` 仅 2 处命中：`reading/service.py:403` 和 `:608`
- 其余 12+ 处 `with_for_update()` 均未使用 `populate_existing()`
- 典型路径：auth 中间件 preload `Child`（plain SELECT → 进 identity map）→ service 层 `with_for_update()` 查同一行 → SQLAlchemy 返回 identity map 中的**旧实例**（不刷新字段）→ 后续守卫（如 `member_status`、`operation_locked`）读到过期值
- `reading/service.py:403` 注释明确承认此陷阱：*"强制用行数据刷新 identity map——due 扫描已按旧快照加载过同一行，不刷新则状态守卫读到旧值失效"*
- 受影响路径：`billing/service.py:58,182`、`activity/service.py:405`、`wm10_service.py:116,301,371`、`order_service.py:213`、`circulation/service.py:102,134,314,319`、`growth/service.py:539`

**影响**：MySQL REPEATABLE READ 下，auth preload 建立 read view → `with_for_update()` 虽获行锁但 identity map 返回旧快照 → 状态守卫失效。这是 P1-F1~F9 行锁批修的系统性漏洞。

**修复提案**：所有 `with_for_update()` 统一追加 `.populate_existing()`；或在 `create_engine()` 设置 `isolation_level="READ COMMITTED"`（一行修复，见域 E E-00）。

**门禁级别**：并发集成测试

**依赖**：与域 E E-00（系统性根因）联合修复

**事实/推断**：事实（代码可验证 + reading/service.py 注释自认）
