- **#1 防重复缺失**：管理端造活动单只查了活动存在/状态/开始时间/名额——**没查"该孩子

  链没抄）→ 已报名已交费的孩子还能再造单再收款=双倍收费风险。

  list_inbox 全量场景（含活动报名）——但**侧边栏徽标 admin_total 明确排除活动报名**
  （T6 注释"单独口径不进 admin_total"）→ 您看到"数字没算上"实为**两个计数口径分叉**
  （tab 数字含、徽标不含——又一个计数不同源）。**裁定：活动报名待确认也是待办，

## 施工顺序：R7 → R8 → R9 → R10

### R7【补刀·上批遗留】管理端造单链发报名待确认通知

**根因**：T6 通知只在家长端 `enroll()` 内发；T2 管理端造单直接 `db.add(ActivityEnrollment)` 绕过发送点（专家活体实锤：造单+确认全链通，通知 0 条）。

**修法**：enroll() 内 T6 发送段抽 `ActivityService._notify_enroll_manual(child, a, e, fee)` 私有方法（dedup_key=enrollment_id 幂等）；enroll() 与 order_service T2 造单段双链调用。**免费活动管理端造单 422**（"免费活动无需创建订单，请走家长端报名"——防呆硬拦）。confirm 链 mark_handled 回写核对（家长端挂了，管理端造单链确认收款时同样要消待办）。

**红测试**：管理端造付费单→通知 1 条+计数 1（当前 0=RED）；确认→mark_handled+归零；免费单 422；家长端报名回归不破坏。

### R8【#1·资金风险】管理端造活动单防重复报名

**修法**：T2 造单段（名额校验旁）补 ACTIVE_STATUSES dup 检查（抄家长端 enroll 同款）：

```python
dup = (
    self.db.query(func.count(ActivityEnrollment.id))
    .filter(
        ActivityEnrollment.activity_id == req.activity_id,
        ActivityEnrollment.child_id == child.id,
        ActivityEnrollment.status.in_(ActivityEnrollment.ACTIVE_STATUSES),
        ActivityEnrollment.is_deleted == 0,
    )
    .scalar()
)
if dup:
    raise ValidationError("该孩子已有此活动的有效报名（待收款/已报名/退款待审），不可重复创建费用订单")
```
注意：refunded/cancelled 终态不拦（S4 口径：退款后可重报=可重造单）。

**红测试**：已报名孩再造单 → 422（当前 200=RED）；refunded 孩重造单 → 200（S4 回归）。

### R9【#2·老毛病第三犯】活动类型下拉补「全部」

**修法**：TYPE_OPTIONS 筛选用途处头插 `{ value: "", label: "全部" }`（A4/B7 同款空串口径，替 allowClear）；表单创建用途处不变（必选真实类型）——**两个用途分离**：筛选 options 与表单 options 拆成两个常量（`TYPE_FILTER_OPTIONS` 含全部 / `TYPE_OPTIONS` 原样）。

**sweep（完整性）**：rg 全 admin-web Select 筛选场景——凡"筛选下拉"逐一核对有「全部」（A4 先例清单外的新漏点列出来）；本次之后该模式进 verify_architecture 检查项（**机械判定**：筛选 Select 必须含空串选项——如实现复杂度高则记入 docs/09 待办，简报声明）。

**验证**：tsc + 目视。

### R10【#3·计数口径统一】活动报名待确认进 admin_total + 去处理按钮

**修法**：
1. **admin_total 口径统一**：todo-counts 的 `admin_total` 改为**全部待处理场景之和**（审核五类 + 活动报名待确认）——删"单独口径不进 admin_total"注释，新注释锚定"运营视角一个数=全部要干的活（2026-09-07 用户裁定）"；`activity_enroll_pending` 字段保留（活动中心侧边栏徽标仍用细分值）。**同源 sweep**：list_inbox 的 pending_count 本来就全场景（tab 数字含活动报名 ✓）→ 修完后 admin_total 与 pending_count 严格一致（注释里"严格一致"的声明从"口径声明"变"事实"）
2. **去处理路由**：ADMIN_REF_ROUTE 补 `activity_enrollment: { path: "/activities", tab: "" , highlight: ref_id}`——跳活动中心并高亮该报名行（活动中心有报名名单区；若名单区无行级 id 定位，跳转后滚动到名单区即可，highlight 传 enrollment_id 供未来用——**最小实现**）；refText 标签补"活动报名"
3. **去处理动作语义**：该场景的"处理"=确认收款（活动中心/会员管理订单 tab）——路由跳 `/activities`（活动中心有报名名单）**或** 会员管理订单 tab（待确认单所在）——**dev 实读两页数据后择一**（哪页能直接完成收款确认就跳哪），简报声明选择

**红测试**：造报名待确认单 → todo-counts admin_total 含它（当前不含=RED）；通知行"去处理"按钮渲染（refText=活动报名）；跳转目标页正确。
