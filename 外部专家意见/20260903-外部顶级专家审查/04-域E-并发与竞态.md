## E-00 【阻断·系统性根因|事实】REPEATABLE READ 隔离级别下"锁主体行 + 锁内普通 COUNT 复查"模式整体失效

**可见性**：阻断级（P1-F1~F9 行锁批修被系统性架空）

**证据**：
- `backend/database.py:16-21`：
```python
engine = create_engine(
    settings.database_url,
    pool_pre_ping=True,
    pool_recycle=3600,
    pool_size=10,
    max_overflow=20,
)
# ← 未设置 isolation_level，MySQL 默认 REPEATABLE READ
```
- MySQL REPEATABLE READ 语义：事务内第一条 SELECT 建立 read view（一致性快照），后续**所有普通 SELECT**（包括聚合 COUNT/SUM）都读该快照，即使其他事务已 commit 新数据
- `with_for_update()` 获得行锁并读取**最新已提交数据**，但：
  - (a) SQLAlchemy identity map 可能返回旧实例（缺 `populate_existing()`，见 B-16）
  - (b) 锁后的**普通 SELECT COUNT 守卫**仍读旧快照——这是致命缺口

**典型受害路径**：
1. 借书额度守卫（`circulation/service.py:203-224`）：锁 Child → COUNT active borrows → 但 COUNT 读旧快照 → 并发借书穿透额度
2. 预约同书唯一守卫（`reading/service.py:283-332`）：锁 copy → COUNT same-book reservations → 旧快照 → 同书双预约
3. 退款重复申请守卫（`wm10_service.py:138-149`）：锁 Order → COUNT pending refunds → 旧快照 → 同订单双退款单
4. 活动报名名额守卫（`activity/service.py:405+`）：锁 Activity → COUNT enrollments → 旧快照 → 超卖

**一行修复**：
```python
engine = create_engine(
    settings.database_url,
    isolation_level="READ COMMITTED",  # ← 加这一行
    pool_pre_ping=True,
    ...
)
```
READ COMMITTED 下每条 SELECT 读最新已提交数据，锁后 COUNT 守卫立即生效。

**影响范围**：全项目所有"锁 + COUNT 守卫"路径（估计 15-20 处），包括 P1-F1~F9 已修复的行锁——行锁本身有效，但锁后的聚合守卫在 RR 下读旧值，等于锁了门但窗户开着。

**门禁级别**：并发集成测试（两线程同时借书/预约/报名，验证守卫是否拦截）

**依赖**：与 B-16（identity map / populate_existing）联合修复效果最佳

**事实/推断**：事实（MySQL RR 语义为文档确认；代码路径可追踪；`reading/service.py:403` 注释自认此问题）

## E-1 【中|事实】CirculationService.renew() 缺少行锁——并发续借可双延期

**可见性**：中（到期日可被延长两次，违反"每本书限 1 次续借"规则）

**证据**：
- `backend/domain/circulation/service.py:357-360`
```python
record = (
    self.db.query(BorrowRecord)
    .filter(BorrowRecord.id == record_id, BorrowRecord.is_deleted == 0)
    .first()  # ← 缺少 with_for_update()
)
```
- 续借逻辑（lines 375-379）：
```python
if record.renew_used >= 1:
    raise ValidationError("续借机会已用完（每本书限 1 次）")
renew_days = int(ConfigService(self.db).get_value("renew_days"))
record.due_at = record.due_at + timedelta(days=renew_days)
record.renew_used += 1
```
- 两个并发续借请求（家长在手机和平板同时点"续借"）→ 两个事务都读到 `renew_used=0` → 都通过校验 → 都执行 `renew_used += 1` → 第二个 commit 时 `renew_used=2`（违反限 1 次规则），且到期日被延长两次

**根因**：续借是低频操作，开发者未考虑并发场景

**修复提案**：
```python
record = (
    self.db.query(BorrowRecord)
    .filter(BorrowRecord.id == record_id, BorrowRecord.is_deleted == 0)
    .with_for_update()
    .first()
)
```

**红测**：两个浏览器 tab 同时打开同一借阅的详情页，同时点"续借"→ 观察 renew_used 是否为 2

**门禁级别**：Service 单测（mock 两个并发 renew 调用）

**依赖**：无

**事实/推断**：事实

## E-4 【低|事实】TransferService.apply() 对 Child 行无锁——并发申请可双冻结

**可见性**：低（家长端低频操作，且 check_conditions 会拦截重复申请）

**证据**：
- `backend/domain/identity/transfer_service.py:146-147`
```python
source = self._child(source_child_id)  # ← 无锁
target = self._child(target_child_id)  # ← 无锁
```
- `_child()` 方法（line ~50）：普通 query，无 `with_for_update()`
- apply 逻辑（lines 162-163）：
```python
source.operation_locked = 1
target.operation_locked = 1
```
- 两个并发申请（家长快速点两次"发起转让"）→ 两个事务都读到 `operation_locked=0` → 都通过 check_conditions → 都设置 `operation_locked=1` → 创建两个 TransferRequest

**根因**：前端应该有防重复提交（按钮 loading），但后端未做防御

**修复提案**：
```python
source = self.db.query(Child).filter(Child.id == source_child_id).with_for_update().first()
target = self.db.query(Child).filter(Child.id == target_child_id).with_for_update().first()
```
并在 check_conditions 中检查是否已有 pending 的 TransferRequest（已有此检查，但无锁时并发可穿透）

**红测**：快速双击"发起转让"按钮 → 观察是否创建两个 TransferRequest

**门禁级别**：Service 单测

**依赖**：无

## E-6 【中|事实】cancel_timeout_orders() 无状态守卫——可覆盖刚确认收款的订单为 cancelled

**可见性**：中（窗口小但后果严重：钱收了、单没了、联动取消报名）

**证据**：
- `backend/domain/identity/order_service.py:395-425`
```python
def cancel_timeout_orders(self) -> int:
    orders = (
        self.db.query(Order)
        .filter(
            Order.is_deleted == 0,
            Order.status.in_([Order.STATUS_PENDING_PAYMENT, Order.STATUS_PENDING_MANUAL]),
            Order.create_time < cutoff,
        )
        .all()  # ← 快照读，无 with_for_update
    )
    for order in orders:
        order.status = Order.STATUS_CANCELLED  # ← 无条件 UPDATE，无状态守卫
        self.db.flush()
```
- 对比 `overdue_mark` 的条件 UPDATE 写法（L462-471，有 rowcount 守卫）
- 若管理员 `confirm_payment` 在任务读取后、提交前完成收款 → 任务把 `PAID` 覆盖回 `CANCELLED`，且联动把报名取消
- 窗口小（仅 cutoff 边界订单），但与活动域"报名随订单取消"直接联动，属资金状态机风险

**根因**：定时任务假设"查询和提交之间不会有其他操作"

**修复提案**：
```python
from sqlalchemy import update
result = self.db.execute(
    update(Order)
    .where(Order.id == order.id, Order.status.in_([Order.STATUS_PENDING_PAYMENT, Order.STATUS_PENDING_MANUAL]))
    .values(status=Order.STATUS_CANCELLED)
)
if result.rowcount == 0:
    continue  # 状态已被其他事务改变，跳过
```

**红测**：创建订单 → 等到接近超时 → 管理员确认收款的同时定时任务执行 → 观察订单终态

**门禁级别**：Service 单测

**依赖**：无

**事实/推断**：事实（代码无守卫可验证）

```python
child = self.db.query(Child).filter(Child.id == child_id).with_for_update().first()
```

**红测**：同一孩子并发两个预约请求（不同副本）→ 观察是否突破额度或创建同书双预约

## E-9 【低|事实】额度公式对逾期书双重扣减——与 CLAUDE.md 公式字面不符

**可见性**：低（偏严格方向，不放水，但属于未声明的口径偏移）

**证据**：
- `backend/domain/circulation/service.py:205-224`
```python
active_count = ... BorrowRecord.status.in_([STATUS_ACTIVE, STATUS_OVERDUE]) ...
```

**红测**：孩子有 5 本逾期 → 额度应为 30-5=25（当前实际：30-5-5=20）

## E-10 【中|事实】expire_due_members 定时任务无行锁——可覆盖并发续费的 member_status

**可见性**：中（窗口小但影响严重：刚续费的孩子被标记为 expired）

**证据**：
- `backend/domain/identity/service.py:376-394`：
```python
due = (
    self.db.query(Child)
    .filter(
        Child.is_deleted == 0,
        Child.member_status.in_([Child.MEMBER_FORMAL, Child.MEMBER_OBSERVATION]),
        Child.member_expire.isnot(None),
        Child.member_expire < today,
```

**系统性根因**：E-00 是本域最重要的发现——MySQL REPEATABLE READ 隔离级别导致全项目所有"锁主体行 + 锁内普通 COUNT 复查"模式整体失效。P1-F1~F9 的行锁修复本身有效（锁确实被获取），但锁后的聚合守卫（COUNT/SUM/EXISTS）在 RR 下读取事务开始时的旧快照，等于**锁了门但窗户开着**。一行修复（`isolation_level="READ COMMITTED"`）可系统性解决此问题，但需要回归测试确认 RC 下无新的幻读风险。

**模式观察**：项目已修复的 P1-F1~F9 覆盖了高频/高风险操作的行锁，但存在两层遗漏：(1) 低频操作（续借、签到、审核、申请、活动取消）未加锁；(2) **定时任务**（cancel_timeout_orders、expire_due_members、overdue_list）全部使用快照读 + 无条件写，与用户操作存在竞态窗口。建议建立"所有状态变更操作默认加锁 + 条件 UPDATE"的编码规范。
