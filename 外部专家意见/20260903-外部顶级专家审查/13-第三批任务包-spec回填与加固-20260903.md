## T30【P1·在任专家亲验存活】H-4：通用退款入口补活动矩阵

**位置**：backend/domain/identity/wm10\_service.py apply()（L48 区域）——`_paid_order` L125 只拦押金类，TYPE\_ACTIVITY/TYPE\_FIRST\_ACTIVITY 订单直接放行建单

**现象**（亲验实锤）：PRD §9.3 活动退款矩阵（已签到不退/已开始线下/前 2h 关线上）只在 activity.apply\_refund 入口执行；家长从「我的订单」（X7）对活动订单发起退款 → 走通用入口 → **矩阵全绕过**，已签到活动也能建退款单进审核。T16 堵了活动侧入口，反向通道存活。

**修法**（函数级 import activity models 先例已在同文件 `_refund_activity_enrollment`，架构关可过）：

```python
# apply() 内 _paid_order 之后：
if order.order_type in (Order.TYPE_ACTIVITY, Order.TYPE_FIRST_ACTIVITY):
    from backend.domain.activity.models import ActivityEnrollment
    e = self.db.query(ActivityEnrollment).filter(
        ActivityEnrollment.order_id == order.id, ActivityEnrollment.is_deleted == 0
    ).first()
    if e and e.status == ActivityEnrollment.STATUS_CHECKED_IN:
        raise ValidationError("已签到，不能退款（人都来了，成本已发生）")
    # 已开始/前 2h 检查同款（活动 start_at 查询后比对，文案与 activity.apply_refund 逐字一致——单一事实源）
```

注意：cancel\_activity 批量路径传 skip\_lock\_check=True 也走 apply——批量取消是馆员操作，**矩阵检查应对 skip\_lock\_check=True 豁免**（活动已 cancelled 时 start\_at 检查必然失败，逻辑上批量路径必须绕过），豁免分支注释写明理由。

**红测试**：已签到活动订单走通用入口 → 422（当前 200 建单 = RED）；未开始活动订单 → 200 正常建单；批量取消路径回归不破。

## T31【挂账】cancel\_activity 半程加固（事务原子性）

**位置**：backend/domain/activity/service.py cancel\_activity()（T16 后批量循环内逐单 `refund_svc.apply()`，apply 内部 commit）

**现象**（二批严审观察项）：循环第 K 单失败 → 前 K-1 单已提交，重跑被"活动状态不可取消"（a.status 已 CANCELLED）挡住 → 剩余 ENROLLED 报名永久滞留。

**修法**：

1. apply() 增加 `skip_commit: bool = False` 参数（True 时只 add+flush 不 commit，调用方统一收口）
2. cancel\_activity 循环外单次 commit
3. 幂等兜底：入口守卫放宽——`a.status == CANCELLED` 且仍有 ENROLLED 报名时**继续处理**（断点续跑）而非 raise；两者都满足才走正常路径
4. T16 批量测试回归 + 新红测试：模拟第 2 单失败（monkeypatch）→ 事务回滚无半程 → 修复失败原因 → 重跑 → 全部进退款待审

**验证等级**：C 级。
