### F-H1 【高|事实】GrowthManage 深链抽屉死循环——关→立即重开

**证据**：`admin-web/src/pages/GrowthManage.tsx:58-69`（effect 读 URL `?child_id=`）；`:193`（关抽屉 `setGrowChild(null)`）

**问题**：useEffect 依据 URL `?child_id=` 自动开抽屉，条件 `cid && children.length && !growChild`。用户关闭抽屉 → `growChild` 变 null → 依赖 `[children, growChild]` 的 effect 重跑 → 条件再次满足 → 抽屉立即重开。**URL 参数从未清除**，带 `child_id` 深链进入后抽屉在视觉上无法关闭。

**影响**：通知中心"查看关联报告"跳转 → GrowthManage 后，管理员无法关闭抽屉查看列表，只能后退离开页面。

**修复提案**：消费后 `window.history.replaceState(null, "", location.pathname)` 清除 URL 参数；或用 `useRef` 做一次性消费标志。

**事实/推断**：事实（代码路径完整可复现）

### F-H2 【高|事实】401 处理仅清 token，违反宪法 §五小程序-2"清除全部身份缓存"

**证据**：`miniapp/utils/request.js:59-74`（401 分支仅 `wx.removeStorageSync('token')`）；`miniapp/utils/session.js:18-24`（`logout()` 清 4 个 key：token/parent/children/currentChildId，但 401 路径从未调用）

**问题**：401 时只移除 `token`，`parent`、`children`、`currentChildId` 留在 Storage 中。globalData 虽被清空（`:68-70`），但冷启动时 `app.js:32` 从 Storage 读 `userInfo`（另一 bug，见 F-L16），`session.js` 的 `getParent()/getChildren()` 仍能从 Storage 读到上一个账户的身份数据。

**修复提案**：401 路径调用 `session.logout()` 替代手工清 token，确保 4 个 Storage key + globalData 全部清除。

**事实/推断**：事实

### F-H3 【高|事实】children / member_status 登录时快照后无刷新路径——家长侧永久陈旧

### F-H4 【高|事实】RefundCenter 资金域列表 false-zero——提现/转账加载失败静默置空（U10 禁假 0 违规）

### F-H5 【高|事实】Reader 心跳上报频率偏差 ~4×——onTimeUpdate 以 tick 计数代替时钟

**证据**：`miniapp/pages/reading-pkg/reader/reader.js:7`（`const HEARTBEAT_SEC = 10`）；`:152-168`（`onTimeUpdate` 回调内 `this._pendingSec += 1`，达到 `HEARTBEAT_SEC` 时触发 `_reportNow()`）

**问题**：`_pendingSec` 在每次 `onTimeUpdate` 事件触发时 +1，假设 1 tick = 1 秒。但微信 `innerAudioContext.onTimeUpdate` 实际以 ~250ms 间隔触发（平台相关）。因此：

- 预期：每 10 秒上报一次进度（R-151 反作弊心跳）
- 实际：每 ~2.5 秒上报一次（10 ticks × 250ms），**请求量为预期的 4 倍**
- 每次 onTimeUpdate 还触发 3-6 字段的 setData（`:157-163`），播放期间持续 ~4 次 setData/秒

**影响**：(1) `/progress` 端点承受 4× 预期负载；(2) setData 频率过高可能导致低端机卡顿；(3) 反作弊心跳间隔与设计文档不符。

**修复提案**：改用 `Date.now()` 差值判断：`if (Date.now() - this._lastReport >= HEARTBEAT_SEC * 1000)`；setData 合并为单次调用。

**事实/推断**：事实（代码确认 tick 计数；250ms 间隔为微信官方文档值，实际因平台而异）

## 五、系统性主题总结

### 主题 A：U10"禁假 0"系统性违规

两端（admin + miniapp）在列表 fetch 失败时普遍静默置空/undefined，渲染为合法空态或计数 0。涉及：F-H4（RefundCenter 资金域）、F-M8（CirculationDesk 逾期）、F-M9（ActivityManage 退款）、F-M12（books/vocabulary/activity-list）、F-M13（error-view 零使用）。**根因**：项目专门开发了 error-view / loading-skeleton 组件但从未接入任何页面。

### 主题 B：tab 计数同族第 4/5 处漏网

WM13-F4、WM3-A1、WM3-插修2-F1 之后，F-M3（children tab）和 F-M5（parent 未读）是同族第 4/5 处。建议将"计数与列表解耦、挂载即拉"写入前端规约并加 lint/CR 检查项。

### 主题 C：宪法规则执行不均

- 菜单级 RBAC 有，路由级守卫无（F-M18）
- 生成类型工具链可用，但 4/9 API 模块手写绕过（F-M17）
- 配置化定价有 SystemConfig，但 4 处硬编码文案（F-M16）
- 401 应清全部缓存，但只清 token（F-H2）

### 主题 D：miniapp 死代码层

~6 个模块（auth.js/consent.js/security.js/platform.js/subscribe.js/pay-button）引用后端从未实现的端点。其中 consent.js 实现了 PRD F3 三段式监护人同意但无页面引用——宪法相关功能仅以死代码存在（F-L7）。
