## T1【P0·阻断】E-00：全局隔离级别 RR → READ COMMITTED

**位置**：backend/database.py:16-23（create_engine 无 isolation_level）

**现象**：MySQL 默认 REPEATABLE READ 下，auth preload（`_parent_from_token`/`_child_of_parent` 普通查询）建立 read view → 后续 `with_for_update` 虽获行锁，但锁内 COUNT/SUM 守卫读旧快照 → 全项目 15-20 处"锁+COUNT 守卫"并发失效（借书额度/预约同书唯一/退款查重/活动名额）。

**修法**：
```python
engine = create_engine(
    settings.database_url,
    isolation_level="READ COMMITTED",  # E-00：RR 下锁后 COUNT 守卫读旧快照（外部审计 20260903）
    pool_pre_ping=True,
    ...
)
```

**前置检查（施工前必做，结果写进交付简报）**：
- A. binlog_format 确认：`docker exec dmkwords-mysql mysql -uroot -p$DB_PASSWORD -e "SELECT @@binlog_format;"` → 必须 ROW（MySQL 8 默认；CI 容器同查）
- B. COUNT 防重场景的锁兜底盘点：逐个确认"COUNT 查重+INSERT"路径是否有主体行锁串行化——借书额度（锁 Child ✓ circulation:102）/ 退款查重（锁 Order ✓ wm10_service:116）/ 活动名额（锁 Activity ✓ activity:405）/ **预约 create（无锁 ✗ → T3 补）**。Reservation 表无唯一索引兜底（models rg 实测），RC 不能替代行锁。

**红测试**（session_pair fixture 已有基建）：
- session1 锁 Child 行 + session2 提交新 BorrowRecord → session1 锁内 COUNT active 读到 2（当前 RR 下读 1 = RED）
- 断言 `engine.dialect.params` 或直接查 `SELECT @@transaction_isolation` 会话级为 READ-COMMITTED

## T2【P0·阻断】B-16：20 处 with_for_update 补 populate_existing()

**位置**（全量坐标，rg 实测 22 处代码级，reading 2 处已有，余 20 处待补）：

**现象**：SQLAlchemy identity map 陷阱——同 session 前序普通查询（auth preload/业务前段）已加载实体 → `with_for_update` 命中 identity map 返回**旧实例**（锁定读的新行数据被丢弃）→ 状态守卫读旧值。**注意：T1 的 RC 修不了这个**（ORM 层缺陷，与隔离级别无关）——两个独立缺陷，都必须修。

**修法**（统一模式，参照项目先例 reading/service.py:403/608 的注释风格）：
```python
.with_for_update()
.populate_existing()  # B-16：identity map 刷新——前序普通读已载旧实例，不刷新则守卫读旧值
```

**红测试**：代表性 1-2 例——session1 普通读 Child（进 identity map）→ session2 改 member_status 并提交 → session1 `with_for_update().populate_existing()` 读到新值（不补时读旧值 = RED）。

**防复发物理化**：verify_architecture.py 新增规则——rg 扫描全部 `with_for_update` 必须同一查询链带 `populate_existing`（与 T6 合并施工，此规则随 T6 的 glob 扩展一起上）。

**验证等级**：C 级（并入 T1 同轮 gate）

## T5【P0·阻断】B-13：退款 reject/cancel 增加退会状态推进

**位置**：backend/domain/identity/wm10_service.py
- review 拒绝分支 L331-341（现只认 `w.status == APPLYING`）
- cancel 路径 L235-243（同款断链）

**现象**：退会批准后 w=REFUNDING → 结算退款单全部被 reject/cancel → `_advance_withdrawal` 仅由 execute 成功触发 → w 永卡 REFUNDING，child 永久 operation_locked=1，无出口（execute 失败有出口回 pending_settle，但 reject/cancel 没有）。

**修法**（双态兼容，reject 与 cancel 两分支都加）：
```python
if req.withdrawal_id:
    w = self.db.query(WithdrawalRequest).filter(...).with_for_update().populate_existing().first()
    if w and w.status == WithdrawalRequest.STATUS_APPLYING:
        # 现状保留：联动退会未被批准，退款被拒/撤 → 退会一并拒绝/撤销 + 解锁
        w.status = WithdrawalRequest.STATUS_REJECTED  # cancel 分支为 CANCELLED
        child.operation_locked = 0
    elif w and w.status in (WithdrawalRequest.STATUS_REFUNDING, WithdrawalRequest.STATUS_PENDING_SETTLE):
        # 新增：结算退款单终态推进（复用 _advance_withdrawal 的 open_cnt 语义）
        open_cnt = <同 _advance_withdrawal L554-569 的 COUNT>
        if open_cnt == 0:
            refunded_cnt = <status == refunded 计数>
            if refunded_cnt > 0:
                self._advance_withdrawal(req.id)   # 有成功单 → completed（幂等）
            else:
                w.status = WithdrawalRequest.STATUS_REJECTED  # 全拒 → 退会失败
                child.operation_locked = 0          # 恢复可用，家长可重新发起
```
建议抽私有方法 `_settle_withdrawal_on_terminal(req)` 供两分支共用，避免复制。

**业务语义**（已与用户确认口径）：全拒 = 退会整体失败（钱没退，会员资格不应被剥夺）；部分成功 = execute 成功路径已有 _complete_refund_withdrawal 处理，保持不变。

**红测试**（三条，全链路测试）：
1. 退会批准（REFUNDING + N 笔结算单）→ 全部 reject → w=REJECTED + child.operation_locked=0 + member_status 未变（仍 formal）
2. 同上但 1 笔 execute 成功 + 其余 reject → w=COMPLETED（_advance_withdrawal 语义）
3. 家长 cancel 路径同款断言（联动 APPLYING 态保持现状回归）

**验证等级**：C 级（并入同轮）

    统一走 R-308 审核链——创建 pending 申请，后续 review→execute 与家长申请同链。"""
    order = self.db.query(Order).filter(...).with_for_update().populate_existing().first()
