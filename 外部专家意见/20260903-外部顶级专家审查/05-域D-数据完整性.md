## D-1 【高|事实】alembic/env.py 漏导 3 个模型——未来 autogenerate 会 DROP TABLE

**可见性**：高（静默数据丢失地雷）

**证据**：
- `alembic/env.py:40`
```python
from backend.domain.reading.models import CheckIn, ReadingProgress, Reservation
# ← 遗漏 DictionaryWord, Vocabulary, Favorite（同文件 L71/82/94）
```
- 这 3 个表仅通过手写迁移 `b8e2f5a7c1d9` 存在
- 未来执行 `alembic revision --autogenerate` 时，alembic 看到 DB 有表但 metadata 无定义 → 生成 `drop_table("dictionary_words"/"vocabularies"/"favorites")`
- 同类事故已记录：`362eb9327df9`（"autogen empty-shell"事件）

**根因**：reading/models.py 后期新增 3 个模型，env.py 导入未同步更新

**修复提案**：
```python
from backend.domain.reading.models import (
    CheckIn, ReadingProgress, Reservation,
    DictionaryWord, Vocabulary, Favorite,
)
```

**红测**：`alembic revision --autogenerate` → 检查生成的迁移是否含 DROP TABLE

**门禁级别**：CI 脚本（autogenerate --check 模式）

**依赖**：无

**事实/推断**：事实（import 缺失可验证）；推断在于"未来 autogenerate 会触发"

## D-2 【高|事实】reading_progress 无 unique (child_id, book_id)——并发可创建重复行

**可见性**：高（进度分裂→完课检测失效或阅读时长重复计算）

**证据**：
- `backend/domain/reading/models.py:16-33`
- `__table_args__` 注释说"学生×书目唯一（进程行）"但**未声明 UniqueConstraint**
- 迁移 `92e6434da8d1` 确认无 unique
- 创建逻辑 `reading/service.py:117-129`：`.first()` 然后 `add`——check-then-insert 无 DB 层兜底
- 两个并发进度报告 → 两行 → 后续读 `.first()` → intervals 分裂 → 95% 完成检测可被绕过

**根因**：依赖应用层 check-then-insert，无 DB 唯一约束兜底

**修复提案**：
```python
# models.py
__table_args__ = (
    UniqueConstraint("child_id", "book_id"),
)
```
+ 迁移

**红测**：同一孩子同一书并发两个进度报告 → 观察是否创建两行

**门禁级别**：Model 单测 + 迁移验证

**依赖**：无

**事实/推断**：事实（无 UniqueConstraint 可验证）

## D-4 【高|事实】软删后重建触发 DB unique 约束——IntegrityError 500（3 处）

**可见性**：高（用户操作直接 500）

**证据**：

**4a. FavoriteService.add**：
- `reading/vocabulary_service.py:139-156`
- dup-check 过滤 `is_deleted == 0`，然后 insert 新行
- 但 `uq_fav_child_book`（`reading/models.py:95`）是 `(child_id, book_id)` unique **不含 is_deleted**
- 删除后再收藏同一书 → unique violation
- 对比：`VocabularyService.lookup`（L43-57）已修复同类 bug（注释"C50：删词后再查同词曾 500"）——Favorite 未同步修复

**4b. create_book / update_book ISBN 检查**：
- `catalog/service.py:167-173` / `203-217`
- `get_by_isbn` → `BaseRepository.get_by_field` 过滤 `is_deleted == 0`
- 但 `ix_books_isbn` 是 unique **不含 is_deleted**（迁移 `3e0d428f18e0`）
- 软删的书永久阻止重新添加同 ISBN → 500

**4c. ParentService.create 手机号检查**：
- `identity/service.py:22-31`
- phone dup-check 过滤 `is_deleted == 0`
- 但 `ix_parents_phone` 是 unique **不含 is_deleted**
- 重新注册已删除家长的手机号 → 500（wechat_openid 同理）

**根因**：C50 模式（vocabulary 已修）未在 Favorite/Book/Parent 同步应用

**修复提案**：
- 方案 A：3 处都采用 vocabulary 的"复活软删行"模式
- 方案 B：unique 索引加入 `is_deleted`（需迁移）

**红测**：收藏一本书 → 删除收藏 → 再收藏同一书 → 观察是否 500

**门禁级别**：Service 单测

**依赖**：无

**事实/推断**：事实（代码可验证）

## D-6 【中高|事实】ChildService.delete 只检查 orders，不检查 active borrows/reservations/transfers

**可见性**：中高（软删的孩子可能有进行中的借阅/预约/转让）

**证据**：
- `backend/domain/identity/service.py:278-291`
- 软删条件：`has_orders` 为 false
- 有 ACTIVE borrow_records / reservations / pending transfer_requests（operation_locked=1）的孩子可被删除
- 删除后：副本保持 borrowed/reserved 状态指向已删孩子，转让/退会流程通过无 is_deleted 过滤的查询操作已删孩子
- ParentService.delete 同理（`service.py:125-133`，cascade 到 children 但同样只查 orders）

**根因**：删除守卫只考虑了订单，未考虑流通域和转让域

**修复提案**：
```python
def delete(self, child_id):
    # 现有 orders 检查
    # 新增：
    active_borrows = db.query(func.count(BorrowRecord.id)).filter(
        BorrowRecord.child_id == child_id,
        BorrowRecord.status.in_([STATUS_ACTIVE, STATUS_OVERDUE])
    ).scalar()
    if active_borrows:
        raise ValidationError("有未归还借阅")
    # 同理 reservations, transfer_requests
```

**红测**：孩子有 active 借阅 → 尝试删除 → 观察是否成功

**门禁级别**：Service 单测

**依赖**：D-5（无 FK 兜底）

**事实/推断**：事实（代码可验证）

## D-8 【中|事实】通知处理器用 db.get() 绕过 soft-delete 过滤

**可见性**：中（已删孩子/书仍可触发通知）

**证据**：
- `tasks/notify_handlers.py:54, 144, 147, 167, 170, 189, 210, 213, 233, 236, 255`
- 使用 `db.get(Child/Book, id)`（PK 查找，无 is_deleted 过滤）
- 同文件其他处理器（L46, 75, 98, 121）正确过滤 `is_deleted == 0`
- 不一致：通知可为已删孩子/书生成

**根因**：db.get() 是 SQLAlchemy 快捷方式，开发者未注意它绕过软删过滤

**修复提案**：统一改为 `db.query(Child).filter(Child.id == id, Child.is_deleted == 0).first()`

**红测**：软删一个孩子 → 触发通知 → 观察通知内容是否引用已删孩子

**门禁级别**：Service 单测

**依赖**：无

**事实/推断**：事实

## 通过项（正面确认）

1. **Decimal 纪律**：所有金额列为 `Numeric(10,2)`，零 float 存储。`float()` 仅出现在 AR 层比较、显示、符号检查——不入库
2. **DateTime 一致**：全项目使用 naive local time（`datetime.now()`），零 `utcnow`/`timezone.utc`。无 naive/aware 混合
3. **alembic 迁移 100% 可逆**：16 个迁移全部有真实 downgrade()，单线 head 无分支
