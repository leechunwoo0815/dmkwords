## A-1 【阻断|事实】架构门禁只扫 router.py，5 个 miniapp_router.py 共 20+ 处违规全部漏检

**可见性**：阻断（门禁产出"Router 零违规"的虚假证据）

**证据**：
- `scripts/verify_architecture.py:49-57` 的 `check_router_violations` 只 glob `router.py`，不扫 `miniapp_router.py`
- 8 个管理端 `router.py` 确实干净，但 5 个小程序 `miniapp_router.py` 系统性违规：

| 文件:行号 | 违规类型 |
|-----------|---------|
| `identity/miniapp_router.py:172` | **Router 内 `db.commit()`**（全项目唯一一处） |
| `identity/miniapp_router.py:23,60,106,115,151,161` | 6 处 `db.query`（通知列表/标记已读整个功能在 Router） |
| `reading/miniapp_router.py:54-56` | `try/except pyjwt.PyJWTError` |
| `reading/miniapp_router.py:61,93,97,134-148,240,256,300,319,407` | 10+ 处 `db.query` |
| `billing/miniapp_router.py:21,43,58` | 3 处 `db.query` |
| `growth/miniapp_router.py:25,108` | 2 处 `db.query` |
| `activity/miniapp_router.py:20` | 1 处 `db.query` |

- `docs/12-证据附件:84` 宣称"Router 零违规" PASS——基于不完整的扫描

**根因**：门禁脚本编写时只考虑了管理端 router，遗漏了小程序 miniapp_router

**修复提案**：
1. `verify_architecture.py:49` 改为 `for router in dpath.glob("*router*.py")`（一行修复）
2. 将 `get_current_parent`/`_parent_from_token` 下沉到 `middleware/`
3. miniapp 查询逻辑逐步下沉到各域 service

**红测**：`python scripts/verify_architecture.py` → 观察是否报出 miniapp_router 违规

**门禁级别**：门禁脚本自身修复

**依赖**：无

**事实/推断**：事实

## A-2 【高|事实】跨域写副作用未走 EventBus——4 条实边违反宪法

**可见性**：高（域耦合度高，重构/测试/理解成本大）

**证据**：

| # | 位置 | 违规 |
|---|------|------|
| 1 | `activity/service.py:440-442` | 跨域调用 `OrderService(self.db)._create_activity_order(...)`——调用他域**私有方法** |
| 2 | `identity/order_service.py:271-273` | 直接调 `billing.DepositService.on_deposit_order_paid()` 完成跨域写，未走 EventBus |
| 3 | `reading/service.py:622-624` | 直接调 `CirculationService(self.db).borrow()`——跨域写 + 嵌套 commit |
| 4 | `billing/service.py:121,149` | billing 直接 `Order(...)` + `db.add` 创建 identity 域的 Order 聚合根 |

- CLAUDE.md:67 明文："跨域写一律走 EventBus"
- 实际执行：identity↔billing↔activity↔reading 形成环状耦合，靠函数内延迟 import 掩盖

**根因**：EventBus 设计用于异步通知，但开发者在需要同步写操作时选择了直调（因为 EventBus 的 `db=None` 分支用独立 session，不适合需要事务一致性的场景）

**修复提案**：
- 短期：在宪法中明确"同步跨域写允许直调，但必须通过 Service 公开方法（非私有）"
- 长期：EventBus 支持 `db=self.db` 的同事务模式（当前 `publish(db=self.db)` 已实现，但只有事件消费方走此路径）

**红测**：N/A（架构问题，非运行时 bug）

**门禁级别**：架构 lint（新增跨域写检测规则）

**依赖**：需要宪法修订

**事实/推断**：事实（代码可验证）

## A-3 【高|事实】reservation.created 事件订阅悬空——预约成功通知永不触发

**可见性**：高（WM11 功能死代码，家长收不到预约成功通知）

**证据**：
- `tasks/notify_handlers.py:284` 订阅了 `reservation.created`
- 全项目 grep `publish.*reservation.*created` → **零发布点**
- 对比：`reading/service.py` 的 `ReservationService.create()` 方法（line 268-360）在创建预约后没有 `event_bus.publish(ReservationCreatedEvent(...))`
- 更糟：`_on_reservation_created` 使用 `SCENE_RESERVATION_EXPIRING`（预约将到期）作为 scene 常量——即使补上发布点，通知分类也错误

**根因**：事件定义了、订阅写了，但发布点遗漏

**修复提案**：
1. `reading/service.py` 的 `ReservationService.create()` 末尾加 `event_bus.publish(ReservationCreatedEvent(...), db=self.db)`
2. 修正 scene 常量为 `SCENE_RESERVATION_CREATED`（需新增）
3. 宪法承诺的"事件发布/订阅双向对账入门禁"需兑现

**红测**：在小程序预约一本书 → 观察家长是否收到"预约成功"通知

**门禁级别**：集成测试 + 事件对账 lint

**依赖**：无

**事实/推断**：事实

## A-7 【中|推断】微信通知状态先于事实——daemon 线程 fire-and-forget 风险

**可见性**：中（通知状态可能与实际发送结果不一致）

**证据**：
- `integrations/wechat/subscribe.py:39-67` + `common/notifications.py:73-75,142`
- 微信推送为 daemon 线程，线程启动即返回 True → 立即回写 `WECHAT_SENT`
- 实际发送可能失败（网络/微信 API 错误），但状态已标记为已发送
- 主事务若回滚，消息可能已发出（不可撤回）
- 进程退出时 daemon 线程丢消息

**修复提案**：
- 短期：接受当前设计（小概率事件，可容忍）
- 长期：改用消息队列（Redis/RabbitMQ）异步发送，发送成功后才更新状态

**事实/推断**：推断（基于代码路径分析，未实际触发过）
