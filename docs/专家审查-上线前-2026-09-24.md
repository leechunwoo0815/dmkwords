## TL;DR（10 行内）

1. **代码质量出乎意料地好**：分层纪律、行锁、Decimal、软删过滤、越权守卫（实测全 422）、配置中心、媒体五道防线都在岗；静态扫出的"恒真断言/静默吞错/float 金额"几乎为零。
2. **但"上线"这个词现在不成立**：生产登录链路是断的（微信 code2session 和短信网关都是**零调用方**的孤岛模块，生产固定验证码被强制关闭→没人能登录）；微信支付回调端点整个不存在（WM12 未开工，阻塞于商户号资质）；`docker-compose.prod.yml` 文档里说"待创建"、仓库里确实没有。
3. **三个真 bug**：EventBus 独立事务模式 `get_session()()` 直接 TypeError（现在是死代码，谁按 docstring 用谁炸）；两个 async 上传端点里跑同步 Pillow 压图（会卡死整个事件循环）；专员账号能手动触发全部 16 个定时任务（含会删文件的媒体体检）。
4. **性能现状健康**：14 个热接口 P95 全部 ≤33ms、并发 50 无失败；但阅读圈信息流每请求 29 条 SQL（N+1）、管理端订单列表 24 条，上量后会先在这里疼。
5. **测试真相**：342 个 BDD 场景只有 30 个在跑（36/38 个 feature 文件挂着 @draft），pytest 533 例才是主安全网。
6. 最该先修的三件事见 §六 整改批次。

**同步/异步混用**：业务路由几乎全为 `def`（线程池执行，安全）；唯二 `async def` 反而藏着同步重活（P1-2）。

**APScheduler**：16 任务全注册（registry.py:153-205），`max_instances=1 + coalesce=True`，cron 任务 12h 宽限+启动补跑（:330,354）——单进程语义正确；多进程风险见 P0-4。

## 六、D 专项：上线部署（腾讯云/阿里云）

### D1 部署形态建议

**建议：单机 Docker Compose（与 ADR-001 一致）+ 托管 MySQL， uploads 音频走对象存储。** 理由：项目已按单机 Compose 设计（docs/20），无 Redis、进程内调度器（ADR-005/008），上 K8s 纯属给自己加复杂度；但**音频上百 GB（ADR-004 自述）不能进系统盘**，必须 COS/OSS+CDN（改造点清单见 §三 A3）。

| 日活档位 | CVM/ECS | 系统盘/数据盘 | MySQL | 备注 |
|---|---|---|---|---|
| 100（起步） | 2C4G（S5/SA3） | 60GB SSD | 托管 1C2G 或同机容器 | 同机容器需严守 P0-4 单实例纪律 |
| 500 | 4C8G | 60GB + 100GB 数据盘（不上传音频时） | 托管 2C4G | 推荐 MySQL 托管版（自动备份+只读从库可加） |
| 2000 | 4C8G + CDN | 100GB SSD | 托管 4C8G | 峰值借还并发在扫码台，DB 压力可控 |
| 1 万（拐点） | 8C16G×2（前后端分离） | 100GB | 托管 8C16G + 只读 | **这是单机形态的拐点**：需把调度器拆独立进程、文件全量 CDN、考虑 Redis 限流 |

磁盘容量估算：uploads 当前 44MB/演示库；生产音频按 2000 本 × 30–50MB = **60–100GB 起步（直接上 COS）**；图片增速按演示库实测（约 30–40MB/月全量含演示重启，生产估计 <5MB/月/千次操作）+ 凭证/报告长尾，本地盘 60GB 足够。

### D2 必做清单（逐条可执行）

1. **域名与备案**：ICP 备案（微信正式版硬前置，周期 1–3 周，立刻启动）；证书用云厂商免费 DV 或 certbot 自动续期（`certbot renew --dry-run` 验收），**弃用 certs/ 自签**（P0-3）。
2. **微信后台**：request/uploadFile/downloadFile 合法域名三件套填正式域名；AppSecret 存 .env（权限 600）。
3. **MySQL**（容器或托管）：utf8mb4、`time_zone='+8:00'`、`innodb_buffer_pool_size=1G`（2C4G 托管）/ 机器内存×0.5（自管）、`max_connections=300`、`slow_query_log=ON` + `long_query_time=1`、binlog ROW 保留 7 天（docs/20 已写）；**连接池算式**：Σ(各实例 pool_size+overflow) ≤ max_connections×0.7。
4. **进程守护**：systemd 或 compose `restart: unless-stopped`；ulimit -n 65535；日志切割（logrotate 或 compose max-size）。
5. **健康检查**：`/health` 探针 30s 间隔；磁盘 >85% 告警（docs/20 脚本已有，挂 cron）。
6. **调度器单实例**：副本=1，或非首副本 `SCHEDULER_ENABLED=false`（P0-4，写进 compose 与验收）。
7. **CORS 收紧**：`allow_origins` 换正式管理端域名或走同域反代（P2-1）。
8. **XFF 覆盖**：nginx `proxy_set_header X-Forwarded-For $remote_addr;`（P2-8）。
9. **uploads 持久化卷**：compose volume 挂载 + 每日增量同步 COS；音频直接写 COS（批次 5/6）。
10. **时区**：系统 `Asia/Shanghai` + MySQL `+8:00` + APScheduler `Asia/Shanghai`（registry.py:293 已硬编码 ✓）。

### D3 运维与灾备

- **MySQL**：托管版自动备份 + binlog PITR（docs/20 有恢复演练三步：全量→binlog 重放→五表对拍+health+登录冒烟）；**上线前必须实际演练一次**（恢复到临时实例跑行数对拍）。
- **uploads**：COS 版本控制或每日 rsync/rclone 快照；回收站机制保留（30 天可还原）。
- **监控告警**：磁盘 85%（已有脚本）、CPU/内存（云监控自带）、5xx 数（nginx 日志 grep cron）、任务失败（P3-5：TaskRunLog failed → 站内通知超管）、慢查询数。
- **回滚预案**：镜像 tag 化（`docker commit` 或 CI 构建），回滚=切回上一 tag；alembic `downgrade -1` 仅在迁移批带破坏性变更时演练（当前 16 个迁移无 downgrade 测试——上线后每次带迁移的发布前补）。
