## §本波（v185）已完成

### A. B1-7 回调商户归属校验（`5eded6e`）
**问题**：v3 回调签名只证明"报文是微信签的"，**不证明这笔钱是我们的**。解密后原先直接按单号找单，
完全不看明文里的 `mchid` / `appid`——别人的商户回调打到本地址只要单号金额对得上就被入账/落终态。
**修法**：`PaymentCallbackData` 增两字段（pay_v3 + mock 都解析，退款通知无 `appid` 需容忍缺省）；
`PaymentNotifyMixin._merchant_guard` 支付/退款两条路径**共用**，位置固定在"解密之后、任何业务判断之前"：
两侧都有值 → 必须逐字相等，不等 → **400 + 资金异常待办**（不入账、不落终态）；任一侧为空则跳过该项。
**判据**：`test_b1_7_merchant_guard_20261127.py` **13 passed**，去修复即红已验（修前错商户报文的响应就是
「成功」/「已退款」）。回归：支付/退款/对账 **99 passed + 2 skipped**。

### B. B5-2 测试库隔离 + 并行（`cb4efa9`）
**问题**：pytest/behave 每用例 `TRUNCATE` ADMIN_TABLES 里的全部业务表，却跑在与 dev 后端共用的 `dmkwords` 上 → 必须先停 dev
（否则假红）、误指库就清真实数据、无法并行。
**修法**：`tests/db_env.py`（库名白名单 + 建库 + `alembic upgrade head`，与 CI 同口径不用 `create_all`），
库名在**任何 backend import 之前**定好（`os.environ.setdefault`，ruff E402 对这类语句开白名单）；
`DMK_LOCK_SUFFIX` 给服务器级命名锁加 worker 后缀（**不**把库名拼进锁名，否则滚动发布期双跑定时任务）；
门禁 [2] 改 `-n 4 --dist load`。**实测**：带覆盖率全量 **26:35**（串行 88 分钟 → 3.2×）；`-n 8` 更慢更不稳。

### C. god-file 处置（`088310a`）
`registry.py` 因锁名工具涨到 814 行 → 抽 `backend/tasks/lock_names.py`（测试后缀 + `with_suffix`）与
`backend/tasks/failure_marker.py`（DB 挂时的文件兜底留痕）→ **787 行**。
**坑（已写进代码注释）**：一度把**契约名常量**也搬进新模块 → `monkeypatch.setattr(registry, "SCHEDULER_LOCK_NAME", …)`
失效、3 条机制用例齐红；定论：**常量留在可被打桩的模块**，只抽"后缀 + 拼名工具"。
