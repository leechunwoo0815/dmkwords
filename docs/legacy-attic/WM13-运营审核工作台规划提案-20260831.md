## 一、问题定义（为什么需要这个模块）

**运营审核员目前是"瞎子"**：家长在小程序申请退款/退会/权益转让后，系统不给运营任何通知——
审核员必须每天主动巡库（打开退款中心逐个 tab 看），晚发现一天，家长多等一天，
转让超时（72h 自动过期）甚至会造成业务损失。

### 现状盘点（2026-08-31 实测证据）

| 能力 | 现状 | 证据 |
|---|---|---|
| 审核事项 | 已有 4 类：订单/押金退款、退会、权益转让（RefundCenter 三合一，超管审核）；活动取消批量退款（ActivityManage 内嵌） | RefundCenter.tsx L142-259、ActivityManage.tsx L190-213 |
| 审核状态机 | 齐备：RefundRequest 七态、TransferRequest 四态含超时 expired、WithdrawalRequest；审核端点已注册 | models.py L156-184、transfer_service.py L273-408、router.py L208-281 |
| 家长端通知 | 完备：scene 枚举 + ref_type/ref_id 业务引用 + 幂等去重 + 微信尽力推送 | notifications.py L24-143 |
| **运营端通知** | **不存在**：Notification 表接收方只有 parent_id；admin 通知中心实为"家长通知的运营只读镜像"（代管已读） | notification_models.py L37-64、admin/router.py L106-139 |
| 通知→业务跳转 | **机制已建好**：admin Notifications 页已有 ref_type→路由映射（transfer/withdrawal_request/refund_request → /refund-center） | Notifications.tsx L42-56 |
| 待办聚合 | 无：Dashboard 无待办卡，Layout 无徽标，审核员无全局入口 | Dashboard.tsx / Layout.tsx |
| 超时守护 | 转让超时自动 expired（WM11）；但"临近超时提醒运营"没有 | transfer_service.py L220-236 |

### 结论

**这不是从零建模块，而是"补一条缺失的通知链路 + 一个待办聚合层"**。
70% 的底座（审核状态机/审核页/跳转映射/定时任务注册表）已经存在，
WM13 的本质是把"家长发起→运营感知→运营处理"这条线闭合。

## 三、关键设计决策（需用户裁决的两处）

### 决策 1：运营通知的存储模型

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **a. 独立 admin_notification 表（推荐）** | 新表，字段复用通知模式（scene/title/content/ref_type/ref_id/dedup_key/read_at），接收方=角色/全员 | 零回归风险：家长通知链路（已验收）完全不碰；读写分离清晰 | 两套通知代码，公共逻辑要抽 common |
| b. 现有 Notification 表加 recipient_type | 加列+改全部查询 | 单表单一事实源（B1） | 侵入已验收的 WM11 链路，回归面大，家长/运营查询互相污染 |

**推荐 a**：验收期不碰已 ACCEPTED 链路（回归红线第 2 条精神），B10 模式（横切归 common）正好指导公共部分下沉。

### 决策 2：运营通知的粒度

- **推荐"事项级"**（一次申请一条通知，带申请人/金额/事项摘要）而非"汇总级"（每天一条"您有 3 笔待审"）。
  理由：事项级可直接跳转对应单据（用户核心诉求）；汇总级信息量不足还需二次跳转。
  汇总诉求由 B 层徽标计数承担，二者互补。

### 已按推荐默认的设计（不再列选项）

- **权限**：通知发给"有审核权的角色"（refund.review 权限组），非全员广播；徽标按各自权限过滤
- **去重**：沿用 dedup_key 幂等（同一申请不重复轰炸）
- **范围控制**：本期只做站内（管理端页面+徽标），不做微信推送给运营（无通道，企业微信是远期）
- **审核回写**：审核完成 → 对应通知自动置已读（待办消音），不做反向通知运营（自己处理的自己知道）
- **家长通知不动**：审核结果通知家长已存在（wm_notify.py），不在本模块范围

**设计依据**（全部取自现有模式）：
- 双 tab 计数：对照 MemberManage 的 `孩子档案（N）/订单（N）`模式
- 管理待办表格列：时间/事项/申请人/金额/状态/操作——对照退款中心待审列表列结构
- 跳转：复用 REF_META 映射（refund_request/transfer/withdrawal_request → /refund-center；活动批量退款 → /activities），"去处理"按钮带 LinkOutlined 图标（现有 L183 同款）
- 状态语义：待处理=橙 Tag，已处理=灰 Tag + 行置灰；审核完成自动转已处理（后端回写）
- URL 镜像：现有四态镜像机制扩为五态（box/tab/page/keyword/scene）

### 6.2 感知层：侧边栏徽标（最小侵入）

侧边栏"通知中心"菜单项 label 包 Badge（`<Badge count={5} offset={[10,0]}>通知中心</Badge>`）：
- 计数 = 管理待办未处理数（不是家长通知未读——运营对家长通知无处理义务）
- 轮询：进入管理端后每 60s 刷新一次 counts（轻量 GET）
- 为什么不放 Header 铃铛：Header 现只有用户下拉，加铃铛要动布局；菜单徽标零布局侵入且与绘本风侧边栏协调。远期有实时推送时再升级 Header

### 6.3 Dashboard 待办卡（仪表盘首屏）

现有 Dashboard 顶部加一张"待办事项"卡（对照现有卡片网格布局）：

```
┌ 待办事项 ─────────────────────────────┐
│ 🔴 待审退款 2 笔     → 退款中心        │
│ 🔵 待审转让 1 笔     → 退款中心        │
│ 🟠 待确认收款 3 笔   → 会员管理·订单   │ ← WM3 counts 接入（预留项）
│ ⚪ 转让临近超时 1 笔  → 退款中心        │
└───────────────────────────────────────┘
```

数据源：一个聚合 counts API（一次请求返回全部分类计数，U3 模式禁 N 次请求）。
设计上"待确认收款"挂进同一张卡——用户在 WM3 裁决过这是运营核心待办，正好借 WM13 落地。

## 七、v2 深化修订（2026-08-31 专家自审，任务包 v2 为权威版本）

用户要求重审后发现的三个 P0 缺陷及修订（详见任务包 v2）：

1. **权限错配**：三类审核 API 全部 require_super_admin()——运营专员若见徽标点"去处理"必撞 403。
   修订：管理待办/徽标/counts 按查看者权限实时过滤（staff 视角为空），模型砍掉 recipient 字段
2. **孤儿通知**：家长可撤销退款/退会/转让 + 转让超时 expired，共 4 条终态路径 v1 未回写——
   通知永远挂"待处理"，运营点进去扑空。修订核心设计：**显示态实时算、审计态事件写**——
   "待处理"不落库，查询时 JOIN 业务表实时判定（StatusResolver），8 条终态路径结构性全覆盖，
   未来漏网自动兜底；新增第三显示态"已失效"（文案注明"家长已撤销/已超时"，比静默消失诚实）
3. **口径分叉**：徽标计数与列表若不同源必出现"计数 5 列表 3"。修订：计数与列表共用同一
   StatusResolver 口径

体验增补（目标：运营用起来不想骂娘）：
- **等待时长列**："已等待 X 小时"，超 24h 红字——等了 30 小时的退款比刚到的急，优先级的事实依据
- **跳转最后一公里**：RefundCenter 支持 ?tab=pending 预筛选 + ?highlight={id} 行高亮——
  从通知跳过来直接看到那一单，不是一片要自己翻的列表
- **徽标刷新联动**：审核完成主动刷新计数（不等 60s 轮询）；counts 拉取失败禁显 0（假 0 防护）
- **通知文案带申请原因原文**：content 即决策依据（"孩子转学"vs"想要回钱"处理节奏不同）
- **管理待办 tab 隐藏导出按钮**：量小，不做假功能
- **手动标记已处理必须填原因 + 审计留痕**：防"假装处理"

验收升级：Safety/Liveness 不变量集（S1-S4/L1-L3/C1-C2）+ 测试反例表（孤儿通知/权限/并发/口径
一致性），作为任务包 v2 的硬验收标准。
