## 二、任务卡

### WM11-F1【中】微信订阅推送在业务事务 commit 前派发：回滚即产生"幽灵通知"

- **验收可见性**：验收测不出（需 monkeypatch commit 失败——测试已写进卡片）
- **证据**【事实】（调用链逐环亲核）：
  - `backend/common/notifications.py:142`：`send()` 内调 `self._wechat_push(new_id, ...)`
  - `backend/integrations/wechat/subscribe.py:56-66`：`threading.Thread(...).start()`
    立即派发 daemon 线程真实调微信 API
  - 业务侧 commit 在后：`backend/domain/activity/service.py:456-467`——

```text
NotificationService(self.db).send(... "报名成功" ...)   # 456：微信线程已出发
self.db.commit()                                        # 467：commit 在后
```

- **现象与根因**：① commit 失败（锁超时/约束冲突）→ 站内消息行回滚，但家长微信
  已收到"报名成功"，无据可查；② `wechat_status='sent'`（notifications.py:75）实为
  "已排队"——daemon 线程内失败不回写，状态失真。根因：通知写入与推送在同一
  service 方法内同步完成，外部副作用未与事务边界隔离（违反"网关调用不进事务"
  纪律的精神——虽不阻塞事务，但副作用先于提交）。
- **修复方案**（推荐 A）：
  - **A（after-commit 钩子）**：推送收集到 pending 列表，
    `sqlalchemy.event.listen(session, "after_commit", ...)` 后统一派发；
    回滚则丢弃（站内无行、微信无通知，两侧一致）
  - **B（异步通道）**：推送统一挪到 tasks/notify_handlers 异步通道（发送记录
    由任务侧落库）——改动更大，与 WM13 待办轮询有联动
- **测试要求**：单测 monkeypatch commit 抛异常 → 断言 `push_subscribe_message`
  未被调用（**修复前会被调用，RED**）；正常路径微信发送回归。
- **验证等级**：C 级（common 层事务钩子，公共层改动必须全量 gate）
- **标注**：【事实】（调用顺序与线程派发）；线上 commit 失败率【推断】

### WM11-F2【中】死信表已建但事件总线未接线：失败事件实际丢失（仅日志）

- **证据**【事实】：`backend/common/events.py:431-439` 的 `_record_dead_letter` 只写
  结构化日志（注释称"新项目无死信表"）；而 WM11 迁移 f7a2c9e3b5d4 已建
  `dead_letters` 表、`notification_models.py:89-98` 已有 DeadLetter 模型——
  两者从未接线（tests/unit/conftest.py:20 TRUNCATE 清单含此表，证明基建在）。
- **现象与根因**：定时任务场景（不传 db 的独立 session 模式）handler 失败 →
  重试 1 次后死信只进日志，看板无从查询（D6 死信落库需求未真正落地）。
  根因：注释与现状脱节（WM11 交付时表建了、接线漏了）。
- **修复方案**：

```text
# events.py _record_dead_letter 改为落库（注意：死信写入必须用独立 session，
# 防连坐主事务——events.py:391 独立 session 模式已有先例）：
    session = SessionLocal()
    try:
        session.add(DeadLetter(event_type=..., payload=json.dumps(...),
                               error=str(exc), ...))
        session.commit()
    except Exception:   # noqa: BLE001 — 死信落库失败兜底回日志
        logger.exception(...)
    finally:
        session.close()
```

- **测试要求**：红测试——注册一个必失败的 handler → publish（无 db 模式）→
  断言 dead_letters 表新增一条（**修复前零条，RED**）；既有事件测试回归
  （events.py 当前 78% 覆盖，missing 384-429 恰是本路径——本卡同时补覆盖）
- **验证等级**：C 级（common 层）
- **施工顺序**：与 HC-T4（事件总线零测试偿债）同批——一次把重试+死信路径测全
- **标注**：【事实】

### WM11-F3【低】一处 monkeypatch 污染全局 SQLAlchemy func.count（patch 面过宽）

- **证据**【事实】：`tests/unit/test_wm11_notifications.py:190`：

```text
monkeypatch.setattr(nmod.func, "count", lambda col: literal(0))
```

`nmod.func` 即 `backend.common.notifications` 模块内 import 的 **sqlalchemy.func
全局对象**——patch 期间进程内所有 `func.count` 调用被替换（monkeypatch 结束才还原）。
- **判定**：故障注入型 mock，目的正当（模拟并发窗口触发唯一索引走 savepoint 分支），
  被测对象未被 mock、断言真实落地——**非假绿**；但同进程其他逻辑在窗口期被静默改变。
- **修复方案**：缩小 patch 作用域（改 patch notifications 模块内的具体查询构造，
  或用 SQLAlchemy `with_variant` 局部替换）；若改造成本高，加注释声明窗口期副作用
  并把该用例标记隔离运行。
- **验证等级**：B 级（tests 改动）
- **标注**：【事实】

### WM11-F4【低】仪表盘 today_logins 不滤 AuditLog.is_deleted（同函数 recent_changes 有滤）

- **证据**【事实】：`backend/domain/admin/service.py:130-138`（无 is_deleted）vs
  `:297-306`（有 `AuditLog.is_deleted == 0`）——同函数族两处口径不一。
  审计日志当前无软删入口，实害为零。
- **修复方案**：today_logins 补 `AuditLog.is_deleted == 0`（与 recent_changes 对齐）。
- **测试要求**：既有仪表盘测试回归
- **验证等级**：B 级（admin 域）
- **标注**：【事实】
