## 四、审查方法论（每个模块都走这五步）

**步骤**：① 读 PRD 对应章节列出规则清单 → ② 读 FEAT 验收标准补充 → ③ **读实际代码**验证每条规则（service 是业务逻辑所在，router 看入口，前端看入口是否存在）→ ④ 读对应 `tests/unit/test_wm*.py` 验证测试是否真的覆盖该规则 → ⑤ 对照手册步骤核对前端入口。

**每条发现归入四类（这是报告的核心分类）：**
- 【缺失】应做未做（连入口都没有）
- 【缩水】做了但比规则少了一截（如"提示不拦截"做成了"无提示"）
- 【反向】实现与规则相反（如该软拦截做成了硬拦截）
- 【测试掩盖】测试存在但断言固化了错误行为，或测试靠手工改库造状态绕过了真实链路（历史案例：WM6 过期测试手工把状态改成 expired，掩盖了"没人会把状态置 expired"的 P0 缺陷——**凡测试里出现手工 UPDATE/直接改库造业务状态的，一律深挖该状态在真实链路里由谁产生**）

**三条排除边界（不报为缺陷）：**
1. WM11/WM12 范围项：全部站内通知/微信订阅消息、全部定时任务（预约超时释放、订单超时取消、转让超时落库过期、逾期标记、会员过期落库、待评估名单、到期提醒、活动提醒、周月报自动生成）、数据看板业务统计、Excel 导出、消息页、死信表、线上微信支付、真微信登录。清单见 `docs/09-补充任务清单.md` §五。
2. PRD §十三"本期不做"23 项。
3. 界面美观/文案措辞类主观项。
