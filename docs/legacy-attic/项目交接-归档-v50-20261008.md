60. **外部回调的状态码不是给自家前端看的**（第 31 轮）：微信只认 200，4xx/5xx 一律重试（最长 24h）→ 回调处理链**任何异常都必须被吃掉并转成明确应答**（服务层返回 `(状态码, 响应体)`，Router 只照搬），且金额不符/流水号重复/迟到支付这类资金异常一律 `payment.anomaly` 审计留痕——钱的事必须事后查得到。
61. **接线级重构要抽"单一来源"而不是复制**（第 31 轮）：线上回调若另写一份"置 paid + 开会员"，会员到期日/押金记账/报名转正这些口径早晚漂移 → 人工确认与回调共用 `_settle_paid`；购买页展示价与下单价共用 `price_member_order`。
62. **回调必须拿原始报文字节**（第 31 轮）：签名是对原始串算的，解析成 dict 再序列化回去（空白/键序一变）必然验签失败——用 `Request` + `await request.body()`，随后 `run_in_threadpool` 回同步 Service（保持"Service 全同步"纪律，审查 P1-2）。
63. **往 god file 加功能前先想"抽哪块出去"**（第 31/32 轮）：`wm10_service.py` 贴着 800 行硬红线，本会话撞了两次（第一次抽 `refund_rules.py`，第二次抽 `refund_online.py` + `refund_queries.py`）——**读侧（列表序列化）与编排（跨网关流程）天生该分居**，硬塞进去只会反复解围。
64. **"受理"不是"终态"**（第 32 轮）：微信退款 API 返回 `success=true` 只代表受理，`status` 可能是 `PROCESSING`——资金状态机里**只有终态才落终态**；同理**对账只报不改**（自动改账是下一个事故的来源）。
