## 一、生产拓扑（单机，与 dev 同构 ADR-001 但职责分离）

```
微信小程序 ──HTTPS──┐
                    │   nginx（TLS 终结 + 静态 SPA）
馆内浏览器 ──HTTPS──┤     ├─ /api/*      → 127.0.0.1:8002（uvicorn 单进程）
                    │     └─ /（admin-web dist 静态）
                    │
              docker mysql:8.0（127.0.0.1 绑定，容器内 3306 不映射公网）
```

**关键决策**：TLS 在 nginx 层终结，后端保持 `uvicorn --host 127.0.0.1 --port 8002` 裸 HTTP。
理由：dev.sh 的 8443 镜像进程教训（P1-F10：双进程 APScheduler 任务双执行，TaskRunLog 同秒
双条）——生产**单后端进程**，证书装 nginx 一处，杜绝双调度复发。

## 二、生产 compose（`docker-compose.prod.yml`，与 dev 分离）**——已落地（2026-10-08，本地实测通过）**

**⚠️ `name: dmkwords-prod` 不是装饰**：两份 compose 的**服务名都叫 `mysql`**，Compose 按「项目名+服务名」认容器，
项目名默认取目录名——同一目录里跑 `-f docker-compose.prod.yml up` 会把 **dev 容器 `dmkwords-mysql` 直接替换掉**
（卷没动，但容器没了、dev 连不上）。2026-10-08 演练实测踩到，已用独立项目名根治。

| 项 | dev（docker-compose.yml） | 生产（已实现） |
|---|---|---|
| 项目名 | 目录名（`dmkwords`） | **`dmkwords-prod`**（见上警示） |
| 端口绑定 | `3306:3306`（**全接口暴露**） | `127.0.0.1:${MYSQL_PROD_PORT:-3306}:3306` 仅本机 |
| root 密码 | `dmkwords_dev`（弱） | `${DB_PASSWORD:?}` 从 `.env` 注入（缺失**直接拒绝启动**，禁写进 compose） |
| 容器名/卷 | dmkwords-mysql / dmkwords_mysql_data | dmkwords-mysql-prod / **dmkwords-prod**_mysql_data_prod（防误连 dev） |
| **binlog** | **未开启**（backup_binlog.sh 的 PITR 依赖它） | `--log-bin=mysql-bin --server-id=1 --binlog-format=ROW --binlog-expire-logs-seconds=604800` |
| 日志封顶 | 无 | json-file `max-size=10m, max-file=3`（R6 磁盘打满） |
| 健康检查 | 明文弱口令 | 容器内展开 `$MYSQL_ROOT_PASSWORD`（命令串不含明文） |
| 时区/字符集 | utf8mb4 +8:00 ✓ | 同款保留 |
| restart | unless-stopped ✓ | 同款 |

```bash
# 生产起停
docker compose -f docker-compose.prod.yml up -d
docker exec dmkwords-mysql-prod mysql -uroot -p"$DB_PASSWORD" -e "SHOW VARIABLES LIKE 'log_bin';"   # 期望 ON
# 本地/演练并存（换一份 env-file，例：MYSQL_PROD_PORT=3308 + 独立强密码）
docker compose --env-file /tmp/drill.env -f docker-compose.prod.yml up -d
```

实测（2026-10-08）：`docker ps` 端口列 `127.0.0.1:3308->3306`、`log_bin=ON`、`binlog_format=ROW`、
`server_id=1`、`binlog_expire_logs_seconds=604800`；与 dev 容器并存互不影响（演练见 §七）。

## 四、nginx 反代（模板已落地：`deploy/nginx/dmkwords.conf.template`）

模板就位（占位符 `__SERVER_NAME__` / `__CERT_CRT__` / `__CERT_KEY__` / `__ADMIN_DIST__` / `__BACKEND_ADDR__`），
部署时 `sed` 替换后落到 `/etc/nginx/conf.d/dmkwords.conf`，`nginx -t && nginx -s reload`。要点（文件头也有）：

```nginx
location /api/ {
  proxy_pass http://__BACKEND_ADDR__;            # 127.0.0.1:8002
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $remote_addr; # ★ 覆盖式，禁 $proxy_add_x_forwarded_for
  proxy_set_header X-Forwarded-Proto https;
}
```

- **★ 这一行与 `.env` 的 `TRUSTED_PROXY_COUNT=1` 成对**（审查 P1-5/P2-8）：nginx 覆盖 XFF（不追加），后端按
  "右起第 1 段"取真实 IP。只配一边 = 要么全站共用一个限流桶，要么伪造 XFF 能换桶（等于没限流）。
- 媒体缓存头（内容寻址 `immutable` 长缓存）由后端中间件下发（`backend/middleware/media_cache.py`），
  nginx **不得**覆写 `/api/` 的 `Cache-Control`。
- **本机无 nginx（brew 未装、沙箱内拉不到镜像），`nginx -t` 未跑**——已用结构性断言兜底
  （模板断言见 `tests/unit/test_prod_skeleton.py`：覆盖式 XFF 存在、`$proxy_add_x_forwarded_for` 不存在、
  花括号配平、与 `TRUSTED_PROXY_COUNT=1` 成对）。**部署机上必须补跑一次 `nginx -t`**。

**禁 0.0.0.0 红线**：uvicorn 生产启动一律 `--host 127.0.0.1`（dev.sh 的 0.0.0.0 仅开发态）。
生产启动脚本已就位：`bash deploy/start-backend.sh`（单进程、无 `--workers`、只绑 127.0.0.1，
且**启动前先跑 `validate_production`**——配置不合规直接拒启并打印常见修法）。

## 七、备份与恢复（R6 联动·P13 演练项）

**已就位脚本**（A-P2-5/6 安全提取 .env，禁 source 注入）：
- `scripts/backup_db.sh`：每日 mysqldump 全量，保留 30 天 → `backups/`
- `scripts/backup_binlog.sh`：每小时 binlog 增量 → PITR（**生产 compose 必须先开 binlog，见 §二**）
- `scripts/restore_drill.py`：**演练脚本**（2026-10-08 新增）——全量恢复 + 五表对拍 + 冒烟；`pitr` 子命令
  做"灾难 + 点对点恢复"（打锚点 → 写探针书 → 误删 → DROP DATABASE → 全量 + binlog 重放到误删前）。
  默认 dry-run，`APPLY=1` 才真跑；库名必须含 `drill` 且与业务库不同名（自毁防线）。

**⚠️ 部署前提（2026-10-08 演练实测踩到，两处工具缺口）**：
1. **宿主没有 mysql 客户端**时 `backup_db.sh` / `backup_binlog.sh` 直接跑不了（本机实测：`mysqldump`/`mysql`/
   `mysqlbinlog` 全部 `command not found`）。两条路：部署机装 `mysql-client`（`apt install mysql-client` /
   `brew install mysql-client`），或把 crontab 命令包一层 `docker exec`（如演练脚本的做法）。
2. **官方 `mysql:8.0` 镜像里没有 `mysqlbinlog`**（只装 `mysql-community-server-minimal`；同镜像的
   MySQL Shell 8.0 也没有 binlog 工具）——**PITR 重放必须在有 mysqlbinlog 的地方做**。所以"开了 binlog"
   不等于"能回放"：部署机装好客户端，或给容器加装 client 包，否则灾难当天才发现回放不了。

**生产 crontab（部署时安装）**：
```cron
0 2 * * *   /opt/dmkwords/scripts/backup_db.sh    >> /var/log/dmk-backup.log 2>&1
0 * * * *   /opt/dmkwords/scripts/backup_binlog.sh >> /var/log/dmk-backup.log 2>&1
*/30 * * * * df -P /opt | awk 'NR==2 && int($5)>85 {print strftime() " disk >85%"}' >> /var/log/dmk-disk.log
```
磁盘告警阈值 85%（R6：音频上百 GB 磁盘打满风险；OSS 迁移预案见 ADR-004 抽象层，本期不实施）。
首轮备份后必须核验产物非空 + `gzip -t` 通过（演练脚本已把这两条做成硬判据）。

**恢复演练步骤（P13 验收必做，演练结果留 LEDGER）**：
```bash
python -m scripts.restore_drill full        # 计划（dry-run）
APPLY=1 python -m scripts.restore_drill full   # 全量恢复 + 五表对拍 + 起后端冒烟
APPLY=1 python -m scripts.restore_drill pitr   # 灾难 + binlog 点对点恢复
```
手工等价（该机器已装 mysql-client，TARGET 指演练实例）：
1. 恢复全量：`gunzip -c 全量.sql.gz | mysql -uroot -p <目标库>`
2. PITR 重放：`mysqlbinlog --start-position=<锚点> --stop-position=<写入后> binlog.0000NN | mysql -uroot -p <目标库>`
3. 核对：行数对拍（books/parents/children/orders/**activities** 五表）+ 表数 + 迁移版本 + 起后端 health + 登录冒烟

**2026-10-08 演练结果**（证据：`gate-runs/2026-10-08/restore-drill-full.log`、`…-pitr.log`）：

## 九、与 dev 的隔离纪律

- 生产一律用 `docker-compose.prod.yml`（`-f` 显式指定），**禁在生产机跑 dev.sh**（0.0.0.0+弱密码+5173 前端热更全不该出现）。
- **两份 compose 靠项目名隔离，不靠文件名**：生产文件已声明 `name: dmkwords-prod`；缺了它，
  `up` 会把同目录的 dev 容器替换掉（§二 警示，2026-10-08 实测）。生产机若同时放 dev 文件，务必确认容器名是
  `dmkwords-mysql-prod`——出现 `dmkwords-mysql` 就是配错了。
- 数据库密码/SECRET_KEY 与 dev 完全不同值；`.env` 不入库（宪法既有红线）。
- 证书资产 certs/ 已入库（v6 批次）——CA key 属敏感件，生产机单独存放并收紧权限（600）。
- 单实例纪律：后端副本=1 + 调度器命名锁护栏（§八），**禁**再起第二个 uvicorn（8443 镜像进程事故复发面）。
