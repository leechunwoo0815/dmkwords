## 2. 逐条重验（每条：被审声明 → 我的证据 → 判定 → 订正）

### 2.1 【推翻·须重新定性】P1：容器镜像缺生产环境变量 → "任意手机号 1234 就能登，mock 支付还能把单结掉"

**被审声明三段**：①镜像和 `compose.prod.yml` 都没设 `APP_ENV`/`TZ`；②`Settings` 默认 `APP_ENV=dev`、`LOGIN_DEV_CODE=1234`、`SECRET_KEY=change-in-production`、`PAYMENT_PROVIDER=mock`；③"`deploy/start-backend.sh` 里的生产校验根本没在镜像路径上"，用这个镜像起服务即可 1234 登录 + mock 结单。

**我的逐环验证**：

1. **②默认值——属实**。`backend/config.py:51` `APP_ENV: str = "dev"`、`:55` `LOGIN_DEV_CODE: str = "1234"`、`:66` `SECRET_KEY: str = "change-in-production"`、`:104` `PAYMENT_PROVIDER: str = "mock"`。
2. **①镜像无 ENV——属实**。`Dockerfile:16-18` ENV 块只有 `PYTHONUNBUFFERED/PIP_NO_CACHE_DIR/UV_PROJECT_ENVIRONMENT`，无 `APP_ENV`/`TZ`。镜像直起 uvicorn（`Dockerfile:44` `CMD ["uv","run","--no-dev","uvicorn",…]`），不经 `deploy/start-backend.sh`。
3. **③"校验不在镜像路径上"——不成立**。`backend/main.py:51-52`：`settings = get_settings()` / `settings.validate_production()` 在**模块顶层无条件执行**——只要 uvicorn 加载 `backend.main:app`，校验必然跑，与用不用 shell 脚本无关。
4. **危害链断点（关键）**：`config.py:151` 校验早退门是 `if not is_production_env(self.APP_ENV) and self.DEBUG: return`——即"非生产 **且** DEBUG=true 才跳过"。镜像默认组合 = `APP_ENV=dev` + `DEBUG=False`（`config.py:52` `DEBUG: bool = False`）→ **不跳过** → 全量校验 → `SECRET_KEY == "change-in-production"` 命中（`config.py:156-160`）→ `config.py:210` `raise RuntimeError("生产环境配置校验失败: …")` → **容器启动即崩（fail-closed）**。
   即：**零环境变量的镜像根本起不来服务，到不了登录页**。"起服务就能 1234 登"要成立，必须运维主动配出 `APP_ENV ∈ 开发白名单` + `DEBUG=true`（跳过全部红线）——而文档化路径不这么教：`docs/20-生产部署手册.md:105/235` 要求 `APP_ENV=production` + `LOGIN_DEV_CODE` 置空；`deploy/start-backend.sh:46` 更是 `exec env APP_ENV=production …` 强制。
5. **①的 compose 半句——名不符实但方向不算错**：仓库实际文件是 `docker-compose.prod.yml`（被审报告写 `compose.prod.yml`，文件名不精确）。该文件**全文 55 行只定义了 mysql 一个服务**（`environment` 只有 mysql 容器的 `TZ: Asia/Shanghai`，line 23-26）——**后端镜像根本不在 compose 生产路径里**；文档化生产路线（docs/20 §一/§四）是原生 uvicorn + `start-backend.sh`。所以"compose 没给后端设 APP_ENV"是**空集上的真话**：它压根不含后端服务。

**判定：推翻原表述**。原 P1 的"安全洞"叙事不成立（fail-closed 先崩）。**重新定性为两条真缺陷**：

- **P2（可用性）镜像自足性**：镜像零 ENV 默认拒启（崩溃信息友好度另议）——想用镜像的人第一体验是 boot loop；且 `TZ` 未钉（python:3.13-slim 默认 UTC，若运维补齐变量起服但忘 TZ，**全部跨日判定——到期/签到/榜单/报表归属日——错位 8 小时**，正是本项目 A18-0022 轴的红线形状）。
- **P3（工程定位）**：后端镜像目前不在任何文档化生产路径上（compose.prod 只有 mysql；docs/20 是原生进程路线）——镜像的定位（CI 用？交付物？）没有口径，缺 ENV 是这个定位缺失的症状。

**订正后的修法建议**（替换 R11-a 原第一条）：
```
Dockerfile 追加：ENV APP_ENV=production TZ=Asia/Shanghai
（默认 fail-closed + 跨日正确；需要 dev 镜像时显式覆盖）

```

**反证记录**：我曾按 `compose.prod.yml` 字面搜索得出"文件不存在、报告事实错误"——**这是我的搜索疏漏**（实际名 `docker-compose.prod.yml`），本报告自我订正；该文件名不精确是被审报告的小瑕疵，但"文件不存在"的说法撤销。

### 2.2 【成立】P2：微信平台证书轮换"刷到了却没用上"

**被审声明**：`refresh_platform_cert` 只写文件，全仓没有清 `get_payment_gateway` 的 `lru_cache`，进程不重启就继续用旧证书验签，任务侧按新文件报绿。

**我的验证**：
1. `backend/integrations/payment/__init__.py:20` `@lru_cache def get_payment_gateway()`——API 进程内**单例**；`:36` `reset_payment_gateway_cache()` 存在。
2. `reset_payment_gateway_cache` **全仓零调用**（含测试——被审报告说"只被测试调用"，实测连测试都没调；措辞不准，实质无差）。
3. 证书持有形态：`backend/integrations/wechat/pay_v3.py:109` `__init__` 时 `self.platform_cert = load_pem_x509_certificate(…)` **加载进内存**；验签 `:214-229 verify_callback_signature` 用的是 `self.platform_cert`（内存对象，不读盘）。
4. **刷新任务的实例来源（定罪点）**：`backend/tasks/registry.py:189-190`——
   ```python
   from backend.integrations.wechat.pay_v3 import WeChatPayV3
   gateway = WeChatPayV3()
   if run_coro(gateway.refresh_platform_cert()):
   ```
   任务**新建了一个一次性实例**去刷新。`refresh_platform_cert` 确实更新内存证书（`:482 self.platform_cert = new_cert`，且 `:474-475` 有防降级判断——这部分写得不错）——**但更新的是这个用完即弃的实例**；API 进程经 `get_payment_gateway()` 拿到的 lru_cache 单例，其内存证书**保持旧值直到进程重启**。
5. 后果链：平台证书轮换日（微信侧证书更换/到期前拉新）→ 任务绿（文件已写、它自己的实例已更新）→ 回调验签继续用旧公钥 → **微信侧切到新证书签名的回调全部验签失败**（真金白银的支付回调）。

**判定：成立（P2 维持）**。修法：任务改用 `get_payment_gateway()`（断言 `WeChatPayV3` 实例后调 `refresh_platform_cert()`——单例的内存证书原地更新，无需清缓存）；或验签路径改为每次读盘+短 TTL。前者改动最小。

### 2.3 【成立】P2：任务运行记录 `running` 行永不成终态（看板"连续失败恒 1"）

**我的验证**（`backend/tasks/registry.py:359-399`）：
1. `:364-367` 创建 `TaskRunLog(status=RUNNING)` 后 `add + flush`（未 commit）。
2. 批次类任务函数**自带中途 commit**（例：第十轮亲读的 `reservation_service` expire 循环逐条 `self.db.commit()`）——running 行随任务中途 commit **落库**。
3. 失败分支 `:384` `session.rollback()`（对已提交的 running 行无效）→ `:387-397` **另插一条** `TaskRunLog(status=FAILED)` → commit。
4. 终态：库里同时存在一条**永久 RUNNING** 的残尸 + 一条 FAILED。看板按"最近 N 次运行"算连续失败时，残尸 RUNNING 行会**隔断失败序列**（"连续失败恒 1"的机制），且 RUNNING 残尸随时间累积污染任务健康视图。

**判定：成立（P2 维持）**。修法：失败分支先 `rollback` 后**重取并更新原 running 行**（`session.expire_all()` 或按 id 重查 `with_for_update`）再置 FAILED，而非另插新行；顺带把"按 started_at 取最近运行"的看板口径对残尸免疫。
