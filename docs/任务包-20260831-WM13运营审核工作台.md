## 〇、不变量集（本模块的验收标准，测试必须逐条对应）

**Safety（绝不允许发生）**
- S1 孤儿通知：列表显示"待处理"，但对应业务对象已终态（撤销/超时/审完）→ 运营点"去处理"扑空
- S2 权限撞墙：无审核权限的角色看到待审计数或徽标，点进去 403/空转
- S3 重复轰炸：同一业务事件产生多条通知（dedup 保证）
- S4 假装处理：手动标记已处理但业务对象仍待审，且无留痕

**Liveness（最终必须发生）**
- L1 申请落库 → 通知落库（同事务，申请成功通知必达）
- L2 业务对象到达终态（**全部 8 条路径**，见批次五）→ 通知审计态回写（同事务）
- L3 审核动作完成 → 前端徽标/计数/列表及时刷新（不等 60s 轮询）

**并发（时序推演已论证）**
- C1 双超管并发审核同一单：can_transition 守卫只放行一个，败者抛错不回写 → 天然安全
- C2 审核与家长撤销并发：状态机只允许一个成功；mark_handled 只挂成功路径 → 回写幂等且正确

## 一、核心设计：显示态实时算，审计态事件写（v2 灵魂）

admin_notification 的"待处理/已处理"**不作为存储状态，而是查询时实时计算**：

```
显示态 = f(业务对象当前状态)
  退款申请通知   → RefundRequest.status == pending ? 待处理 : 已失效/已审结
  退会申请通知   → WithdrawalRequest 待审态      ? 待处理 : ...
  转让申请通知   → TransferRequest.status == pending ? 待处理 : ...
  活动批量退款   → 该 activity 关联退款申请【全部终态】? 已处理 : 待处理
  转让超时预警   → TransferRequest.status == pending ? 待处理 : 已失效
```

- **handled_at / handled_by 仍物理存储**，但只作审计展示（"谁在何时处理的"），**不参与显示态判定**
- 这样设计的原因：通知的"待处理"本质是业务状态的派生投影（E-09 族），靠事件回写维护派生态必有漏网（v1 就漏了 4 条路径）；实时算让 S1 在结构上不可能，未来新增任何终态路径自动被覆盖
- 三种显示态：**待处理**（橙，行高亮）/ **已审结**（灰，带处理人）/ **已失效**（灰，文案注明"家长已撤销"/"已超时自动失效"——运营能看到"这单家长自己撤了"，比静默消失诚实）
- 徽标/待办卡计数与列表**同一实时口径**（同一条 SQL 逻辑），S1 与口径分叉一起歼灭
- 性能论证：单馆日申请量级几十条，JOIN 计数无压力；60s 轮询可承受

## 二、权限模型（v2 修订：按查看者权限实时过滤）

**事实**（router.py L231-301 实查）：退款/退会/转让的列表与审核端点全部 `require_super_admin()`。

- AdminNotification **不做"发给谁"的 recipient 字段**（v1 设计砍掉）——它是全局待办墙，**按当前查看者权限过滤显示**：
  - 超管：看到全部待办（当前三类审核全是他的事）
  - 运营专员（staff）：管理待办 tab 为空（徽标 0 隐藏）——因为他审不了任何一类；家长通知 tab 正常（dashboard.view）
  - 将来退款审核下放新角色时，只改权限过滤配置，模型不动
- todo-counts 同样按查看者权限过滤——S2 结构性歼灭
- 前端不做权限隐藏以外的逻辑：staff 视角管理待办 tab 保留（空态文案"暂无需要您处理的申请"），让运营知道这个功能存在

## 批次一 WM13-1：底座（模型 + 服务 + 触发点）

**模型**（backend/common/，B10 模式）：

```python
class AdminNotification(Base):
    (
        id,
        scene,
    )  # admin.refund_apply / admin.withdrawal_apply / admin.transfer_apply / admin.activity_batch_refund / admin.transfer_expiring / admin.refund_execute_failed（拷问 Q5 裁定新增，镜像家长端 money.refund_failed）
    title, content  # 事项级摘要，content 必含申请原因（见批次五文案规范）
    ref_type, ref_id  # refund_request / withdrawal_request / transfer / activity
    applicant_name  # "家长名·孩子名"
    amount  # 可空 Decimal
    dedup_key  # 唯一索引（S3）
    handled_at, handled_by  # 审计字段（展示用，不参与显示态判定）
    created_at
```

- 迁移 + 干净库验证迁移链
- AdminNotifyService.send（幂等）+ mark_handled(ref_type, ref_id, admin)（只写审计字段，幂等）
- **状态计算器 StatusResolver**（本批次核心新增）：输入通知 → 实时 JOIN 业务表 → 输出显示态（待处理/已审结/已失效+失效原因文案）。六种 scene 各一个分支，列表与计数共用。映射表以拷问 Q5 裁定为准（refund_apply: pending→待处理, approved/processing/refunded/rejected→已审结, failed→已审结【闭环由 execute_failed 通知接管】, cancelled→已失效·家长已撤销）
- 触发点 5 处（RefundService.apply / WithdrawalService.apply / TransferService.apply / 活动取消批量退款 / **RefundService.execute 失败分支**），同事务调用
- 测试：每触发点 1 例落库 + dedup 幂等 + StatusResolver 每分支（构造各状态业务对象断言显示态）——**StatusResolver 测试直接对应 S1 反例表**

## 批次五 WM13-5：回写闭环 + 跳转最后一公里 + 交付物

| # | 路径 | 位置 |
|---|---|---|
| 1-2 | 退款审核通过/拒绝 | RefundService.review |

| 5-6 | 转让审核通过/拒绝 | TransferService.review |

（每处一行调用，零逻辑改动）
注：即使某处回写遗漏，显示态仍正确（实时算）——回写只为审计展示完整，**这是双层设计的容错红利**

**跳转最后一公里**：RefundCenter 支持 URL 参数 `?tab=pending` 预筛选 + `?highlight={request_id}` 行高亮 3 秒——运营从通知跳过来**直接看到那一单**，不用自己找（v1 跳过去是一片列表，最后一公里断裂）

**通知文案规范**（content 即决策依据）：
- 退款申请："【退款申请】张女士为小明申请退款 ￥6000（订单 DMK...）。原因：{家长填的 reason 原文}"

- 原文引用不加翻译润色——运营看到原始理由才能判断优先级（"孩子转学"vs"想要回钱"处理节奏不同）
