## 一、必须修（合并前）

### R-1【P1】`after_commit` 在 SAVEPOINT 提交时提前触发 → 微信推送静默丢失

- 位置：`backend/common/notifications.py:35`（`_flush_pending_wechat`）。
- 事实：SQLAlchemy 对 **nested transaction（begin_nested / SAVEPOINT）的提交同样派发
  `after_commit`**（本机实测：`with s.begin_nested(): pass` 后事件已触发，`session.in_transaction()`
  仍为 True）。监听器无条件 `session.info.pop(...)` 并 dispatch → dispatch 用独立 session 查行，
  此时业务事务**尚未提交**，行对新 session 不可见 → 命中 `_dispatch_pending` 的"行不存在就跳过"
  分支 → 队列被清空；外层真正 commit 时队列已空 → **该条微信永远不推**（只留一条 warning）。
- 复现（本机实跑，非推演）：
  ```
  send()            -> calls after send: []
  begin_nested() 提交 -> wechat push skipped: 通知行 #35 不存在
  db.commit()       -> calls after outer commit: []      # 应恰好 1 次
  ```
- 当前触发面：今天没有"先 send 再 savepoint"的调用路径，因此是**潜伏缺陷**；但
  `add_with_unique_fallback`（SAVEPOINT）在 `order_service` / `activity/service` / `growth/service`
  / `identity/service` 都有真实调用点，任何一次顺序重构（或未来在通知之后补一个 upsert）就会命中。
  且 batch 150 的核心承诺「提交后恰好一次」在当前实现下**不成立**。
- 必须修法（最小）：`_flush_pending_wechat` 先判 `if session.in_transaction(): return`（不 pop），
  只在最外层 commit（`in_transaction` 为 False）时 dispatch；`after_rollback` 行为不变。
- 必须补判据：send → `begin_nested` 释放 → 外层 commit → 断言推送**恰好 1 次**；
  变异：去掉 `in_transaction` 守卫 → 该用例必须红。
- 现有测试缺口：`test_p2_1_commit_then_push_20261031.py:162`（`test_dispatch_skips_rows_missing_from_db`）
  把"行不存在就跳过"当成正确行为，恰好把这条丢失路径固化了；需要新增 savepoint 用例而非改口径。

### R-2【P2】A-L1 结论不成立（当前部署），且建议的启动告警会误报

- 位置：`docs/27` §六 A-L1；`backend/middleware/rate_limit.py:106`。
- 事实：生产 uvicorn 0.52.4 以默认 `proxy_headers=True`、`forwarded_allow_ips=127.0.0.1` 运行
  （服务器实测），nginx 设置 `X-Forwarded-For`，因此 `request.client.host` **已经是真实客户端 IP**；
  `_client_ip` 在 `TRUSTED_PROXY_COUNT=0` 时回落 `request.client.host`，**按 IP 的桶没有坍缩**。
  A-L1 所说"所有按 IP 限流变成全站共享一个桶"不是当前事实。
- 连带问题：A-L1 建议的"收到 `X-Real-IP` 而 `TRUSTED_PROXY_COUNT=0` 打 WARN"会在**每个生产请求**
  上误报（nginx 每次都设该头），是把一个不存在的故障变成日志风暴。
- 正确处理：保留 `.env.example` 的代理链说明（说明 `TRUSTED_PROXY_COUNT` 只在**关闭 uvicorn
  proxy headers 或再加一层代理**时才需要），删掉"中危·优先处理"与启动告警建议；如需防御，
  应写在启动脚本里断言"uvicorn 未开 proxy_headers 且 TRUSTED_PROXY_COUNT=0"这一组合，而不是看请求头。

### A. 先纠正复审者自己的错误（R-1 修法）

上一轮我建议用 `in_transaction` 做守卫——**这是错的**。本轮独立探针（两次，不同 session）确认：

- `after_commit` 派发期间：SAVEPOINT 提交 `in_transaction=True / in_nested_transaction=True`；
  最外层提交 `in_transaction=True / in_nested_transaction=False`。按我原文守，**所有推送都不会发生**。
- `after_rollback` 在 SAVEPOINT 回滚时**同样派发**（`in_nested_transaction=True`），滚动侧也必须加守卫——
  这是我上轮漏掉的另一半。
- 接手模型用的 `in_nested_transaction` 双守卫是正确的；我独立做了两个变异：
  摘提交侧守卫 → ⑥ 红；摘回滚侧守卫 → ⑦ 红。判据真实有效。

这条记入教训：**给事务/事件语义开药方前必须在目标 SQLAlchemy 版本上探针，不能凭记忆**。
