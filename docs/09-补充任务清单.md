## 一、P0 业务正确性缺陷（用户测试 WM3/WM5 大概率撞上，优先修）

### D1｜会员过期零拦截【最严重】 ✅ DONE（2026-08-24，测试 tests/unit/test_d1_member_gates.py，门禁 exit 0）
- **证据**：全库无任何代码把状态置为 `expired`（MEMBER_EXPIRED 只被 reading 权限和榜单 is_history *读取*，无写入路径）；`is_active_member` 只看 `member_status` 不看 `member_expire`。
- **后果**：正式会员到期后仍可借书/预约/听全馆音频，PRD §3.7 与 §12"过期边界"完全落空（WM6 那条"过期仅在手"测试是手工改库造的状态，掩盖了此洞）。
- **修法建议**（三层）：
  1. `Child.is_active_member` 改为：`member_status in (observation, pending_evaluation) or (formal and member_expire >= today)`——观察期/待评估按 §3.3 权益保留不限时，formal 过期即失效，**不依赖定时任务立即生效**；
  2. `renew()` 补过期拦截（现连会员状态都不查）；
  3. WM11 定时任务再把过期的 formal 落库为 `expired`、过期的 observation 落为 `pending_evaluation`（榜单历史口径 + 待评估名单用）。
- **回归测试**：formal 造 `member_expire=昨天` → 借书被拒（软提示可放行见 C17）、预约被拒、音频仅在手、续借被拒、测验已解锁可完成。
- **落地记录**：第 1/2 层已做（models.py `is_active_member`/`is_expired_member` 双属性）；涟漪同步修复：reading 音频门（formal 未落库也走"仅在手"分支）、周期榜 SQL 过滤 + 总榜 is_history、转让"转出方正式会员"检查、二孩折扣判活（过期的 formal 不触发 9 折）；第 3 层留 WM11。

## 附：验证分级纪律（2026-08-24 由用户裁定，立即生效）

| 级别 | 改动范围 | 本地验证要求 | 提交/CI 要求 |
|---|---|---|---|
| A 级 | 仅 `admin-web/**`，纯前端 | `pnpm exec tsc --noEmit` | commit 前可只跑 tsc；push 后由 CI 跑全量 gate（信任 CI） |

6. **展示价 ≠ 下单价**：购买页价格来自配置（`GET /api/miniapp/payment/plans`），但**下单价以服务端下单时重算为准**（二孩折扣按订单时刻判定，V1.1 §3.1）。

## WM12-B 任务包：原路退款 + 对账（2026-10-08，第三十二轮）

> 来源：PRD「退款方式（按当初怎么收的）：**微信线上支付的：审核通过后自动原路退回**家长的微信」（§3.6 退款）+ 上线前审查批次 5 的"对账"项 + WM12-A 收尾清单。

### 一、本批做了什么

| # | 项 | 落地 |
|---|---|---|
| 1 | **原路退款自动分流** | `RefundService.execute` 按**原始订单的收款渠道**分流：线上支付（`pay_method=wechat` 且 `transaction_id` 非空）→ 调微信退款 API；线下收款 → 沿用线下打款登记（不变） |
| 2 | **三段式退款**（模式手册 P2） | Phase 1 置 `processing` + 生成 `out_refund_no` 并提交（释放锁）→ Phase 2 事务外调网关（失败不回滚状态，善后交对账/重试）→ Phase 3 锁内重取：回调已置终态则认回调结果，否则按网关返回（`SUCCESS` 终态入账 / `PROCESSING` 留在执行中 / `CLOSED|ABNORMAL` 记失败） |

### 二、口径（不可回退）

1. **渠道跟着原单走**：能不能原路退，取决于**原始订单当时怎么收的**（`pay_method=wechat` + 有 `transaction_id`），不看退款单是谁申请的。
2. **网关"受理成功"≠ 退款成功**：微信退款是异步的——`status=PROCESSING` 时退款单必须留在"执行中"，**只有 `SUCCESS` 才落"已退款"**（钱没到账就不能显示已退）。
2b. **网关异常 = 未知态，不是失败**（2026-10-08 审查 P0-1 整改）：Phase 2 抛异常/超时 → 退款单**保持 `processing`** 并标记"未知态"（`gateway_unknown_at`），禁止在未知态重提（`execute` 只接受 `approved`/`failed`，未知态一律 422）；要重试必须先走**退款查单**（`POST /api/admin/refund-requests/{id}/query-gateway` → 微信 `query_refund`）确认上一笔未被受理。落 `failed` 再重试会生成新的 `out_refund_no`——若上一笔其实已被受理就是二次出款（这正是本项要防的）。
3. **回调幂等与乱序**：已 `refunded` 的单，重复或迟到的失败通知一律忽略（200），防资金状态反转。
4. **押金多笔支付不自动拆分**：押金若由多笔线上支付构成（首缴 + 补缴），**本批不自动原路退**（一笔退款只能对应一笔原交易）→ 回落线下打款登记 + 审计注明原因 + 对账报告可见。单笔构成的押金正常原路退。
5. **对账只报不改**：报告是给人看的（差异清单 + 定位），**绝不自动改单**——自动改账是下一个事故的来源。
5b. **对账的"合计不得超付"**（2026-10-08 审查 P0-1 整改，本地审计 L5/L6）：同一订单的活跃退款单（`approved`/`processing`/`refunded`）金额合计 > 订单已付金额 → 必报差异；押金类按孩子汇总与已缴押金合计比对。这是"重复出款"的对账兜底。
6. **对账缺凭据 = 跳过而非失败**：真通道未配置时记为 `skipped`（附原因），不把任务跑红（否则每天一条假失败）。
6b. **`skipped` 只允许两种原因**（2026-10-08 审查 P0-2 整改）：① 线上支付未开启/未接微信（未配置通道）；② 当日无账单（微信 `NO_BILL_EXIST`）。**哈希校验失败、签名失败、账单缺列/无法解析一律记 `failed`**——把"文件不可信"记成"跳过"，运营会读成"没问题"（本项修复前正是这个 bug）。账单 `hash_value` 缺失亦 fail-closed 拒绝（不得静默跳过校验）。
6c. **跨日退款按 `out_refund_no` 关联**（2026-10-08 审查 P0-2 整改）：退款行不依赖"当日已支付订单"集合，直接按商户退款单号反解退款单核对金额与状态；否则每笔跨日退款都会产生假 `bill_only` 差异，且跨日退款的金额/状态**永远不校验**。账单解析改用 `csv` 模块（商品名含逗号不再错列）。

### 二、口径（不可回退）

1. **未知态 ≠ 失败**：网关调用异常/超时保持 `processing` 且标记未知态；未查单确认前**禁止重提**（防止换单号二次出款）。
2. **`skipped` 是白名单**：只有"未开通道""当日无账单"两种；文件不可信（哈希/签名/格式）一律 `failed`。
3. **对账兜底"合计不超付"**：同一订单活跃退款单金额合计 + 同一孩子押金退款合计，不得超已付。
4. **线上支付 = 微信一键登录专属**（用户裁定）：判据是**家长档案已绑微信**（`parents.wechat_openid` 非空，即走过微信一键登录）；其他登录态小程序不显示支付入口，服务端 422 兜底。**不做**"短信登录后补绑 openid"的路径（99.99% 用户走微信登录）。演示库由 `seed_wm11_demo` 给演示家长预置 mock openid（`mock_openid_demo_parent`，仅 dev/验收链路）——否则本地 mock 通道无法演练"点立即开通"（本地拿不到真 openid）。
5. **生产校验开关是 `APP_ENV`**，不是 `DEBUG`（`DEBUG` 只影响日志与开发态行为）。
6. **限流只认可信来源**：默认不读 `X-Forwarded-For`；反代后由 `TRUSTED_PROXY_COUNT` 显式声明信任层数。
7. **回调"永久性不一致"不再 500**：金额不符 → 400 + 审计（拒绝落终态）；状态不可执行 → 200 + 审计（阻止 24h 重试风暴）。
