## 二、FEAT-091 新代码的具体 bug（docs/36 之后、按甲方明示绕过全量门禁上线生产的那批）

FEAT-091 按宪法 §八 自己的分级是 **C 级**（新迁移 `8e18104fc7d9` + 新依赖 psutil + 公共中间件），却只跑了 8 个单测 + tsc/build 就部署生产（交接卡 v180 §压缩点）。以下问题全部出自这批未过门禁的代码，**已逐行核验**：

### B1（P2，数据质量）采样线程与 live 请求线程共享速率基线、无整体互斥 → 监控曲线假尖峰/假零

- `monitor_service.py:123-148`：`now = time.monotonic()` 与 `psutil.disk_io_counters()/net_io_counters()` 在 `_rate_lock` **之外**执行，锁内只做"算差值 + 写基线"。两个线程交错时，后读计数器的线程可能先写基线，先读的线程后写 → **基线时间戳回退** → 下一次 `elapsed = max(now - prev_at, 1e-6)` 被钳到 1e-6 → 磁盘/网络速率出现**假尖峰**。
- `monitor_service.py:192-222`：`_proc_cpu` 整表换写（`_proc_cpu = current`），并发调用互相丢失对方刚建的基线 → 进程 CPU% 随机归零。
- `monitor_service.py:243-251`：`_last_mysql` 被 live 与采样两条路径共用 → QPS 差值互相污染。
- 触发方：`monitor_sampler.py:45-46`（APScheduler 线程，每 60s）与 live 端点（FastAPI 线程池，每管理员每 10s）**调用同一组采集函数**。3 秒 live 缓存只挡请求频率，挡不住与采样器的交错。
- **这是"运维主界面"的核心数据可信度问题**：页面越被当真，假尖峰越误导排障。
- 修法（三选一，推荐 a）：
  a. **采集单写者**：只有采样器调 `collect_host_metrics/collect_mysql`；live 读"最近一次采样快照 + 进程 Top 现采"，速率类字段直接复用采样行。结构性消灭竞态，还省 CPU。
  b. 把"读计数器→算→写基线"整段包进 `_rate_lock`（采集 ~100ms，锁竞争可接受）。
  c. 基线写入加单调守卫（`now <= prev_at` 则丢弃本次）。
- 判据：双线程交错注入的回归测试（断言速率不出现 >物理上限 的尖峰、基线时间单调）。

### B2（P2，口径错误）live KPI「应用请求 N 次/分」既不是"近 1 分钟"也没归一化

- `metrics.py:50-53`：`snapshot()` **不轮转**；轮转只发生在采样器每 60s 的 `snapshot_and_rotate()`（`monitor_sampler.py:47`）。
- 因此 live 的 `requests_1m` 实际是"**距上次采样轮转以来**"的计数，窗口 0–60s 锯齿：轮转后第 5 秒只有 5 秒的量。
- `ServerMonitor.tsx:626-630` 把这个原始计数直接标成 **「次/分」**：30 次/5 秒会显示"30 次/分"（真实速率 360/分）；轮转刚过则显示 0 次/分但有流量。P95 同理（`tsx:826`「最近 1 分钟 P95」）。
- 历史路径做了 `step/60` 归一（`tsx:162-167`），**live 路径漏了同款处理**——同一指标两套口径，正是错误记忆库 §八十六「同一指标算两遍」族的新实例。
- 修法：滚动 60s 窗口（时间戳环形桶/双桶加权），或至少 `count / window_seconds * 60` 归一 + 标签改「本窗口」。`window_seconds` 字段已经返回，前端没消费。

### B3（P3）采样器不受单实例锁的**逐次**保护，接管窗口会双写

- `monitor_sampler.py:28-38` 直接 `scheduler.add_job(sample_system_metrics, ...)`，函数体内**无 `ensure_scheduler_lock()` 复核**；文件头注释「仍受调度器单实例锁保护」只在**注册时**成立。
- 对比：其余 21 个任务走 `guarded_run`（`registry.py:517-527`）每次执行前复核锁。持锁副本丢锁（`wait_timeout` 掐连接）→ 看护线程让新副本接管注册 → **旧副本的采样 job 仍在跑**（它不复核）→ 双写 `system_metrics`、历史曲线密度翻倍。
- 修法：采样函数入口加 `ensure_scheduler_lock()` 复核（一行），或改走 guarded_run 的轻量变体（不写 TaskRunLog 但复核锁）。

### B4（P3）失败静默 + 无数据新鲜度指示

- `monitor_sampler.py:90-93`：失败只 `logger.exception`，不进看板、无告警通知（设计如此，防刷爆 TaskRunLog）。但若采样持续失败，历史曲线**静默停止生长**，页面无从分辨"服务刚部署"与"采样死了"。
- `monitor_service.py:303-308`（`_today_totals`）与 `398-403`（history）：DB 异常吞掉返回 0/空曲线——**后端版"失败伪装成空/0"**，与项目自己的 `check_admin_failure_states`/W4 红线同形（检查器只管前端，后端喂 0 前端无从分辨）。
- 修法：页面显示"最近采样时间"（数据里就有 `collected_at`，超过 2×60s 判陈旧并出失败态）；`_today_totals`/history 返回 `degraded` 标志。

### T2（P1，结构性）测试与 dev 共库是一整族事故的根因，建议测试库隔离

- 现状：`tests/unit/conftest.py:140-144` 对 **dev 同一个库** TRUNCATE；由此衍生：跑 pytest 前必须 `dev.sh stop`、docs/19 整本恢复手册、4 次历史翻车、gate.sh 收尾自动 restart+基线核验的复杂度、BDD 抢库卡死、"门禁在跑我又并发跑一个"事故（记忆库 §九十二）。
- **conftest 已经用同一招隔离了 uploads**（`conftest.py:13`：首次 import backend 前 `os.environ.setdefault("UPLOADS_DIR", tmpdir)`）。同款手法可隔离数据库：`os.environ.setdefault("DB_NAME", "dmkwords_test")` + 一次性 `alembic upgrade head` + seed 重放。
- 「单一环境 MySQL-only」约束的是**引擎与同构**，不是 schema 名——同一 MySQL 实例上第二个库不违反宪法，CI 本来就是独立 service 库。
- 收益：消灭整个"门禁后现场恢复"事故族；dev 演示数据不再被门禁清空；gate 收尾的 restart 逻辑可退役；pytest 与 dev 可并存。
- 成本与风险：一次性迁移；需核对个别测试是否隐式依赖 dev seed（如 check_demo_baseline 留在 dev 库）；behave environment 同步切库。建议先在一个分支验证全量绿再合入。
