## 2. MDL 挂起：排查与根因（本会话核心工作）

### 2.1 复现与证据链

```
pytest tests/unit/test_wm10_state_machines.py -o faulthandler_timeout=25 -v
- test_member_refund_links_withdrawal_r309 PASSED [ 20%]
- test_refund_execute_fail_then_retry FAILED        ← 'applying' vs 'pending_settle' 断言失败
- test_parent_cancel_refund_and_withdrawal Timeout  ← clean_db TRUNCATE TABLE withdrawal_requests 卡 25s+
    pymysql `_read_bytes`（SSL read 阻塞 in conftest.py:55）
```

- faulthandler 原生栈精确指向 `conftest.py:55`（`engine.begin()` 里 TRUNCATE）
- MySQL 侧：`innodb_trx` 无 RUNNING 事务（当时快照客户端异常，见 2.4 诚实标注）、`processlist` 无 MySQL 内部阻塞者
- 已排除：dev.sh 旧连接（先 stop 后复现）、MySQL 僵尸、锁等待超时（innodb_lock_wait_timeout=50s 未触发）、磁盘满（容器 df 正常）

### 2.2 根因（两个独立 bug 叠加）

**业务逻辑缺口（主因）**——`backend/domain/identity/wm10_service.py`：
1. `RefundService.review(approve)`（L254-259）：审核通过时**没有推进联动退会状态**。R-309 联动创建的 `WithdrawalRequest`（source=refund_linked）停留在 `applying`。
2. `RefundService.execute` 失败分支（L351-359）：仅当 `w.status == STATUS_REFUNDING` 才回 `pending_settle`——因 review 没推进，实际永远停在 `applying`，与 R-311"失败回待结算可重试"语义不符。
3. `_advance_withdrawal`（L447-451）：重试成功后仅接受 `refunding/applying` 才聚合推进 `completed`——`pending_settle`（失败回退态）不在白名单，重试成功后无法闭环。

**测试泄漏放大器（次因）**——`tests/unit/test_wm10_state_machines.py`：
- `_db()` helper（`get_session()` 直连）：`db.close()` 全部在 happy path；断言失败即泄漏。
- 用例 2 于 L156 断言失败 → 泄漏的 session 持有对 `withdrawal_requests` 的 MDL 引用 → 用例 3 的 TRUNCATE 无限等待（DDL 等独占 MDL）。
- 这正是"单跑用例 2 断言失败但不卡死；整文件跑用例 3 卡死"的现象成因（单跑时无后续 TRUNCATE）。

### 2.3 现象漂移说明（诚实标注）

交接卡记录 GLM 时代现象为"第 2 个用例的 TRUNCATE 卡住、单跑任一用例通过"。本会话实测：**用例 2 断言失败（非卡）、用例 3 TRUNCATE 卡、用例 2 单跑也是 FAILED**。
推断：GLM 时代为用例 1 某断言失败→泄漏→用例 2 TRUNCATE 卡；或当时未单跑用例 2。**两者的根因模型完全一致**（断言失败→`_db()` 泄漏→下一个 TRUNCATE 被 MDL 阻塞），本修复针对根因而非现象。

### 2.4 取证边界（诚实标注）

复现时快照脚本（docker exec 客户端，每 2s 采 innodb_trx/metadata_locks/processlist）产物为空——当时用于快照的 mysql 客户端查询疑似被同源问题干扰（原因未定案，可能为客户端在 TRUNCATE 等待期间执行相同查询时连接队列被占）。故未取得"挂起瞬间 MDL 持有者"的实时快照；定位结论基于：①faulthandler 精确栈 ②用例 2 特定断言失败 ③代码缺陷三点交叉验证（高度确信，但不含服务器端锁等待实时证据链）。**请专家复核是否存在替代解释**。
