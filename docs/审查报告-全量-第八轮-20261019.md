## 3. 缺陷清单

### 3.1 P1（12 条）

#### P1-1 借阅台逾期列表抢写状态，`overdue_mark` 漏扫 → **家长逾期通知永久不发**
> ✅ **已闭环（2026-10-19 第九十一批 A 批）**：`overdue_mark` 扫描面放宽 `IN (ACTIVE, OVERDUE)` + `_notified_keys()` 预取；变异红。守护 `tests/unit/test_audit8_a1_overdue_notify_20261019.py`。
- **位置**：`backend/domain/circulation/service.py:744-766`（`overdue_list` 逐行 UPDATE）vs `:700-715`（`overdue_mark` 只扫 `STATUS_ACTIVE`）
- **现象**：借阅台挂载/借还后都会调 `/api/admin/circulation/overdue`；它把 `ACTIVE` 记录改成 `OVERDUE` 并 commit。5 分钟一班的 `overdue_mark` 只扫 `ACTIVE`，此后永远扫不到这批记录 → `mark_and_notify` 不发通知。
- **影响**：`borrow.overdue`（PRD 逾期提醒）对"先被馆员看到"的书**静默失效**；全仓该场景唯一生产方就是 `overdue_mark`。状态本身仍正确，所以没人会发现问题。
- **证据/强度**：**实测✓**（V1；对照组与实验组差 1 条通知）
- **复现**：借书 → `due_at` 改昨天 → `GET /api/admin/circulation/overdue` → `POST /api/admin/tasks/overdue_mark/run` → `processed=0`，`notifications` 无 `scene=borrow.overdue`
- **建议**：`overdue_mark` 扫描条件放宽为 `status IN (ACTIVE, OVERDUE) AND due_at < now`（通知去重键已含到期日，幂等安全）；或让 `overdue_list` 只读不写（把惰性标记彻底收归任务）。

#### P1-2 押金退款缺"累计在途"闸：两张同额退款单可同时过闸 → **押金余额可被打成负数**
> ✅ **已闭环（2026-10-19 第九十一批 A 批）**：补"网关在途累计"闸（只数 `PROCESSING`）；变异红。守护 `tests/unit/test_audit8_a4_deposit_refund_cumulative_20261019.py`。
- **位置**：`backend/domain/identity/deposit_refund_guards.py:35-42`；对照订单侧同文件 `:52-96`（有 `sum(RefundRequest.amount)` 累计）；扣减只发生在 `wm10_service.py:496`（终态）
- **现象**：`assert_deposit_refund_executable` 只比"当前余额 vs 本次申请额"；`available_amount` 到回调/人工登记成功才扣。两张押金退款单可同时处于 `PROCESSING`，第二张仍读到 1200 可用 → 放行。**同族放大器**：`existing_dep_rr`（`wm10_service.py:598-611`）只数 `PENDING/APPROVED/PROCESSING`，**被拒/失败的押金退款单不算在途** → 会员费退款成功时会**自动重建**一张新押金退款单，与前一张 FAILED 的重试叠加。
- **影响**：线上通道受微信"单笔交易退款总额 ≤ 支付额"兜底；**线下人工打款登记路径无兜底** → 真金白银重复出款；无论哪条路径，`available_amount` 可为负（P0-D 明令不许）。
- **证据/强度**：**实测✓**（V2 闸放行）+ 代码确证（扣减时机、`existing_dep_rr` 过滤、`ALLOWED_TRANSITIONS[FAILED]={PROCESSING}`）
- **复现**：见 V2 探针；完整业务序列（R1 执行失败 → R0 成功触发自动重建 R2 → 重试 R1 → 双 PROCESSING）需 mock 网关集成探针
- **建议**：押金侧补齐订单侧同款累计闸（`本次 + 同押金在途/已退合计 ≤ 押金本金`）；`existing_dep_rr` 把 `FAILED/REJECTED` 一并纳入"不得自动重建"的判据，或改为"同一退会单只允许一张押金退款单"。

#### P1-3 未认证可无限写库：支付回调免限流 + 验签失败也落审计与待办

- **位置**：`backend/middleware/rate_limit.py:119`（`/api/pay/` 前缀在豁免名单里）<!-- docs-code-ignore: /api/pay/ -->；`backend/domain/identity/pay_notify_router.py:43`；`payment_service.py:456-467`；`payment_notify.py:178-228`
- **现象**：`handle_notify` 验签失败即 `_audit_anomaly`（1 行 `audit_logs` + 1 行 `admin_notifications`，`ref_id` 含 body 哈希 → 每次换 body 都是新行），而该路径**被限流豁免**。
- **影响**：未认证远程可无上限填充审计表与待办墙（磁盘/查询/告警刷屏）；`audit_logs` 无归档任务（P2-25），只增不减。
- **证据/强度**：**实测✓**（V3：5 请求 → +5/+5）

#### P1-4 全局限流三处可打穿（内存 DoS / 换桶绕过 / 并发 500）
> ✅ **已闭环（2026-10-20 第九十四批 B 批）**：① 新增 `is_routed_path()`（路由面取 **OpenAPI 契约面**——本版 `app.routes` 里是 `_IncludedRouter` 包装、无 `path` 属性），未命中的写请求并入 `UNROUTED_PATH` 兜底桶；② `_identity` 按 HTTP 语义归一（空白折叠 + scheme 大小写不敏感，取**凭证本体**再哈希）；③ `check`+清扫整体持 `threading.Lock`；④ 附加**桶数硬上限** `_MAX_BUCKETS=10_000`（到顶后新键并入单一溢出桶，**不淘汰活跃桶**）。**变异 4/4 红**（M1 摘路由检查 / M2 身份退回原文 sha1 / M3 去锁 / M4 摘封顶）。守护 `tests/unit/test_audit8_b_batch_20261020.py`。
- **位置**：`backend/middleware/rate_limit.py:39-68`（`_sweep` 遍历无锁）、`:96-107`（`_identity` 取原始头）、`:143-150`、`:175-193`
- **现象**：① 中间件在**路由匹配前**对所有写方法建桶，`normalize_path` 只归一数字/长 hex → 任意随机路径（`POST /x-probe-<随机>`）各建一桶，`_STALE_AFTER=3600` 且清扫是"每 512 次全表遍历"；② `_identity` 对 `authorization` 原文做 sha1 → `Bearer  tok` / `bearer tok` 等变体产生无限多桶（FastAPI 侧 `param.strip()` 后是同一个身份）；③ `RateLimiter` 无锁，事件循环线程与线程池并发修改 dict → `RuntimeError`（偶发 500）。
- **影响**：未认证内存/CPU DoS（单进程部署下直接打满 RSS）；已登录用户可任意放大写入频率；登录/支付等挂 `rate_limit` 的端点偶发 500。
- **证据/强度**：**实测✓**（V4 桶键 5/5；V5 8 线程 7 次 RuntimeError）+ 静态（桶爆炸路径）
- **建议**：`_identity` 先按 HTTP 语义归一（scheme 小写 + 去多余空格）再哈希；桶只对"路由存在"的路径建（或对 404 写路径用一个兜底桶）；`RateLimiter` 加 `threading.Lock`，`_sweep` 先复制 key 列表。

#### P1-5 图片解码顺序错误：像素上限在 `img.load()` 之后 → 上传可 OOM
> ✅ **已闭环（2026-10-20 第九十四批 B 批）**：改成「`open` → 判像素 → `load`」，并把 `Image.MAX_IMAGE_PIXELS` 对齐到同一上限（第二道闸）。**变异红**（把像素闸挪回 `load()` 之后）。守护用例用 9000×9000 巨幅 header + 1×1 数据构造，可判别「先判像素还是先解码」。
- **位置**：`backend/common/file_storage.py:143-149`
- **现象**：`Image.open()` → **`img.load()`（全量解码）** → 才判 `width*height > MAX_DECODE_PIXELS(50M)`。50MP 图解码约 150MB（RGBA/CMYK 更高），而体积闸只卡 8MB——纯色 PNG 可远低于体积闸。
- **影响**：有上传权限的 staff 可在 1 分钟内制造数 GB 峰值；生产单进程 uvicorn 无 worker 隔离 → 整站不可用。封面/活动图/凭证/报告图全走此入口。
- **证据/强度**：**代码确证**（顺序确定）；内存数字按 Pillow 口径推算
- **建议**：先读 `img.size` 判上限，再 `load()`；同时把 `Image.MAX_IMAGE_PIXELS` 显式调低以 fail-closed。
