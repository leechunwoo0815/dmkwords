### P0-1｜活动取消被 `expire_all()` 抹掉未落库状态：**活动仍是"已发布"、报名仍是"待支付"，接口却回报名为已取消** ✅
✅ **2026-10-17 已修**：`expire_all()` → `self.db.flush()`（回归 `test_activity_cancel_persists_activity_and_enrollment`；变异还原 `expire_all()` → 1 红）。

- **位置**：`backend/domain/activity/cancel_flow.py:36`（`a.status = CANCELLED`）、`:62-66`（`e.status = CANCELLED` + `e.cancel_reason`）、`:87-89`（作废订单后 `self.db.expire_all()`）
- **探针实测（真库，非推断）**：

```
[探针1] 接口回报={'activity_id': 1, 'refund_pending': 0, 'cancelled': 1, 'orders_voided': 1}
        活动=published | 报名=pending_payment | 订单=cancelled
```

- **根因**：session 是 `autoflush=False`（`backend/database.py:26`），循环内除 `RefundService.apply` 外**没有任何 flush**；
  SQLAlchemy 的 `Session.expire_all()` 会**丢弃所有未落库的挂起修改**（不是"仅刷新缓存"）——
  于是活动与报名的状态改写凭空消失，只有那条**立即执行的 `Query.update()`（作废订单）**留了下来。
- **触发路径**：任意「收费活动 + 存在一条 `pending_payment` 且关联订单未收款」的报名 → 管理端 `POST /api/admin/activities/{id}/cancel`。
  若这条报名在所有报名里排第一（id 最小，最常见），`:36` 的活动状态一并丢。
- **后果**（都是可见的经营事故）：
  1. 活动**仍是 published** → `ActivityService.enroll` 只校验「published 且未开始」→ **"已取消"的活动继续卖票**；小程序照常展示；
  2. 报名停在 `pending_payment` → 家长端显示"待收款"，管理待办【活动报名待确认】永挂；而订单已作废 → 收银台点确认收款会被拒（"钱收不到、事也没了"的哑状态）；
  3. 接口回报 `cancelled: 1` 与事实不符（**"接口说成功了，库里没发生"**，比报错更难发现）。
- **建议修法**：`expire_all()` → `self.db.flush()`；同时补断言测试「取消后 ① 活动 `cancelled` ② 无 `pending_payment` 报名 ③ 关联未收款订单 `cancelled`」。

8 线程 × 40 次（两查一提交）：完成 0 / 异常 8

- **修法**：`_holds_scheduler_lock/_acquire/release` 加一把 `threading.Lock`，或每个 job 用**独立短连接**取锁。
