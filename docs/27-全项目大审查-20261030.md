## 一、亲验确认（11 条，按严重度）

### P1-1 退会结算不过滤「已随转让处置」的订单 → 同一笔年费可再退一次
- 证据：`backend/domain/identity/wm10_withdrawal_service.py:418-440` 的订单扫描只按
  `refundable_types + status=PAID + is_deleted=0` 过滤；`refund_rules.refundable_amount`
  （`backend/domain/identity/refund_rules.py:42-54`）对 transferred 无任何判据。
  而家长入口有闸（`wm10_service.py:130-134`）、管理端受理有闸（`order_guards.py:109`），
  **唯独自动结算链没有**。
- 触发：年费单随权益转让置 `refund_status=transferred` → 孩子 WITHDRAWN → 重新入会 →
  再次申请退会并审核通过 → 结算把它当可退单建退款单。
- 后果：同一笔年费「转给受让方 + 退给原家长」= 重复得利/资金损失。
- 建议修法：结算查询加 `Order.refund_status != Order.REFUND_STATUS_TRANSFERRED`；
  判据：造一张 transferred 单，`_settle_items` 的 items 不得包含它（变异：去掉过滤 → 红）。

### P1-2 活动费「申请后退款窗口内签到」可全额退
- 证据：活动矩阵只在**申请时**检查（`backend/domain/identity/wm10_service.py:118-126`）；
  执行前六项复核**明确排除活动单**（`wm10_service.py:404-411`：「活动费/自定义单不触发」）；
  终态 `_finalize_refund` 无条件退全款，`_refund_activity_enrollment`
  （`wm10_service.py:729-737`）只对 ENROLLED/REFUND_PENDING 翻状态，**CHECKED_IN 跳过但钱照退**。
- 触发：活动开始前申请退款（允许）→ 正常签到参加 → 管理员事后审核通过并执行。
- 后果：已参加活动仍全额退款（成本已发生）。
- 建议修法：`_finalize_refund`/execute 对活动单再跑 `activity_refund_block`；
  已签到 → 拒绝执行并提示改为人工协商（或按配置扣费）。

### P1-3 人工确认收款（无流水号）遇到微信重复支付回调 → 静默 200
- 证据：`backend/domain/identity/order_service.py:415` `_settle_paid(..., transaction_id=None)`（默认），
  人工确认后 `order.transaction_id` 为空；`payment_service.py:536-544` 的幂等分支只有
  `locked.transaction_id and locked.transaction_id != data.transaction_id` 才记异常。
- 触发：同一订单先线下收现金（`confirm-payment`）→ 家长/系统又完成线上支付 → 回调到达。
- 后果：双收但系统只记一笔、无审计、无待办。
- 建议修法：`status=PAID` 且订单无线上流水（`pay_method` 非微信/`transaction_id` 空）时收到回调
  → `_audit_anomaly("已人工收款又收到线上支付回调")` + 管理待办。
- 现状缓解：生产 `PAYMENT_ENABLED=false`，回调不会到达；**开启支付前必须修**。

### P1-4 押金退款在途时重新入会 → 押金永久停在 REFUNDED
- 证据：`backend/domain/billing/service.py:184-185` 只在 `status == REFUNDED` 时复位；
  `wm10_service.py:487-489` 押金退款终态**无条件**置 REFUNDED。
- 触发：押金退款单处于 pending/processing（押金仍是 `refunding`）→ 孩子重新入会
  （入会复位看到非 REFUNDED 直接 return）→ 退款随后成功 → REFUNDED 终态。
- 后果：在册会员押金停在 REFUNDED，四条缴款入口全拒、借阅无担保。
- 备注：触发窗口取决于退会/转让流程的 `operation_locked` 解锁时机，**需端到端复现确认**。
- 建议修法：入会复位同时处理 `refunding`（挂起/取消在途退款单），或终态落库前再判当前会员态。

### P1-5 管理端造押金单不检查押金账户状态
- 证据：`order_service.py:102-105` 只有 `assert_no_inflight_deposit_order`；
  `order_pricing.py:83-84` 对 deposit 只读配置金额。对比 `billing/service.py:235-238`、
  `payment_service.py:183-191` 都有账户状态闸。
- 触发：孩子押金已缴/已部分扣除/已退时，管理端仍可建押金单并线下收款；
  `confirm-payment` 才被 `billing/service.py:76-77` 拒绝。
- 后果：钱已收、押金未记账，只能人工退款。
- 建议修法：造单前复用 `DepositService` 的同一判据（单一来源）。

### P2-1 通知在业务事务提交前推微信
- 证据：`backend/common/notifications.py:314-318`：INSERT IGNORE 后**立即** `_wechat_push`；
  调用方 commit 通常在之后（如 `order_service.py:402`、`wm10_service.py:586`）。
- 后果：主事务回滚/提交失败时，微信已告知「付款成功/退款到账」，站内信却消失。
- 建议修法：提交后推送（after_commit 钩子）或 outbox 表 + 后台投递。
- 现状缓解：生产 `WECHAT_SUBSCRIBE_ENABLED=false`，只落库不推送。

### P2-2 积分累加无行锁（管理调整路径）
- 证据：`backend/domain/growth/service.py:416` 普通读 `ensure_state`；
  `:101` `state.points_total += points`；无 `with_for_update`。
  对比测验路径（`growth/service.py:617` 附近）有 Child 锁。
- 触发：两个管理员同时调整同一孩子积分，或调整与打卡/测验并发。
- 后果：后写覆盖先写，`point_ledgers` 与 `points_total` 永久漂移；审计 `after` 失真。
- 建议修法：锁定读（`with_for_update().populate_existing()`）或条件 UPDATE
  `points_total = points_total + :p`。

### P2-3 家长建档先查后插，并发撞唯一索引 → 500
- 证据：`backend/domain/identity/service.py:78-81` 活跃查重是普通读；
  `parents.phone` 是全局唯一索引（含软删行，`alembic/versions/540436252807_*.py:105`）。
  注释宣称「行锁保证串行」，但行锁只加在**软删复活**分支，正常插入路径没有。
- 触发：两管理员同时用同一手机号建档（同型：ISBN 建书、首次押金账户）。
- 后果：后到者 1062 → 500（应为可读 409）。
- 建议修法：复用 `add_with_unique_fallback`（项目已有 SAVEPOINT 兜底）或 ON DUPLICATE KEY。

### P2-4 成长页失败后重试成功，错误态不消失
- 证据：`miniapp/pages/member-pkg/achievement/achievement.js:42-76` 成功分支只 `setData({summary,badges})`，
  **不重置 `loadError`**；`achievement.wxml:4` 用 `wx:if="{{loadError}}"` 整页替换。
- 后果：一次网络失败后，重试成功仍显示「成长数据加载失败」，用户只能退出重进。
- 建议修法：成功分支 `loadError: ''`；补一条 selftest/页面判据。

### P2-5 书详情进度加载失败被静默吞掉
- 证据：`miniapp/pages/reading-pkg/book-detail/book-detail.js:117` `catch { /* 静默 */ }`；
  `onQuiz`（`:263-278`）以 `progress.finished` 为闸 → 已读完的书也会被「需先听完音频（95%）」拦住；
  `checkFavorite` 静默 → 已收藏的书点收藏必吃 409。
- 建议修法：失败态可见 + 重试；或 `onQuiz` 以服务端 quiz 状态为主判据。

### P3-1 两处直连 fetch 绕过统一 401 处理
- 证据：`admin-web/src/components/PaymentReconcilePanel.tsx:125`、
  `admin-web/src/pages/GrowthManage.tsx:150` 直接 `fetch`，未走 `request()`/`handleAuthStatus`，
  token 过期只弹「导出失败/图片加载失败」，不跳登录。
- 建议修法：统一走 `request()` 或抽出带鉴权处理的下载工具。

## 三、总体判断

- **资金链路整体是有纪律的**（锁、幂等、审计、单一链路在多数路径上都在），本轮确认的问题集中在
  **「同一规则只写在部分入口」**：转让闸、活动矩阵、押金状态闸、退款执行复核——都是「一个入口有、
  另一个入口没有」。建议后续把这类判据继续往 `refund_rules` / `*_guards` 收敛，并加**入口清单判据**
  （列出所有调用点，逐个断言）。
- **前端问题集中在「失败态与竞态」**，与 2026-10 前几轮同族（W4/W7 检查器已覆盖"失败要有可见态"，
  但没有覆盖"成功后要清失败态""旧响应不许覆盖新状态"）。
- **鉴权/越权分域本轮未覆盖**，是当前最大的审查缺口。
