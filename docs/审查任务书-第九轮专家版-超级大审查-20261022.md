## 3. 判据：本项目认为"什么才算缺陷"

按严重度分级（定性必须落到某一条上，不许含糊）：

| 级别 | 定义 | 例子（本项目的真实缺陷） |
|---|---|---|
| **P0** | 资损/数据损坏/可被外部直接打穿导致钱或隐私出问题 | 未认证可改他人资金状态 |
| **P1** | 用户可见的功能破损或安全缺口，但需要特定条件 | 预约成功通知链整体断裂（订阅方在、发布方从不存在）；限流可绕 |
| **P2** | 口径漂移、并发可覆盖、静默截断、失败伪装成空/0、越权可枚举 | 响应头给了截断信号但前端读不到（列表静默截断） |
| **P3** | 卫生、可观测性、文档撒谎、死代码、弱证据 | 事件 docstring 写着不存在的订阅者 |

**明线（违反即缺陷，无需讨论"严重不严重"）**：
1. **错误不许伪装成 0/空**（失败态必须与业务空态可区分）。
2. **上限/窗口类数字一律后端下发**，前端不得自持副本。
3. **金额一律 `Decimal`**，禁 float。
4. **业务主数据禁物理删除**（软删 + 保留）。
5. **幂等键必须是业务对象键**（周期类必须带周期）；默认键 "1" = 终身一条 = 缺陷。
6. **跨域写必须走事件或公开方法**（不许直接改别人表/调私有方法）。
7. **读端点不许有副作用**（尤其不许 `commit()`）。
8. **越权与不存在必须同回应**（铁律 128）。
9. **文档里的数字也是断言**：基线/覆盖率/场景数/端点数是断言，过期即失真。
10. **自述必须与实现一致**（注释/宪法/检查器自述里承诺的事没做 = 缺陷；本轮的 P1-8 就是这么来的）。

### 4.2 台账判定词汇与规则

- `R1` 行（**高风险**）：必须**独立判定**，禁止"以上同理""其余同类"。

- 判定词汇：`OK` / `P0`·`P1`·`P2`·`P3`（附缺陷号）/ `VA`（不适用，**必须写理由**）/ `RG:<规则号>` / `MF`（**变异失败**：你改坏了而检查器没抓到——这本身就是发现）。
- **覆盖率算术**：逐节给 `已判定行数 / 该节总行数`，再给总计；与附录行数一致（我方会**重跑附录 A 的生成命令**核对分母）。

## 8. 方法协议（必须遵守）

### 8.1 证据三态（标签不许混用）
- `实测✓`：你**真的跑了**（贴命令与原始输出：HTTP 状态/DB 行/SQL/日志）；
- `静态`：读代码/契约/文档得出的结论（**必须写清读了哪一段**）；
- `无法判定`：写清**为什么**（缺凭证/缺环境/外部条件）。

### 8.2 探针规范
- 探针**只读优先**；需要写库时**只在一次性库/事务内**做，跑完回滚或按 §8.4 恢复。
- **探针必须先证明"能发现违规"**：我方首轮的教训——`probe_w3_invariants.py --self-check` 第一版把两个不变量方向比反，一度误判"探针是装饰"。任何探针都要有"注入 → 变红 → 回滚 → 回绿"的自证。
- 探针跑完**删除或入库**（不许留 untracked 文件让门禁步[9] 红——这是本项目的真事故）。

### 8.3 独立性与反假绿
- **不许引用我方结论当证据**；要引用必须先自己复现。
- 你的每个"OK"都必须有**反证抽样**（抽 ≥3 个最可能坏的实例）。
