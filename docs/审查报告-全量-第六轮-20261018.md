## 一、P1（6 条）

> 前 5 条是**第五轮结转未修**，本轮只做"是否仍存在"的复核（任务书 §3：确认而非重报）。第 6 条是已文档化的能力缺口。

### P1-1 押金 `refunded` 复位只挂观察期路径：走**年费**重新入会的孩子，押金永远缴不了（第五轮 P1-1 结转，**仍存在**）

- **位置**：`backend/domain/identity/order_service.py:407-415`（只有 `TYPE_OBSERVATION` 调 `_open_membership`）；`_open_membership` 内才调 `DepositService.reset_refunded_on_rejoin`（`order_service.py:528`）
- **触发路径**：孩子退会/转让结算 → 押金置 `refunded`（钱已退）→ 家长改走**年费**重新入会 → `_settle_paid` 走 `TYPE_FORMAL` 分支（只顺延到期日）→ 复位函数**不被调用** → 押金仍是 `refunded` → 四条缴款入口全拒 → 借书被 `borrow_gate` 拦，只能人工放行。
- **为什么是问题**：PRD 未限定"重新入会必须走观察期"；`WITHDRAWN → FORMAL` 是合法边（R-301）。资金担保缺失 + 孩子"是有效会员但缴不了押金"，属静默失效（无报错、无待办）。
- **证据**：`静态`（调用链唯一性可判定；未造"退会→年费"端到端）
  ```
  grep -rn "_open_membership" backend      → 只有 order_service.py:408（TYPE_OBSERVATION 分支）
  grep -rn "reset_refunded_on_rejoin"      → 定义 billing/service.py:139 + 唯一调用 order_service.py:528
  order_service.py:415 elif order.order_type == Order.TYPE_FORMAL:  → 只顺延 member_expire，不复位
  ```
- **影响面**：退会后再以年费入会的家庭；低频但一旦发生即"缴不了押金"，需人工改库。
- **建议修法**：把复位移到 `_settle_paid` 的公共前置（任何开通/续费成功后都调），或至少在 `TYPE_FORMAL` 分支也调；不要按订单类型分叉资金账户语义。
- **回归用例建议**：`refund.feature` 或 `membership.feature` 增"退会 → 年费重新入会 → 押金可缴"场景；单测断言 `deposit.status == unpaid` 且可创建押金订单。
- **变异建议**：删掉 `TYPE_FORMAL` 分支里的复位调用（修复后新增的）→ 用例必须红。

### P1-2 续借后第二周期的到期提醒被去重键永久吞掉（第五轮 P1-2 结转，**仍存在**）

- **位置**：`backend/domain/circulation/reminders.py:76-86`
- **触发路径**：一本书到期前收到"今天到期"提醒（`ref_id=borrow_record.id`，`dedup_key="0"`）→ 馆员办理续借 → 新的到期日再次跑到"0 天"节点 → 唯一索引 `(parent_id, scene, ref_type, ref_id, dedup_key, is_deleted)` 判定重复 → **第二次不再发**。
- **为什么是问题**：续借是 PRD 明文功能（每本 1 次），提醒是它的配套动作；去重键没有周期维度，属宪法红线"周期类场景的去重键必须带周期"。
- **证据**：`静态`（键构造可判定；第五轮为实测）
  ```
  reminders.py:83  ref_type="borrow_record", ref_id=str(rec.id)
  reminders.py:85  dedup_key=str(days)        ← days=节点(5/3/1/0)，无"第几轮"维度
  ```
- **影响面**：所有续借过的借阅记录（每本 1 次续借 → 大约每本都有一次）；家长端静默收不到第二周期提醒 → 逾期率上升。
- **建议修法**：`dedup_key=f"{days}:{rec.renew_used}"`（续借次数进键），或把 `ref_id` 换成"借阅周期实例 id"。
- **回归用例建议**：`borrowing.feature` 增"到期提醒 → 续借 → 新到期日前 0 天再提醒"→ 断言两条通知。
- **变异建议**：把键改回 `str(days)` → 用例必须红。

### P1-3 资金异常/退款执行失败两类待办用默认去重键（第五轮 P1-3 结转，**仍存在**）

- **位置**：`backend/domain/identity/payment_notify.py:193-203`（`SCENE_PAYMENT_ANOMALY`，无 `dedup_key`）；`backend/domain/identity/wm10_service.py:559-570`（`SCENE_REFUND_EXECUTE_FAILED`，无 `dedup_key`）
- **触发路径**：① 同一订单第二次回调异常 → 去重键默认 `"1"` + 同一 `ref_id` → 待办被判重，**第二条异常不落待办**；② 定位不到订单时 `ref_id="-"`，所有此类异常挤成一条。
- **为什么是问题**：这两类待办是资金事故的唯一运营入口（审计页仅超管可见）。静默丢失 = 钱出问题没人知道。
- **证据**：`静态`
  ```
  payment_notify.py:199  ref_id=target_id or "-"      ← 无 dedup_key 参数
  wm10_service.py:562    ref_id=str(req.id)           ← 无 dedup_key 参数
  AdminNotifyService.send 的默认 dedup_key="1"（common/admin_notifications.py:59）
  ```
- **影响面**：资金异常/退款失败场景；每次"第二起"即丢失；频次随规模上升。
- **建议修法**：`dedup_key` 带事件唯一标识——支付异常用 `transaction_id`/回调摘要，退款失败用 `req.id + 失败时间戳(分钟级)`；`ref_id="-"` 改为 `order_no`。
- **回归用例建议**：`test_audit6_money_todo.py`：同一订单连续两次异常回调 → 待办 2 条。
- **变异建议**：删掉 `dedup_key` 参数 → 用例必须红。

### P1-4 软删书目的 ISBN 唯一索引（单列、不含 `is_deleted`）→ 同 ISBN 重建直接 500（第五轮 P1-4 结转，**仍存在**）

- **位置**：`backend/domain/catalog/service.py:214-235`；DB 索引 `books.ix_books_isbn UNIQUE(isbn)`
- **触发路径**：下架并软删一本书 → 用同一 ISBN 新建 → `get_by_isbn()`（仓储自动过滤 `is_deleted=0`）查不到 → `book_repo.create()` 撞唯一索引 → `IntegrityError` 未被捕获（该处只有副本码 conflict 的 try）→ 裸 500。

- **证据**：`实测✓`（索引结构）+ `静态`（路径）

- **影响面**：图书资产管理；每次"软删后重建"必现；馆员无法自助解决。
- **建议修法**：二选一（与 `parents.phone` 同款）——软删时把 ISBN 置空/加后缀（复活需人工确认），或在 `create_book` 前置查询**含软删**行并转 409/复活。
- **回归用例建议**：`catalog.feature`/单测：建书 → 软删 → 同 ISBN 再建 → 断言 409（或复活成功），禁止 5xx。
- **变异建议**：把前置查询改回只查 `is_deleted=0` → 用例必须红。

### P2-1 死信 `dead_letters` 有落库、无任何读取面——跨域副作用失败只能靠人翻数据库

- **位置**：`backend/common/events.py:440-495`（`_record_dead_letter`）；`backend/common/notification_models.py:93`；**无任何 router 引用**
- **触发路径**：任一 EventBus 处理器重试后仍失败 → 写 `dead_letters` + error 日志 → 系统里**没有任何页面/接口/任务**读它；运营看不到、巡检脚本没有、看板不含。
- **为什么是问题**：第六十九批 P2-18 把"只写日志"修成"落库"，但对偶效应没做——落库之后谁看？同一族的 `TaskRunLog` 有 `/api/admin/tasks/runs` 看板，死信没有；跨域副作用（积分/词数/通知/审计）失败是**静默的数据缺失**，与"待办墙是运营唯一入口"的设计前提矛盾。
- **证据**：`实测✓`
  ```
  grep -rn "DeadLetter" backend | grep -v notification_models|events.py  → 0
  admin-web/src 内 dead* 命中仅为 enroll_deadline（无关）
  SELECT COUNT(*) FROM dead_letters → 0（当前尚未发生，但也没有"发生时会有人知道"的通道）
  ```
- **影响面**：全系统异步副作用；频率取决于事件失败率；发生后不可自助感知。
- **建议修法**：加 `GET /api/admin/dead-letters`（超管，分页 + 按 event_type 过滤）+ 待办墙加 `admin.dead_letter` 场景（复用现有 dedup 索引）；或最简：任务看板加一个"死信数"卡片。

- **变异建议**：删掉 `_record_dead_letter` 的 DB 写入 → 用例必须红。

### P2-2 待办墙全量加载 + 表缺 `(is_deleted, created_at)` 索引：量级上来后首屏与徽标一起变慢

- **位置**：`backend/domain/admin/todo_service.py:479-503`（`rows = q…all()` 后内存排序切片）；索引现状：`admin_notifications` 只有 `uq_admin_notif_dedup(scene,ref_type,ref_id,dedup_key,is_deleted)` + `ix_admin_notifications_scene(scene)`
