## 一、TL;DR

**结论：当前代码不能开启真实微信收款或退款。** 门禁绿（exit 0），但门禁测的是 mock 通道，而 mock 通道掩盖了三类真实资金问题：

1. **退款网关超时会被记成"失败"，而不是"执行中"**（P0-1）。这与项目自己的 F-030 口径相反。管理员随后重新执行，会用新的商户退款单号再退一次。已实测复现状态落点。
2. **对账是我们唯一的"漏退/多退"探测器，但它漏检跨日退款、把商品名含逗号的账单读错列、把哈希校验失败记成"跳过"**（P0-2）。用探针实测，三种情况都复现。
3. **线下手机号登录的家长无法线上支付**（P0-3）：`POST /pay` 返回 422"未取到微信标识"。短信兜底登录同样没有 openid。
4. **短信验证码校验存在丢失更新，可被并发暴力尝试**（P0-4）：20 个并发错误验证码全部被处理，库内 `attempts` 只记到 4（上限 5）。配合 `X-Forwarded-For` 可绕过登录限流（P1-5）。

**先干什么（按顺序）：** ① 修 `refund_online.py` 的网关异常分支，使其保持 `PROCESSING` 并禁止在未知状态下重提（P0-1）；② 修短信校验为原子条件更新（P0-4）；③ 修账单比对（P0-2），并增加"每笔订单退款合计不得超过已付金额"的对账项。门禁绿不代表这三件事正确，它们都需要专门的单元测试。

## 三、问题清单

分级标准：**P0** = 上线前必须修，否则资金、凭证或主链路会出错；**P1** = 上线前应修，或有明确的临时缓解；**P2** = 应当修，可排期；**P3** = 文档、代码卫生或证据不足。

### P0-1 退款网关异常被记为"失败"，重新执行会二次出款（资金）

- **位置**：`backend/domain/identity/refund_online.py:169-171`（except 分支注释："网关炸了也要落痕：退款单留在'执行中'"），`:173-230`（Phase 3 对异常无条件 `finalize(success=False)`，`:223-230`）。
- **与口径冲突**：`docs/billing-circulation模式手册.md` L75-76（F-030）："Phase 2 失败…**保持 PENDING，不回滚**，因为网络超时窗口内微信可能已受理。"本代码的注释也写了"留在执行中"，实现却相反。
- **触发条件**：网关调用抛异常或超时（`gateway.refund` 抛出，而不是返回 `success=False`）。
- **复现（已执行，只读，stub 网关，不连库）**：`/tmp/review1009/refund_probe.py`。
  ```
  网关超时后 finalize(success=..)= [False]
  退款单终态 = failed | out_refund_no = RF7-1-1
  备注 = 微信退款失败：网关异常：read timed out after 30s（RF7-1-1）
  允许 FAILED→PROCESSING 重新执行 = True
  ```
  预期：状态保持 `processing`，等待退款结果通知或人工查单。实际：落 `failed`。
- **后续链路**：
  1. `wm10_service.py:387-391`：`execute` 接受 `APPROVED` 或 `FAILED`；`models.py:205`：`FAILED → PROCESSING` 合法。管理员重新执行会生成 `RF7-2-1`，即**新的商户退款单号**。
  2. 若 `RF7-1-1` 实际已被微信受理（超时窗口），而退款额是部分退款（如 49.50 元，订单 99 元），`RF7-2-1` 也会被受理，**同一请求出两笔钱**。
  3. 迟到的 `RF7-1-1` 成功通知：`refund_online.py:257-263` 中 `FAILED→PROCESSING→REFUNDED` 合法，单子变成已退款。随后 `RF7-2-1` 的成功通知会被"已退款"守卫忽略（`refund_online.py:257-258`）。**结果：钱出了两笔，本地只记一笔，且没有任何差异记录。**
  4. 对账无法发现：`payment_reconcile_service.py:152-165` 的 L2 只查 `PROCESSING`，`FAILED` 的单子不可见；`_diff_refund_row`（`:379-409`）逐行比对，不做"每笔订单退款合计 ≤ 已付金额"的校验（全文无 sum 比对，已 grep 确认）。
- **影响面**：钱（重复出款，且本地无痕）。仅部分退款或押金多笔场景会真的多出款（全额退第二笔会被微信以"超过可退金额"拒绝，但本地仍误记）。
- **验收判据**：
  - 单测：网关抛 `TimeoutError` 后，退款单状态为 `processing`，`gateway_attempts` 不变或被标记为"待查"；不得写 `failed`。
  - 单测：在状态为未知的退款单上再次 `execute` 必须被拒绝（422），直到通过微信查单确认为未受理。
  - 对账单测：同一订单两笔 `REFUND` 合计超过订单金额时，必须产生差异项。
- **最小修法**：异常分支不调用 `finalize`，保持 `PROCESSING` 并写审计 `refund.gateway_unknown`；增加"未知态"标记；对账增加每笔订单退款合计校验；重试前先调微信退款查询接口（`query_refund`，需要新增网关方法，**未实现**，见 §五）。
- **验证状态**：**已验证**（探针复现状态落点；代码路径已读）。微信真通道未测。

### P0-2 账单比对三处结构性缺陷，对账不可信（资金/数据）

对账是 P0-1 之外唯一的漏退探测器，它本身有错。三处缺陷都用探针复现（`/tmp/review1009/bill_probe.py`，伪造会话，不连库）。

**(a) 跨日退款产生假差异，且退款校验对跨日退款永不执行。**
- 位置：`payment_reconcile_service.py:315-356`。`ours` 只包含**当日**支付的订单（`paid_at` 在账单日内）。退款发生在另一天时，订单不在 `ours`，走到 `:345-356` 的 `bill_only` 分支并 `continue`，**`_diff_refund_row`（`:367`）从不执行**。
- 复现输出：`场景1 跨日退款：checked=1 diffs=[('bill_only','O1')]`；同一订单若在当日，`diffs=[]`。
- 影响：每一笔跨日退款都会产生假的 `bill_only` 差异；真正的退款金额不符、退款状态不符对跨日退款**永远检测不到**。

**(b) 账单解析用朴素逗号切分，商品名含逗号时列错位。**
- 位置：`payment_reconcile_service.py:432`（`ln.split(",")`），`:435` 按列序取值。
- 复现输出：`场景2 商品名含逗号：diffs=[('amount_mismatch','金额不符：账单 0% vs 本地 99.00')]`。商品名"绘本套装,上册,下册"使 `订单金额` 列取到了费率列。
- 影响：假的金额不符；更严重的是列错位后，错误金额可能与本地金额碰巧相等，从而**漏检**。
- 注：需要用真实微信账单样本核对列序（未验证，见 §五）。

**(c) 哈希校验失败与签名失败被记为"跳过"。**
- 位置：`payment_reconcile_service.py:278-282`：`"账单" in message` 则为 `SKIPPED`。`pay_v3.py:368` 的哈希失败文案是"微信对账单哈希校验失败…"，含"账单"，故被记为 `SKIPPED`。
- 复现输出：`场景3 哈希失败文案被映射为： SKIPPED`。
- 另：`pay_v3.py:363` `if expected_hash and meta.get("hash_type", "SHA256").upper() == "SHA256":` 在 `hash_value` 为空或 `hash_type` 不是 SHA256 时**整段校验跳过（fail-open）**，且不记录任何告警。
- 影响：文件被篡改或下载不完整，对账显示"跳过"，运营会误读为"没问题"。这正是 brief 第 8 条担心的"对账跳过被误读"。

- **验收判据**：
  - 跨日退款：账单退款行必须通过 `out_refund_no` 关联到退款单（不依赖当日订单），金额与状态被校验。
  - 解析：改用 `csv` 模块解析并处理引号；单测覆盖商品名含逗号。
  - 哈希失败、签名失败必须记为 `failed`，不得为 `skipped`；`hash_value` 缺失应记为 `failed` 或显式告警。
  - 单测使用真实微信账单样本（需要用户提供或从商户后台导出）。
- **最小修法**：按 `out_refund_no` 反查退款行；`csv` 解析；`SKIPPED` 只允许"账单不存在 / 未开启通道"两种明确原因。
- **验证状态**：**已验证**（三个场景用探针复现）。真实账单格式未验证。

### P0-3 线下手机号登录的家长无法线上支付（主链路）

- **位置**：`payment_service.py:169-173`（`openid` 为空即 422）；`auth.py:108-136`（`authenticate_parent` 与 `authenticate_parent_sms` 只查 `phone`，不写 `wechat_openid`）。
- **复现（已执行）**：S2、S3 均返回 `422 {"detail":"当前登录未取到微信标识，无法发起微信支付（请用微信一键登录后重试）"}`。
- **影响**：任何通过手机号 / 验证码登录的家长都无法在线支付，包括短信兜底登录。微信一键登录是主通道（`auth.py:125` 注释），但在它失败、或家长换手机号时，支付入口会以一个模糊的 422 失败。
- **验收判据**：明确产品口径。若"必须微信登录才能支付"，则小程序在非微信登录态下必须隐藏支付入口（而不是点了报 422），且有单测。若允许兜底登录后支付，则需要绑定或拉取 openid 的路径。
- **需要用户决策**：见 §七。
- **验证状态**：**已验证**（API 实测 422）。

### P0-4 短信验证码校验为非原子读改写，可被并发暴力尝试（凭证）

- **位置**：`sms_service.py:123-153`。`:144-146` 读取 `row.attempts` 并判断上限，`:147-151` 比对后 `row.attempts += 1` 再 commit。全程无行锁、无条件更新。
- **复现（已执行）**：对手机号 13800006666 发送验证码后，用 20 个线程并发提交 20 个错误验证码（每个请求带不同 `X-Forwarded-For`，见 P1-5）。
  - 结果：20 个请求全部返回 `验证码错误（还可尝试 N 次）`，N 为 4、2、3、1 等，**没有一个返回"错误次数过多"**。
  - 库内：该手机号最新 `sms_codes.attempts = 4`，而 `sms_max_attempts = 5`。20 次尝试只被持久化了 4 次，丢失更新。
- **影响**：每个验证码（6 位数字，有效期 300 秒）可以在一个窗口内被远超 5 次地尝试，并发请求即可绕过次数上限。验证码的暴力破解空间是 10^6，并发足以使它在有效期内可行。当前 SMS 登录路径（`auth.py:132`）在 dev 码之外的所有码都要过这里；bind 路径（`auth.py:200`）同理。
- **验收判据**：并发 50 个错误码，`attempts` 最终等于请求数（或达到上限后被拒），且返回"次数过多"的请求数正确；单测用真实 MySQL 行锁或条件更新 `UPDATE sms_codes SET attempts=attempts+1 WHERE id=:id AND attempts<:max`，检查 `rowcount`。
- **最小修法**：条件更新 + 检查 `rowcount`；校验成功时同样用条件更新置 `used_at`，防止同一码被并发重放。
- **验证状态**：**已验证**（并发 burst + 库内计数）。

### P1-5 登录限流可被 X-Forwarded-For 绕过（凭证）

- **位置**：`backend/middleware/rate_limit.py:50-61`（信任 XFF 首段）；`:64-75` 以 `path:ip` 为键。注释（`:53-54`）承认依赖网关覆盖 XFF，但代码未做任何校验。
- **复现（已执行）**：P0-4 的 20 个请求分别带 `10.9.1.{i}` 的 XFF，全部通过 `/api/miniapp/login` 的 `3/60` 限流。若不伪造，同一 IP 的连续登录在窗口内会被 429（审查过程中多次实测，返回 `429 请求过于频繁，请 60 秒后再试`）。
- **影响**：IP 限流形同虚设。配合 P0-4 即为暴力破解的放大器。
- **验收判据**：只在可信代理之后读取 XFF（配置 `TRUSTED_PROXY`），否则使用 `request.client.host`；单测带伪造 XFF 的请求落入同一桶。
- **验证状态**：**已验证**。

### P1-7 退款回调不校验退款金额（微信侧信任边界）

- **位置**：`payment_service.py:379-393`（SUCCESS 分支只按 `out_refund_no` 反解，不比对 `data.refund_amount`）；`refund_online.py:233-265`（`finalize_gateway_result`）。
- **影响**：若微信回调携带的退款金额小于申请金额（部分退款），本地仍会把整单记为已退款。在签名有效的前提下，这是"回调与事实不一致"，而不是伪造。
- **验收判据**：回调退款金额与 `req.amount` 不一致时拒绝并告警，不落终态。
- **验证状态**：代码已读，**未实测**。签名有效性前提在真通道未验证。

### P2-8 退款列表 N+1，每请求 SQL 随行数线性增长（性能）

- **位置**：`backend/domain/identity/refund_queries.py:48-63`。每行额外查询 `Child`（`:52`），以及 `Order`（`:56`，仅 order 类退款）；`resolve_online_source` 对押金类退款再查一次（`refund_online.py:66-73`）。
