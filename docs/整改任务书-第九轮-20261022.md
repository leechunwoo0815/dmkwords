#### ② N-1「书城列表仍全表扫 + filesort」= **前提不可达**

- 事实：全仓**没有任何** books 查询按 `create_time` 排序（`grep -rn "Book\.create_time" backend/` → 空）；书城/书目列表的真实形状是 `WHERE is_deleted=0 AND status=? ORDER BY id DESC`。
- 实测（项目 engine，只读 EXPLAIN）：
  ```
  ① books 真实形状(is_deleted+status+id desc) → type=index key=PRIMARY  Extra=Using where; Backward index scan   ← 无 filesort
  ② 专家形状(is_deleted+status+create_time desc) → type=ALL key=NULL Extra=Using where; Using filesort          ← 不可达
  ```
- 且该形状早在**第七十六批**就修过：索引 `ix_books_deleted_status_id(is_deleted,status,id)` 在位（`SHOW INDEX FROM books` 可见），专项测试 `tests/unit/test_audit7_p2_indexes_20261018.py`，设计理由写在 `backend/domain/catalog/models.py:20-22`（"索引列尾用 **id**（真实排序键）而不是报告建议的 create_time——默认排序是 `id DESC`，用 create_time 收尾仍会 filesort"）。
- 结论：**撤销 N-1**，不需要任何改动。这也是专家自己在 M-3 里提的那条教训（"复现方法本身要审"）的同类——把自构造的 SQL 当成了线上形状。

#### ③ N-3「orders `ORDER BY create_time DESC` 无覆盖 → filesort，建议加 `(child_id, create_time)`」= **形状错 + 修法错**

- 实测（同上）：
  ```
  ③ orders 管理端默认(is_deleted+id desc)        → type=index key=PRIMARY             Backward index scan
  ④ orders order_by=created_at_desc(真实可达)    → type=index key=ix_orders_create_time Backward index scan  ← 无 filesort
  ⑤ 专家假想形状(child_id=? + create_time desc)  → type=ref   key=ix_orders_child_id Using filesort          ← 不可达
  ```
- `ix_orders_create_time` **已存在**（`SHOW INDEX FROM orders`）；管理端订单列表的过滤条件只有 `is_deleted / status / keyword`（`backend/domain/identity/order_service.py:589-596`），**没有 child_id**——所以建议的 `(child_id, create_time)` 对真实查询无用。
- 结论：**撤销 N-3**，不加索引。

#### ④ N-7「CheckInEvent 发布无订阅（白发）」= **假阳性**

- 事实链完整：
  - `backend/common/events.py:191` 类定义，`:200` `event_type: str = "reading.checkin"`；
  - 发布：`backend/domain/reading/service.py:228` `event_bus.publish(CheckInEvent(...))`；
  - **订阅：`backend/domain/growth/growth_handlers.py:23` `event_bus.subscribe("reading.checkin", _handle_checkin)`**，并在 `backend/main.py:152` `register_growth_handlers()` 启动注册。
- 为什么会漏：订阅用的是**字符串字面量** `"reading.checkin"`，不是 `CheckInEvent.event_type` / 类名——任何按类名或 `.event_type` 形式做的 AST 扫描都看不见它。
- 结论：撤销「白发」判定。**但其中真实的半条保留**：该 docstring（`events.py:192-198`）写的订阅者是「child 更新连续打卡天数 / achievement 检查打卡成就」，实际是 **growth 周期积分**（`growth_handlers.py:19`）→ 降为 **P3 文档订正**（进 E 批）。
- **对 P1-8 的硬设计约束**：事件对账器**必须把字符串字面量订阅解析进订阅集合**（并覆盖 `X.event_type` 与类名两种写法），否则会把这条假阳性复制进 gate 里。

#### ⑤ P2-1 的修法「给未建档手机号不发短信」会 **打死注册流程**

- 事实：`POST /api/miniapp/sms/send` 的定位是「登录兜底 / 微信绑定共用」（`backend/domain/identity/miniapp_router.py:430-439`）；服务层已有三道闸：同号间隔 / 每日上限 / 校验失败次数 + 单 IP 日上限（`backend/domain/identity/sms_service.py`）。
- 判据：**若注册路径依赖短信验证码**，"未注册就不发"= 新家长永远注册不进来；**若注册走微信手机号授权**、短信只作兜底，则该闸成立。这是产品语义问题，不是纯技术问题。
- 结论：**不照抄**。→ 进 §八 挂起项等甲方一句话；默认做法 = **分档限流**（未建档号更紧的日/IP 上限 + 发送审计 + 阈值告警），不改变可注册性。
