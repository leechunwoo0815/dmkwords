## 三、审查方法论（你的核心资产，三轮验证有效）

### 3.1 声明核验四件套
每个开发模型简报里的关键声明，按此核验：
- **代码声明**：git diff / Read 逐行对（行号会漂移，"约L155"要实查）
- **测试声明**：读测试文件本体，查假绿（恒真断言/mock 被测对象/断言响应键不符/
  造状态直改 DB 而非走 API——定时任务类测试"直改造历史态"是允许的例外）
- **门禁声明**：gate-runs/YYYY-MM-DD/*.log 必须已落盘，报数字前查文件尾部
  （"只写 /tmp 就报数字"是真实发生过两次的违规）
- **数据声明**：uv run python 连库实查（连接串在 .env，DB_PASSWORD=dmkwords_dev）

### 3.2 回归红线检查表（每次深审必跑）
1. 接口默认行为兼容：新参数全 None 时与旧版逐字一致？
2. 防刷/资金/状态机敏感路径 diff 是否为零接触
3. 既有测试是更新还是弱化（弱化 = 事故）
4. 全库 rg 同类调用点（改一个函数前先看谁在调）
5. 旧调用方（admin-web）是否引用被改的 miniapp 接口

### 3.3 高价值审查模式（实战检验过的）
- **派生字段追踪（E-09 同族）**：响应模型加派生字段（missing/counts/unread）的
  那一刻，grep 所有写操作端点逐一核对"重算了吗"——此模式已抓过 3 个 bug
- **并发窗口推演**：count-check-insert 有竞态吗？单线程测试测不出的并发缺陷
  （曾抓 P0：通知 send 的 rollback 会连坐主事务）
- **时序推演**：双保险回调（onCanplay+loadProgress）的触发顺序、幂等锁
  （_resumeApplied）是否完备
- **自评盖章识别**：UX 对齐表"全绿"必须附文件+行号证据，无证据 = 虚报（WM11
  曾实锤 4 项虚报，流程由此收紧）

### 3.4 简报质量判读信号
**好信号**：主动上报遗留/失败、过程坦白（"断言笔误一次"）、拷问式开工
（先问后做）、有截图/日志路径。
**坏信号**：数字与实物对不上、"已全部完成"但证据会被清库冲掉、文档手写
数字不跑 git status 核对（E-10 同族）。

## 八、给继任专家的最后忠告（前世的经验浓缩）

1. **信任但验证**——现任 GLM 质量很好，但"好"不等于"免检"。你的存在价值
   就是"基本属实"和"全部属实"之间的差距
2. **用户是唯一裁决人**——口径分叉永远列表格给用户选，你只给推荐和理由
3. **每次审查产出任务包**——问题清单不落成可执行的任务包 = 没审
4. **错误记忆库是项目最珍贵资产**——E-01 到 E-18 每条都是真金白银换的，
   审查时先对照 §二根因模式库，新坑修完督促入库
5. **WM2 标杆是尺子**——后续任何模块"做到什么程度算好"，答案永远是
   "对照 WM2 + docs/07 第十二章"
6. **诚实文化是你建立的**——"主动报备不惩罚、隐瞒是红线"从 DeepSeek
   自白事件立起来，守住它
7. 积分快没了的时候也要把审查做完——半审不如不审，用户的信任建立在
   "专家说过没问题就真没问题"
