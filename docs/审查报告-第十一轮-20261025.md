## 二、已复核确认（逐条给复核命令与结论）

### R11-01 · **P2（原判 P1，经专家复核后重定性——主审自纠）** · 容器镜像未钉 TZ 且未接入文档化生产路径

- 位置：`Dockerfile:44`（`CMD uv run … uvicorn`）、`docker-compose.prod.yml:23-26`（`environment` 只有 `TZ`）、`backend/config.py:51/55/66/84/104`。
- 复核（实测）：
  - `grep -nE "APP_ENV|TZ=" Dockerfile` → **无**；`deploy/start-backend.sh` 里的 `APP_ENV=production` + `validate_production` + `TZ` **不在镜像路径上**。
  - `Settings` 默认值实测：`APP_ENV="dev"`、`LOGIN_DEV_CODE="1234"`、`SECRET_KEY="change-in-production"`、`SMS_PROVIDER="mock"`、`PAYMENT_PROVIDER="mock"`。
  - `backend/domain/identity/auth.py:147-149`：`dev_code` 非空且相等即**放行**（生产要求置空）。
- **【主审自纠 · 2026-10-26】** 原判"起服务就能 `1234` 登家长端"**是错的**，专家推翻成立。实测纠错链：
  `backend/main.py:52` **无条件**调用 `settings.validate_production()`；`backend/config.py:151` 的早退门是
  `if not is_production_env(APP_ENV) and self.DEBUG`，而 `DEBUG` 默认 **False**（`config.py:52`）⇒
  镜像里 `APP_ENV=dev` + `DEBUG=False` 会**照样全量校验** → `SECRET_KEY=change-in-production` 命中红线
  → **启动即 RuntimeError 拒启（fail-closed）**。所以"能登"到不了登录页。
- **真缺陷（重定性后）**：
  1. **镜像未钉 TZ**（`Dockerfile` 无 `TZ`）⇒ 容器内 `datetime.now()` 走 UTC，而 MySQL 容器钉了 `+08:00`
     ⇒ **业务日边界错位 8 小时**（打卡/到期/周月报/"今日"统计）——正中 A18-0022 红线；同族既有事故形状。
  2. **镜像不在文档化生产路径里**：`docker-compose.prod.yml` 全 55 行**只有 mysql 服务**（后端不在其中），
     `docs/20` 的生产路线是原生 uvicorn + `deploy/start-backend.sh`（那里才强制 `APP_ENV=production` + TZ + 校验）。
     ⇒ Dockerfile 目前是**没有归属的产物**（能构建、跑不起来、也无人使用）。
  3. 危险诱饵仍在：若有人为了让它跑起来而加 `DEBUG=true`，早退门会**跳过全部红线**（固定验证码 + mock 支付全放行）。
- 修法（按专家 §5 修订）：① `Dockerfile` 加 `ENV TZ=Asia/Shanghai`（与 `start-backend.sh` 同源）；
  ② 二选一并写进 `docs/20`：**要么**把镜像接进生产路径（CMD 走 `start-backend.sh`，`APP_ENV=production` 由部署方注入，
  `.dockerignore` 补 `data/`/`外部专家意见/`），**要么**明确标注"镜像仅本地调试、生产用原生部署"并加一条 CI 守卫禁止其进生产；
  ③ `docs/20` 补一句"不要在镜像里用 `DEBUG=true` 换可用性"。

### R11-03 · **P2** · 任务运行记录 `running` 行永不成终态 ⇒ 看板"连续失败"恒为 1（假绿）

- 位置：`backend/tasks/registry.py`（`run_task` 失败分支 `rollback()` + **新插一行** failed）、`backend/common/batch.py:24-36`（批次任务中途 `commit()`）、`backend/domain/admin/task_specs.py:52-58`（`streak` 遇非 failed 即 `break`）。

### R11-05 · **P2** · 预约不校验"该孩子已在借同一本书"（`checkout` 必然失败的白约）

- 位置：`backend/domain/reading/reservation_service.py::create`（只查同书"进行中预约"、额度、可用副本；`BorrowRecord` 只用于额度计数）、对照 `backend/domain/circulation/service.py::borrow`（同书未还即拒）。
- 复核（实测）：`create()` 内无"同书在借即拒"判据；`checkout()` 先改状态再调 `borrow()`，被"该书尚未归还，不能重复借阅"顶回 → 事务回滚、预约仍挂着。
- 后果：锁一册副本 72h + 占 1 格额度 + 家长白到店；小程序只在 `borrowState==='borrowing'` 时前端拦，可直接调 API 或状态 `unknown` 时绕过（同族小程序发现 A1）。
- 修法：`create()` 补与 `borrow()` 同源判据（该孩子对该书有 ACTIVE/OVERDUE 借阅 → 422）；`checkout()` 在改状态**之前**预检。
