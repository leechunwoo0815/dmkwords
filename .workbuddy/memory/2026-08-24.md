## CI 失败定位（run 32739061604）与一次误判教训
- 现象：CI run 32739061604 `conclusion=failure`，卡在 gate step 1 `ruff format --check .`；单测等后续步骤实际全过（144 passed / 覆盖率 77.99%）。
- 真实根因（用户诊断正确，已实证）：`scripts/cleanup_uploads.py` 模块 docstring `"""` 之后缺一个空行，ruff format 要求补上。用 `git show 9bca885:scripts/cleanup_uploads.py` 提取旧 blob 跑 `ruff format --check --diff` 复现：`1 file would be reformatted`，diff 恰为 `+` 一个空行。
- **我的误判教训**：本地 `ruff format --check .` 全过（198 files），我据此错判为「CI uv 缓存导致 ruff 版本漂移」。实际是**比错了提交**——CI 跑的 headSha 是 `9bca885`，本地 HEAD 是 `78d7ab5`，reflog 显示后者是前者的 `commit (amend)`（开发模型格式化后 amend + force-push）。两个提交 message 完全相同，只有 SHA 不同，极易误导。
- **诊断口诀（下次先做）**：CI 红但本地绿 → 先 `gh run view <id> --json headSha` 比对 `git rev-parse HEAD`，再 `git reflog` 查是否 amend/force-push；确认同一 SHA 后才谈环境差异。
- 结果：amend 后的 `78d7ab5` 已触发 run 32739770479 **success**（4m19s），全量门禁 PASS 退出码 0、144 passed、BDD 12 scenarios、step 8 tsc 执行、覆盖率 77.99%。无需任何修复动作。
- 流程风险提醒：对 main 用 amend + force-push 修 CI，会让失败 run 指向已不可达的孤儿提交，破坏证据链可追溯性（本次即因此误导审查）。建议改为追加新提交（如 `style: format cleanup_uploads.py`）。
- 附：CI 144 passed vs 本地 131 的差异，来自 4de29d0 之后新增的 C31-C35 相关用例，非口径异常。
