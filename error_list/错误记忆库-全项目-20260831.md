### E-20260831-01 ruff ≥0.16 把 Markdown 内 python 代码块纳入 `format --check`（门禁级）
- 事实：WM13 架构关整改后重跑全量门禁，第 [1] 步 `ruff format --check .` 报
  `✗ 门禁失败`，未格式化对象是 **文档** `docs/任务包-20260831-WM13运营审核工作台.md:67:5`。
  该 .md 内嵌 1 个 ` ```python ` 块（`class AdminNotification(Base)` 字段表），
  ruff 要把 `id, scene` 单行拆成多行括号形式。
- 被抓方式：门禁日志第 [1] 步直接报 `✗ 门禁失败: ruff format --check .`；
  复验 `ruff format --check .` 得 `1 file would be reformatted, 249 files already formatted`，
  确认**未格式化范围仅此 1 个文件**，无其他连带。
- 根因：ruff **0.16.4** 起支持格式化 Markdown / docstring 内嵌的 Python 代码块。
  项目 `pyproject.toml` 的 `[tool.ruff]` 并**没有**任何 `.md` 相关配置——
  这是工具版本新能力带来的覆盖面扩张，**不是项目配置问题**，靠改配置规避属于掩耳盗铃。
- 修复（待执行）：`ruff format "docs/任务包-20260831-WM13运营审核工作台.md"` 后补 commit。
- **复发风险：高**（任务包/设计文档里嵌 python 代码块是本项目惯例，
  每个含代码块的 .md 都会炸门禁）。防复发：
  1. 写含 ` ```python ` 的文档后，**提交前必跑 `ruff format <该 .md>`**；
  2. 开发模型易犯的错：只跑 `ruff format <自己改的 .py>` 就宣称"ruff 全绿"，
     但门禁跑的是**全量 `ruff format --check .`**——**两者覆盖面不同，不得互相替代**；
  3. commit message 里写"ruff 全绿"前，必须确认跑过的是全量 check 而非指定文件。

### E-20260831-02 gate.sh 的 `run()` 失败不中断（读日志易误判）
- 事实：门禁日志同时出现 `✗ 门禁失败: ruff format --check .`（第 [1] 步）
  与后续 `[2] 单测 [3] BDD [4] 架构关` 正常执行。
- 根因：`scripts/gate.sh` 的 `run()` 实现为
  `if ! "$@"; then echo "✗ 门禁失败: $*"; FAILED=1; fi`——
  **只置位 `FAILED=1`，不 `exit`**，是有意设计（收集全部失败项后统一判退出码）。
- 影响：读日志时**看到后面步骤在跑 ≠ 前面步骤通过**，最终是否放行只看退出码。
- 防复发：**判门禁过没过，看退出码；看日志时要专门 grep `✗ 门禁失败`**，
  不能因为日志末尾在跑第 [7][8] 步就认为前面绿了。

### E-20260831-04 useSyncExternalStore getSnapshot 返回新对象字面量 → 登录后全站白屏（P0，门禁全绿）
- 事实：WM13 批次三 `useTodoCounts.ts` 的 `getSnapshot()` 每次调用返回
  `{ counts: cache, failed: loadFailed }` **新对象字面量**，违反 useSyncExternalStore
  快照引用稳定合同 → React 用 Object.is 比较快照永"不相等" → 无限重渲染 →
  `Maximum update depth exceeded` → **React 卸载整棵树**。该 hook 挂在 Layout（徽标），
  Layout 包裹全部受保护路由 → **登录后全站白屏**（登录页正常，未挂 Layout）。
- 被抓方式：用户手动验收打开 :5173 一片空白（恰好是验收流程本要抓的环节）。
  专家用浏览器子代理登录复现：仪表盘/通知中心/会员管理全部 0 节点白屏。
- 根因（三层漏检，每层都"绿"）：
  ① tsc 类型层全绿——这是运行时语义 bug，类型完全正确；
  ② 开发模型无浏览器工具（简报如实声明"目视验收未做"）；
  ③ **专家深审漏检**：用 curl 验了后端 API 全通，却没把"前端能渲染"当独立验证项——
  专家明明有浏览器子代理能力，审后端不等于验前端。
- 修复（已执行，用户授权紧急破例直修）：模块级 `snapshot` 稳定引用，
  `fetchOnce` 数据落地时才换引用；tsc 0 错 + 浏览器端到端复测
  （登录/仪表盘待办卡/通知中心双 tab/会员管理全渲染，报错清零，徽标 2 与计数一致）。
- **复发风险：高**（React 18 全项目在用 useSyncExternalStore）。防复发：
  1. **前端批次交付的验证清单必须含"浏览器端到端目视"**——curl 验后端 ≠ 前端已验证，
  专家审查改前端的前端批次时必须派浏览器子代理走登录-渲染链（本次白屏从 WM13-3
  提交起一直存在，两轮审查（简报核验+专家深审）都没发现，直到用户打开浏览器）；
  2. useSyncExternalStore 使用三查：getSnapshot 返回缓存引用 / subscribe 幂等 /
  数据落地才 notify；
  3. 全站无 ErrorBoundary——任何组件崩溃即整树卸载白屏。改进项挂 docs/09
  （App 根部加 ErrorBoundary 显示"页面崩溃请联系管理员"而非空白）。

## 二、工具链坑（审查/验证动作自身，防误判）

### T-20260831-01 zsh 会吞掉 `grep "A\|B"` 的 `\|`（致假阴性）
- 事实：`grep -n "WM13\|WM12" docs/LEDGER.md` 返回**空**，一度据此怀疑
  "开发模型声称更新了 LEDGER 但没更新"。单独 `grep -c "WM12"` 复验得 2、
  `grep -c "WM13"` 得 1——台账**是更新过的**，首次结论是**假阴性**。
- 根因：zsh 对未加引号/引号内的 `\|` 处理与预期不符（macOS BSD grep 亦不支持 `\|`，
  需用 `-E` 或 `grep -e A -e B`）。
- **复发风险：高**。防复发：
  1. 多关键词搜索用 `rg -e "A" -e "B"` 或分次单关键词，不用 `\|`；
  2. **"没搜到"不等于"不存在"——异常的空结果必须先复验再下结论**，
     否则会基于假阴性去指控开发模型，损害协作信任。

### T-20260831-02 rg 的 `-E` 是 `--encoding`，不是 grep 的扩展正则
- 事实：`rg -E "^(a|b)"` 报 `unknown encoding`。
- 防复发：rg 多模式用 `-e` 多次传入，或直接写裸正则（rg 默认即正则）。

### T-20260831-03 门禁进行中查库会读到中间态
- 事实：门禁 [2] 单测跑 pytest 时想查 `dictionary_words` 行数验证 340 万，
  但 conftest 正在操作数据库，此时查到的行数不可信。
- 防复发：**门禁/测试跑期间不做数据声明核验**，等跑完再查；
  代码层结论（有无 `.all()`、有无索引）不受影响，可先下。
