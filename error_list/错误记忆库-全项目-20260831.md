### E-20260831-01 ruff ≥0.16 把 Markdown 内 python 代码块纳入 `format --check`（门禁级）
- 事实：WM13 架构关整改后重跑全量门禁，第 [1] 步 `ruff format --check .` 报
  `✗ 门禁失败`，未格式化对象是 **文档** `docs/任务包-20260831-WM13运营审核工作台.md:67:5`。
  该 .md 内嵌 1 个 ` ```python ` 块（`class AdminNotification(Base)` 字段表），
  ruff 要把 `id, scene` 单行拆成多行括号形式。
- 被抓方式：门禁日志第 [1] 步直接报 `✗ 门禁失败: ruff format --check .`；
  复验 `ruff format --check .` 得 `1 file would be reformatted, 249 files already formatted`，
  确认**未格式化范围仅此 1 个文件**，无其他连带。
- 根因：ruff **0.16.4** 起支持格式化 Markdown / docstring 内嵌的 Python 代码块。
  项目 `pyproject.toml` 的 `[tool.ruff]` 并**没有**任何 `.md` 相关配置——
  这是工具版本新能力带来的覆盖面扩张，**不是项目配置问题**，靠改配置规避属于掩耳盗铃。
- 修复（待执行）：`ruff format "docs/任务包-20260831-WM13运营审核工作台.md"` 后补 commit。
- **复发风险：高**（任务包/设计文档里嵌 python 代码块是本项目惯例，
  每个含代码块的 .md 都会炸门禁）。防复发：
  1. 写含 ` ```python ` 的文档后，**提交前必跑 `ruff format <该 .md>`**；
  2. 开发模型易犯的错：只跑 `ruff format <自己改的 .py>` 就宣称"ruff 全绿"，
     但门禁跑的是**全量 `ruff format --check .`**——**两者覆盖面不同，不得互相替代**；
  3. commit message 里写"ruff 全绿"前，必须确认跑过的是全量 check 而非指定文件。

### E-20260831-02 gate.sh 的 `run()` 失败不中断（读日志易误判）
- 事实：门禁日志同时出现 `✗ 门禁失败: ruff format --check .`（第 [1] 步）
  与后续 `[2] 单测 [3] BDD [4] 架构关` 正常执行。
- 根因：`scripts/gate.sh` 的 `run()` 实现为
  `if ! "$@"; then echo "✗ 门禁失败: $*"; FAILED=1; fi`——
  **只置位 `FAILED=1`，不 `exit`**，是有意设计（收集全部失败项后统一判退出码）。
- 影响：读日志时**看到后面步骤在跑 ≠ 前面步骤通过**，最终是否放行只看退出码。
- 防复发：**判门禁过没过，看退出码；看日志时要专门 grep `✗ 门禁失败`**，
  不能因为日志末尾在跑第 [7][8] 步就认为前面绿了。

### E-20260831-04 useSyncExternalStore getSnapshot 返回新对象字面量 → 登录后全站白屏（P0，门禁全绿）
- 事实：WM13 批次三 `useTodoCounts.ts` 的 `getSnapshot()` 每次调用返回
  `{ counts: cache, failed: loadFailed }` **新对象字面量**，违反 useSyncExternalStore
  快照引用稳定合同 → React 用 Object.is 比较快照永"不相等" → 无限重渲染 →
  `Maximum update depth exceeded` → **React 卸载整棵树**。该 hook 挂在 Layout（徽标），
  Layout 包裹全部受保护路由 → **登录后全站白屏**（登录页正常，未挂 Layout）。
- 被抓方式：用户手动验收打开 :5173 一片空白（恰好是验收流程本要抓的环节）。
  专家用浏览器子代理登录复现：仪表盘/通知中心/会员管理全部 0 节点白屏。
- 根因（三层漏检，每层都"绿"）：
  ① tsc 类型层全绿——这是运行时语义 bug，类型完全正确；
  ② 开发模型无浏览器工具（简报如实声明"目视验收未做"）；
  ③ **专家深审漏检**：用 curl 验了后端 API 全通，却没把"前端能渲染"当独立验证项——
  专家明明有浏览器子代理能力，审后端不等于验前端。
- 修复（已执行，用户授权紧急破例直修）：模块级 `snapshot` 稳定引用，
  `fetchOnce` 数据落地时才换引用；tsc 0 错 + 浏览器端到端复测
  （登录/仪表盘待办卡/通知中心双 tab/会员管理全渲染，报错清零，徽标 2 与计数一致）。
- **复发风险：高**（React 18 全项目在用 useSyncExternalStore）。防复发：
  1. **前端批次交付的验证清单必须含"浏览器端到端目视"**——curl 验后端 ≠ 前端已验证，
  专家审查改前端的前端批次时必须派浏览器子代理走登录-渲染链（本次白屏从 WM13-3
  提交起一直存在，两轮审查（简报核验+专家深审）都没发现，直到用户打开浏览器）；
  2. useSyncExternalStore 使用三查：getSnapshot 返回缓存引用 / subscribe 幂等 /
  数据落地才 notify；
  3. 全站无 ErrorBoundary——任何组件崩溃即整树卸载白屏。改进项挂 docs/09
  （App 根部加 ErrorBoundary 显示"页面崩溃请联系管理员"而非空白）。

### T-20260831-01 zsh 会吞掉 `grep "A\|B"` 的 `\|`（致假阴性）

     否则会基于假阴性去指控开发模型，损害协作信任。

- 防复发：**改一个入口的文案时，必须同时检查它的跳转目标是否匹配新文案**；
  "改文案不改行为"会产生比原文案更糟的误导（用户按新文案预期点了，拿到旧行为）。

### E-20260915-19：`calc(25% - Xrpx)` 正好等于容器宽 → 浮点误差吃掉一列（**本族第三例**）
- 现象（用户第 4 轮第 1 条）："我的页面布局又回到了最古老的状态，留白那么大"。
  截图里「成长中心」7 个入口排成 3+3+1，格子被拉高、满屏留白（应为 4 列）。

## 七十三、受控输入/DOM 直写边界 · 时间口径（2026-09-15 第六轮 门店扫码签到）

### E-20260915-20：`el.value = ""` 清不掉输入框 —— 扫码连扫会**拼接成废码**
- 现象（我自己实操发现，非用户报）：管理端扫码签到面板，扫完一张券后输入框里**还留着上一张的券码**
  （提交路径看着一切正常：提示弹了、名单刷新了、焦点也在）。接着扫第二张 → 实测输入框内容变成
  `TK00001000026F7BTK00001000026F7B`（扫码枪在光标处**追加**）→ 后端回「入场券不存在」→ **连扫彻底失效**。
- 真因：`inputRef.current.input.value = ""` 只改了 DOM，**AntD/rc-input 内部还留着 React 侧的值**；
  提交后 `setBusy(false)`/`setRecent(...)` 触发重渲染，内部值被写回 DOM，清空被"撤销"。
- 修复：走**原生 setter + 派发冒泡 input 事件**，让 React 的 value tracker 同步到空串：
  ```ts
  const desc = Object.getOwnPropertyDescriptor(Object.getPrototypeOf(el), "value");
  desc?.set ? desc.set.call(el, "") : (el.value = "");
  el.dispatchEvent(new Event("input", { bubbles: true }));
  ```
- 防复发：**只要代码用 ref 直写 React 输入框的 `.value`，就必须补这一步**（React 会把它当"未变化"而回滚）。
  判别信号：清空后"过一会儿又回来了"= 内部状态回写，不是 CSS/浏览器问题。

### E-20260915-21：展示给门店的时间用了 UTC —— 差 8 小时
- 现象（同轮自查发现）：扫码签到"最近签到"列表里，**失败行**的时间比**成功行**早 8 小时。
- 真因：成功行取后端返回的本地时间串（`checked_in_at`），失败行是前端 `new Date().toISOString()`
  —— `toISOString` 是 **UTC**，而门店对账看的是墙上时钟。
- 修复：新增 `nowHms()` 用 `getHours/getMinutes/getSeconds` 取本地时分秒。
- 防复发：**凡是给人看的时间戳，一律不用 `toISOString`**（它是序列化/传输格式）；
  同一列表内不同来源的时间必须统一时区口径（本族第二次：早前"成绩待同步"也是同一事实两个源）。

### E-20260915-22：设计做完、入口没接 —— 🎟️ 占位下的 `qr-*` 死样式（**本族第二例**）
- 现象：`activity-detail`「我的报名」一直是 🎟️ emoji 占位，而 `qr-section/qr-placeholder/qr-emoji/qr-hint`
  四个类早已写在 wxss 里、模板却只用了其中一半。（与 §七十 E-08「设计做完、模板被掏空」同族，

## 七十四、小程序 canvas 原生层 · 状态枚举 · JSX 改动静默失效（2026-09-15 第六轮追加）

### E-20260915-23：`canvas type="2d"` 首帧错位 —— 二维码画到了封面/按钮上（用户报"遮挡"的真因）
- 现象（用户第六轮）：「小程序活动页，二维码和条形码会覆盖遮挡下面的按钮」。
  自查截图复现：二维码整块画在 **hero 封面**上、条形码画在按钮附近，而它们各自的布局框里**是空的**。
- 真因：**2d canvas 是原生层（native component）**。首帧绘制若发生在页面布局稳定之前，
  画面会停在旧坐标上，之后**不会自愈**（等 5 秒仍是错的）。
  证据链：①首帧截图错位；②手动再调一次 `_renderTicket` 立即归位；③冷启（reLaunch）用"补画"后正确。
  **不是**单纯的内容压住按钮，也不是 z-index 问题——移动 section 位置解决不了它
  （我一开始按"内容顺序"理解，是走了弯路的）。
- 走过的弯路（**重要，别再走**）：先试了"布局稳定后补画"（0/350/1200ms 各画一次），
  当场截图看着是好的，**下一次冷启又错位**——原生层的坐标是靠不住的，补画只是碰运气。
- **最终修复：展示层不再用 canvas。** 画布移到可视区外（`position: fixed; left: -9999rpx`）
  只当"渲染后端"，用 `wx.canvasToTempFilePath` 导出临时文件，页面展示改成 `<image src>`。
  `<image>` 是普通节点，没有原生层的坐标问题，这一类 bug 从根上消失。
  出图失败则露出券码文本兜底；`canvasToTempFilePath` 的 `success` 里 setData 图片路径。
- ⚠️ 配套坑：出图画布**必须与展示 `<image>` 同比例**（二维码 420rpx×420rpx、条形码 620rpx×120rpx），
  否则图片被拉伸——第一版两个画布共用一个 `.draw-canvas{420×420rpx}`，
  条形码被横向拉宽且发虚（模块从 1px 被插值成 1.4px，扫码枪可能就废了）。
- 验证方法（比"看着对"强得多）：导出物在开发者工具的临时目录里
  (`~/Library/Application Support/微信开发者工具/.../WeappFileSystem/.../tmp/xxx.png`)，
  **直接把那个 PNG 抓出来解码** → 二维码 720×720 解出 `TK00002000010CC2`、
  条形码 1065×204 经 macOS Vision 解出同一券码。
  （注：从屏幕截图再解码会因缩放+重采样偶尔失败，**不能**用它否定成品；
  怀疑渲染问题时，优先解"导出物"这个原始像素。）
- 防复发：**小程序里不要用 canvas 当"展示层"**（它只配当渲染后端）；
  用户说"遮挡/覆盖"时先怀疑**渲染层错位**，别急着调间距或改顺序。

### E-20260915-24：状态枚举漏一个分支 → 兜底文案"状态更新中"（**本族第四例**）
- 现象（用户原话）：「按钮显示状态更新中，是什么意思？」
- 真因：wxml 的按钮分支覆盖了 `enrolled / pending_payment / refund_pending / cancelled`，
  **漏了 `checked_in`** → 已签到的孩子落到 `wx:else` 兜底 → 显示"状态更新中"。
  （同族前三例：T4 裸输出英文 status、WM9 枚举补齐、book-detail 判定源分叉。）
- 修复：补 `checked_in` 分支（「已签到 ✓ 欢迎参加」）+ 兜底文案改成"怎么办"
  （「状态未同步，请下拉刷新或联系馆员」）；券码区同步显示「已于 14:51 签到」。
- 防复发：**状态机的每个态都要有明确文案；兜底分支必须写"用户下一步做什么"**，
  禁止"加载中/更新中/处理中"这类不说明问题的占位文案。

### E-20260915-25：改 JSX 顺手删掉别的 Drawer 的 `open` prop → 功能静默失效
- 现象：管理端「报名名单」按钮点了没反应（抽屉不开），无任何报错、无 console 异常。
- 真因：我在同一文件里插入"活动详情抽屉"时，把报名名单 Drawer 的
  `width={640} open={!!enrollActivity}` 整行删掉且忘了加回 → `open` 恒为 undefined。
- **抓它的不是 tsc、不是 lint、不是单测，是浏览器实操**（tsc 对 JSX props 缺失无能为力）。
- 防复发：**改 JSX 结构时必须回看被改动标签的完整属性**；
  新增交互组件后，"点一遍主路径"是硬动作——本轮的详情页跳转就是靠这一步发现全坏。

### E-20260915-26：抽屉间跳转时自动聚焦被"焦点回填"顶掉
- 现象：从「活动详情」抽屉点「报名名单」跳到名单抽屉，扫码框**没有自动聚焦**（直接点行进的路径正常）。

  ③ 视觉基准逐字取自图书详情封面（`radius 6 / 1px var(--paint-border) / objectFit cover /

  凭证放大 2 倍仍清晰。
- **复发风险：高**（"同一交互两套实现"是本项目最稳的复发模式：批量生成/退款/审核/预览都犯过）。
  防复发：**同一交互只准有一个实现** —— 第 2 个页面要用时，先把组件抽到 `components/`，
  再回头改第 1 个页面；发现自己在第 2 个页面"照着抄一遍"时，就是该抽组件的信号。

### E-20260915-29：antd `preview={{ mask: null }}` ≠ "用默认遮罩"，而是"**不要遮罩**"
- 事实：给共享组件加 `maskText` 参数时按直觉写 `mask: maskText === null ? null : maskText`，
  以为 `null` 会回落到 antd 默认（眼睛图标 + 「预览」）。实测周报图上 `.ant-image-mask`
  **count = 0**，遮罩**完全没渲染**，与预期相反。
- 被抓方式：浏览器里 `document.querySelectorAll(".ant-image-mask").length === 0`
  （结构性证据，不是靠"看着没有"）。
- 根因：antd `Image` 的合并是 `{ mask: <默认眼睛+文案>, ...restPreviewProps }`
  ——调用方传入的 preview **展开在后**，所以 `mask: null` 会**覆盖**默认值；
  而 rc-image 内部 `previewMask && canPreview && <div class="mask">` 对 `null` 判假 → 不渲染。
  即：**"想用默认值"的正确写法是不传这个键，不是传 `null`**（对象展开与 `??` 在此处语义不同）。
- 修复：删掉 `maskText` 参数（只有一个调用方，且它本就想用默认），组件内固定
  `preview={{ mask: "预览" }}` —— 与图书详情封面逐字一致，天然统一；少一个参数少一处歧义。
- 防复发：**给"可选样式参数"设计 `null` 语义前，先看库的默认值合并顺序**；
  能用"不传"表达缺省的，就别引入 `null` 分支。

  ① 后端把"家长名下孩子"抽成**唯一序列化出口** `identity.auth.children_payload()`

### E-20260916-36：`getApp()` 在 `App.onShow` 里返回 undefined（微信经典坑）
- 事实：修 35 时第一版把刷新挂在 `app.onShow()` 里，探针显示
  `FAILED Cannot read properties of undefined (reading 'globalData')` ——
  `utils/request.js` 第一行 `const app = getApp()` 拿到 **undefined**。
- 根因：`App.onLaunch/onShow` **执行期间 App 实例尚未就绪**，此时 `getApp()` 返回 undefined。
  错误信息指向 `globalData`，完全看不出"时机不对"，极易误判成接口/鉴权问题。
- 修复：① 刷新改挂在**页面 onShow**（页面上下文里 `getApp()` 一定可用）；
  ② `utils/request.js` 首行加显式守卫：`if (!app) reject('应用未就绪（勿在 App.onLaunch/onShow 里发请求）')`
  ——把"时机错误"翻译成人话，全项目所有调用方都受益。
- 防复发：**不要在 App 生命周期钩子里发请求**（要发就 setTimeout 0 或放到页面 onShow）；
  被 undefined 干扰时先看错误信息是不是"时机型"而非"逻辑型"。

### E-20260916-37：**去重锁没有超时** —— 一次悬挂把后续刷新永久锁死
- 事实：`refreshChildren` 用 `_inflight` 做并发去重（多个调用方共享同一次请求）。
  探针实测：`api.myChildren()` **进入了但 promise 永不 settle**（既不 success 也不 fail），
  于是 `_inflight` 永远非空 → 64 秒后下一次调用仍然 `return _inflight`（拿到一个死 promise）
  → **刷新功能静默失效，且页面的 `await` 会一直挂着**。
- 根因：**用 Promise 做锁时没有超时**。底层（`wx.request`/`wx.getNetworkType` 的回调）在
  个别环境下可能一个都不触发；没有超时兜底，"锁"就变成"死锁"。
- 修复：`Promise.race([api.myChildren(), 6s 超时])`；失败/超时后清零节流时间戳（下次 onShow 立刻重试）；
  成功才吃 30 秒节流。
- 防复发：**任何"共享在途请求"的锁都必须配超时**（`Promise.race` 是标配），
  并且失败路径要能自愈（清锁 + 清节流），否则一次网络抖动会永久废掉这个功能。

## 八十一、预览渲染族（2026-09-17 用户报障 封面预览"又小又糊"）

> 本族共性：**跨浏览器渲染差异 + 渲染前置条件（尺寸/解码时机/动画时序）**。

### E-20260917-42：**封面预览"又小又糊"** —— antd 预览大图的**百分比高度链**在 Safari 下退化
- 用户报障：「Harry Potter… 和 Charlotte's Web 的封面预览非常模糊，其他图书正常；我去 uploads 看这两张图是正常的」。
  后续澄清：是**管理端图书编辑页的封面预览**，且**无痕窗口必现**，我内置浏览器（Chromium）一直正常。
- **先排除的（都带实测，别跳过这步）**：① 全部 35 本封面同规格 600×900、量化表逐字节相同（非二次压缩、非渐进式）；
  ② `/books/{id}/cover-media` 与小程序 `/covers/{id}` 都是 `FileResponse` 原样返回，全后端无按需 resize；
  ③ 文件内容锐度：报障两本 65.5/53.9 vs 其他 62–65，**同一水平**；④ 浏览器渲染像素 vs 源图直缩：锐度差 3%（正常重采样损耗）。
  → **文件与链路都没问题**，"糊"不在数据侧。
- **真因**：antd 预览大图 CSS 是 `.ant-image-preview-img { max-width: 100%; max-height: 70% }` ——
  **百分比高度**必须相对"父级已解析高度"才有意义；预览 wrapper 是绝对定位 + flex 居中，其高度在 **Safari**
  下按内容计算 → 这条链退化：实测 784px 高的窗口里预览只有 **212px**（≈27%），而 Chromium 是 **549px**（=70%×784，完全吻合）。
  封面里的书名原本就占整图 5% 高度，缩到 212px 后只剩几像素 → 用户看到的"非常模糊"**其实是"太小"**。
  用户原话里的顺序（"**小**且模糊"）就是线索。
- 修复分五步（每加一步都是用户复验时当场发现的下一层，别指望一次到位）：
  **① 尺寸链**：`admin-web/src/styles/paint.css` 用**视口单位**断掉百分比依赖，上限 70% → 82vh
  （实测 366×549 → **429×643**，`max-height` 计算值从 `70%` 变成 `642.88px`）。
  **② 竞态（真凶）**：预览大图**没有显式 width/height**，布局尺寸完全取决于“解码出的 intrinsic size”——
  预览挂载瞬间若该图还没解码完，尺寸为 0/占位值，**Safari 会按错尺寸栅格化并保持不回刷**
  （Chromium 会重栅格化，所以我这边连试多次全正常）。这解释了“每次刷新换一本、无规律”。
  修法：`PreviewImage.tsx` 新增 `useNaturalSize(src)`（同一 URL 预加载取 naturalWidth/Height，
  命中缓存零额外请求），把真实尺寸作为 `preview.width/height` 交给预览 img，**挂载即有正确布局**；
  命令式 `useImageViewer` 路径同样补上。
  ⚠️ **连带坑**：补了固定属性后 box 尺寸由属性决定，而 `max-height` 会把它压矮，而 antd 的
  `.ant-image-preview-img` 默认 `object-fit: fill` → **图会被纵向压扁**（实测 box 600×643 装 600×900）。
  故 CSS 必须同时 `object-fit: contain !important`（box 可矮，图在 box 内等比居中不拉伸）。
  最终实测（Chromium 1208×784）：attrs `600x900` / box `600x643` / objectFit `contain` / 图视觉 430×644 比例正确。
  **③ 连带副作用（用户复验时当场报障）**：补上尺寸后**入场动画看得见了**。antd 预览默认
  `transitionName: 'zoom'`——动画**从“点击点”放大到居中**，而缩略图在页面左侧 ⇒ 图从左边滑到中间。
  以前图未解码不显形所以看不出来，现在全帧可见 ⇒ 用户看到“先在左边闪一下再跳到中间，好难受”。
  逐帧采样证实：t=68ms 已是最终态(x=297,w=600) → t=118ms 跳回起点(x=86,w=420) → 约 300ms 动画回中。
  **修法**：`preview.transitionName = ""`（rc-motion `CSSMotion.js:27` 的 `!!(props.motionName && ...)`
  见假值即不启用动画；遮罩淡入走独立 `maskTransitionName`，仍保留）。
  验证：逐帧采样 0→408ms 只有 **1 个**位置/尺寸状态（x=297 / y=71 / 600×643 全程不变）。
  **④ 入场动画重做（用户否掉了 ③ 的"直接显示"）**：用户在 ③ 之后反馈「效果比以前差了，以前有动画的，
  很丝滑，点击之后像直接从小图放大到大图的预览」。逐帧采样确认 ③ 之前的问题是**预滚帧**：
  rc-motion 的 appear class 晚一帧才加，所以动画前会先按最终位置画约 60ms（t=17 已是最终态 600×643，
  t=77 才跳回起点 120×129）→ 用户看到"先闪一下最终态、再跳回起点飞过来"。
  **修法**：关掉 antd 自带 zoom（`preview.transitionName = ""`），改用自己写的 CSS 动画 `pv-fly-in`
  （`paint.css`）：点击瞬间把缩略图相对屏幕中心的位移/起始缩放写进根元素变量
  （`--pv-dx/--pv-dy/--pv-scale`，`PreviewImage` 的 `onClickCapture` 抢在 rc-image 打开预览前写），
  预览 img 从**元素第一帧**即起始态 → 从缩略图那一侧的小尺寸飞到居中；`animation-fill-mode` 不设 forwards，
  动画一结束就把 transform 交还 rc-image（缩放/拖拽不受影响）。命令式预览（无点击点）在 viewer 的 open 方法里
  复位成"中心 + 0.88 缩放"，避免沿用上一次的坐标。含 `prefers-reduced-motion` 兜底。
  实测逐帧：t=27 首帧 101×108 @(272,285)（缩略图正是 72×100 @(277,289)）→ 平滑放大 → t=355 到 600×643，
  **全程单调、无预滚帧**。
  **⑤ 预览里滚轮不该滚页面（用户报障）**：`.ant-image-preview-wrap` 带 rc-dialog 的 `overflow-y: auto`，
  内容比视口高时可滚动 → Safari 把滚轮默认行为落在它身上（出现滚动条、图被滚到看不见）；而 rc-image 的
  滚轮缩放处理器在 React 里是**被动监听**，`preventDefault` 无效、拦不住。
  修法：`.ant-image-preview-wrap { overflow: hidden !important }` 关掉这条滚动通道。
  实测：滚轮后 img transform 变 1.5×（缩放生效）、`window.scrollY=0`、`wrap.scrollTop=0`。
- 防复发：**给"尺寸上限"写百分比前，先问父级高度是不是已解析值**（绝对定位/flex 内容高度下不成立）；
  跨浏览器尺寸类问题**必须两个引擎都量**，别用单一浏览器"看起来正常"结案。
  排查顺序照 E-33：先排除数据（文件/编码/端点），再怀疑渲染；用户描述里的形容词优先级 = 事实优先级（"小"比"模糊"更接近根因）。
  **改了"渲染前置条件"（尺寸/布局/绘制时机）之后，必须回头看一眼依赖它的动画与过渡**——本例三处修复
  层层相扣（① 尺寸链 → ② 补 intrinsic size，动画随之变可见 → ③ 关入场动画），每次只修一层就会被下一层打回来。
  **动画类改动必须逐帧采样验收**（开→稳定期间每帧记 rect/opacity）："看起来有没有跳"肉眼不可靠，
  逐帧一比就知道是预滚帧、还是动画起点不对；改动画前先量出**参考轨迹**，改完对拍。
  **跨浏览器差异的取证姿势**：用"逐帧采样 + 读 CSS 计算值"（`getBoundingClientRect` 逐帧 +
  `getComputedStyle().maxHeight/transform`），比反复肉眼截图快且不会误判；修完用同一手法**回测到只剩 1 个状态**才算完。

## 八十二、测试里的**时间炸弹**：写死的"明天"到期日（2026-09-20 fix44 施工中实测）

- **现象**：fix44 全量门禁跑出 `4 failed, 477 passed`，四条全在活动域：

  该值在 **2026-09-20 15:19** 变成过去 → 后端"开始时间必须在未来"校验拒绝 → **测试自己过期了**。
  上一次全量门禁（09-17，`gate-115422`）还是绿的，纯属日期未到。
- **同类残存**：`test_wm1_dashboard.py` / `test_r313_guards.py` 用的是 `"2099-01-01T10:00:00"`
  —— 同样是绝对时间，但年份够远（**远期哨兵**），永不到期，属可接受写法。
  反例的另一半：`test_p0_fix20_a.py` 的 `"...T15:00:00.000Z"` 之所以当天没红，是因为带 `Z` 按 UTC 解析
  （+8 时区下等于当地 23:00）——**靠时区差异续命**，同样会在当晚 23:00 到期。
- **修法（四文件）**：把写死日期改成**相对未来**——
  `_future_iso(days=7)` = `datetime.now() + timedelta(days=days)` 后格式化；
  测试语义不变（仍要求未来时间），且永远不会过期。
- **防复发（已机化）**：`scripts/check_fake_assertions.py` 新增**规则 B 时间炸弹**（同文件顶部 docstring 已同步，红线 31）：
  扫描 `start_at` / `end_at` / `enroll_deadline` / `publish_at` / `deadline` / `expire_at` 键上的字符串时间字面量，
  年份落在 **[当前年, 2049]** → FAIL；年份 ≥ 2050 视为远期哨兵放行。
  自证：注入 `{"start_at": "2026-12-01T10:00:00"}` → 命中 FAIL；删除 → 恢复 0。
- **教训（跨项目通用）**：**测试里的绝对时间 = 定时炸弹**，只要它落在"合理项目寿命内"就一定会炸，
  而且炸在无关的人身上（谁当天跑门禁谁倒霉）。**要么相对时间，要么远期哨兵，二者必居其一**；
  "明天"这种意图更要写相对量，因为"明天"会变成"昨天"。

- **真因**：我在 wxml 里写块注释时用了 JS 习惯的 `*/` 收尾：
  ```xml
  <!-- …客户口径变更…（「我的报名」列表项上的按钮进入）。 */      ← 错：应写 -->
  ```
  WXML 的注释只认 `-->`，于是这条注释**一路吞到下一个 `-->`（第 74 行）**，
  中间 50 多行模板全被当成注释，标签配对整体错位 → 第 79 行的 `</block>` 被判定为"缺 `</view>`"。
  **报错行（79）与真凶行（18）相差 60 行**，靠读错误信息基本不可能定位。
- **怎么定位出来的（方法值得复用）**：GUI 猜了三轮无果后，改读**开发者工具自己的日志**——
  `~/Library/Application Support/微信开发者工具/<hash>/WeappLog/logs/<最新>.log`：
  ```
  [ERROR][PROJECT][T.onInstanceError] Error: 编译 .wxml 文件错误 …
  ./pages/activity-pkg/activity-detail/activity-detail.wxml:79:7: expect end-tag `view`, near `block`
  ```
  再用「忠实解析器」（跳过注释、跨行标签、引号内不识别 `>`）复现，才看到真正的吞并行为：
  `L16: 注释 → L74`。**注意：我第一版"按行正则"的平衡检查报的是"闭合 ✓"**——
  因为按行处理时注释只算普通文本，永远看不出吞并。**轻量扫描器会撒谎，要用与编译器同构的解析。**
- **修法**：`*/` → `-->`。
- **防复发（已机化）**：`check_miniapp_style.py` 新增 **R14 WXML 结构**：
  ① 注释必须以 `-->` 收尾；② 注释体内不得出现 `*/`；③ 标签配对（含跨行标签、引号内 `>` 不误判）。
  实树注入自证：把注释改回 `*/` → R14 报 4 项；还原 → 0 项。同步更新 docstring 规则清单（红线 31）
  与 `CLAUDE.md` 门禁表、`gate.sh` 注释的 R1–R13 → **R1–R14**。
- **另一个教训（工具环境）**：本次 GUI 验证被 macOS 通知中心的全屏浮层挡住（`notificationcenterui`
  持有 [0,0,1470,956] 的窗口，所有点击都被它接走），`killall NotificationCenter` 后仍会重新弹出——
  **当自动化点击全部落空时，先查"当前像素所有者是谁"**（报错信息会直接写明 pid 与窗口 bounds），
  而不是继续怀疑自己的坐标。

## 八十四、回页刷新把整页卸载 → 滚动位置被打回顶部（2026-09-20 用户实测）

- **现象**：活动详情页点开配图预览，关掉图片回到页面——**页面跳回活动最上面**。用户原话：
  「我看到哪里点开图片看一下，关掉图片应该还在原处才对」。
- **根因**：`wx.previewImage` 关掉后会触发页面的 `onShow`，而我的刷新逻辑是
  `onShow → load() → setData({loading:true})`；而 wxml 里骨架屏与正文是**互斥的 wx:if**
  （`<loading-skeleton wx:if="{{loading}}">` / 正文 `wx:if="{{!loading && ...}}"`）——
  置 loading=true 的瞬间**整页被卸载**，数据回来再重挂，滚动位置自然归零。
- **修法**：`load({ silent })` —— 骨架屏只在「首次进入 / 出错重试」出现；**回页刷新一律静默**
  （不置 loading，只换数据）。同族三页一起改：活动详情、活动列表（从详情/入场券返回同样会跳顶）、
  入场券页。
- **防复发**：
  1. **"回页刷新"与"首次加载"必须分开**：凡 `onShow` 里重拉数据的页面，刷新路径**不得**翻
     `loading`；骨架屏与正文互斥的写法下，翻 loading = 整页重挂 = 丢滚动位置（还有闪烁）。
  2. 桩测试锁死：`/tmp` 脚本断言"首次进入 loading 轨迹 = [true,false]；回页刷新 loading 轨迹 = []"，
     顺带断言配图 URL 必须走 `media.fullUrl`（绝对地址 + token）——上一批刚因为漏了这一步导致全裂图。
  3. 这是一类**只在真机/模拟器手感上才暴露**的问题：门禁与单测都看不见滚动位置，只能靠目视或用例化
     断言"不该发生的事没发生"（本次用的就是后者）。
